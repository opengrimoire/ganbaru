# Chat schema

Chat persistence separates organizational conversation, provider execution, authorization, workspace identity, and derived presentation. This keeps a project channel stable when a provider session fails or is replaced and prevents provider-native trust from becoming application authority.

Authorization semantics are normative in [Chat access control](../access-control.md). This document describes durable ownership and relationships.

## Organizational layer

The current organization layer is project-owned channels. Each project has a built-in general channel and may have additional navigable or archived channels. Channel identity, name, archive state, ordering, and membership are independent of any provider.

Projects and working folders replicate between devices, so Chat creates a project's general channel and each folder's current-folder execution environment (never for an archived folder) on demand, when a device that writes Chat lists channels, environments, or assignment targets, or resolves a run target. The general channel's ids derive from the project id, so devices agree on them; fresh vaults therefore seed no conversations. A device that cannot write Chat shows only stored rows. A conversation has exactly one channel.

Organizational ids are a kind prefix and 128 random bits, or derive from their inputs when devices must agree: a reply thread's id derives from its root message and a work assignment input's id from its message. They fit the 128-byte sync row key bound. Ordinary commands archive or end organizational rows instead of deleting them: agents are archived, and an agent's channel membership ends with a removal timestamp that every reader filters. Device-local rows that reference organizational rows cascade when that row is deleted.

A channel note is a short fact about how work goes in one channel, up to 1000 characters, stored in `chat_channel_notes` as replicated organizational content and deleted with its channel. Only a person writes a note: a trigger refuses a note whose editor is not the local person or a human participant, outside the sync applier. A teammate may propose a note; a person accepts it into a row whose id derives from the proposal, so two devices that accept one proposal write one note, or dismisses it as a deleted row with the same id.

Membership records participant identity, capability, history boundary, defaults, and current authorization revision. Personal navigation sections and last-selected channel are device-local presentation state rather than shared organization membership.

Canonical messages and coordination events retain channel identity, author or actor identity, sequence, reply or reference provenance, and delivery state. A provider transcript is not a replacement for this history.

Broader groups, cross-project workspaces, and direct messages are future schema work unless a later migration and feature specification introduce them.

## Channel and provider-session links

A channel can link several provider sessions over time in a stable order. The link explains which execution continuation contributed to which organizational scope and when it was active. Replacing or handing off a provider session creates or updates linkage without rewriting earlier channel history.

Provider thread rows store the continuation and execution timeline understood by the application. Provider-native IDs are opaque handles. They do not encode membership, folder authority, audience, or ownership.

Provider configuration and model mapping are separate from provider sessions. Changing a configured provider does not mutate historical messages or sessions.

## Canonical events and projections

Provider events are validated, bounded, normalized, and appended as canonical application events. Sequence and projection changes commit before a lightweight frontend notification is emitted. Event, item, and request IDs that a provider numbers per process are scoped to the provider session, and a projection row keyed by a provider item ID is only ever updated by events of its own thread.

The combined timeline, turn state, message view, command activity, usage summary, and inspector data are projections. They may be persisted for performance but remain rebuildable from canonical events and organizational messages. Projection rebuild preserves channel and authorization scope. Each provider thread keeps a device-local change clock that every write to a timeline row or turn advances, with a bounded record of deleted rows, so a live reader rereads only the rows written after the clock value it last saw and reloads in full when that record no longer reaches back far enough.

Provider-reported changed paths are converted to canonical relative paths only after verifying that they remain below the authorized workspace. Absolute paths, traversal, malformed paths, duplicates, and secret-bearing diagnostics are removed at ingestion.

## Assignments and execution targets

An organizational thread or run may remain targetless for discussion and planning. Current schema explicitly permits targetless Chat assignments. Before native work begins, the application locks the run to exactly one authorized target, either:

- A managed or externally bound project working folder.
- A private scratch generation.

A run cannot mix both. Target consistency constraints and service validation ensure that a selected folder or scratch environment belongs to the expected project and logical scope.

Working-folder identity is portable. Managed paths are relative to the active vault. External absolute bindings, executable paths, Git identity, and current filesystem fingerprints remain device-local.

Scratch generations have logical identity, ownership, lifecycle, provenance, and cleanup state. Their native paths remain device-local. Promotion into a managed folder is an explicit transfer, not a target mutation.

Daily teammate usage (`chat_teammate_usage_daily`, table 399) replicates one row per executing device, teammate, and local date, keyed by the device so only that device writes it. Its counted tokens, working seconds, and run count only grow and merge by maximum, and a row follows its teammate when the teammate is deleted. The executing device adds the increase since its last flush every minute and when a run stops working; the `summarized_*` columns of `chat_agent_run_usage` record what each run already added, so a flush counts nothing twice. Usage lands on the device's local date at flush time, and reads sum the devices for each day within the last 90 local days.

Assignment budgets (`chat_assignment_budgets`, table 398) hold at most one row per work assignment, keyed from the assignment id so concurrent sets on two devices merge into one row. The token and working time limits, who set them, and when replicate as one register, so a concurrent set keeps one whole pair of limits; the used counted tokens and used working seconds are separate groups that only grow and merge by maximum, written by the executing device, so a limit change never loses usage and usage never undoes a limit change. Clearing a budget deletes the row, and a later set creates it again. A row without a limit is invalid, and a row follows its assignment when the assignment is deleted. A new assignment gets a row, for a delegated child, its parent's remaining amounts (floored at the minimum limits) or the child teammate's default when that is lower, else the limits of the work of the same teammate it follows, else the teammate default (`default_assignment_token_limit` on the policy revision); no source writes no row. A continuation or a retry that moves work to another device starts a fresh row with the same limits; a retry on the same device requeues the same assignment and keeps its row, because the used amounts cannot go back down. A default or parent-derived budget records no setter, and setting a budget from the thread records the person here. The executing device writes the used amounts when a run crosses 75, 90, or 100 percent of a limit and when the run settles; warnings are derived from the replicated amounts, never stored. Reaching a limit fails the assignment with `state_reason` `budget_limit_reached` and a `failure` update whose payload carries `code`, `limit` (`tokens` or `working_time`), `used`, and `limitValue`. A run that a provider usage limit ends fails with `provider_usage_limit` and a payload with `code` and `resetsAt`. Retrying work whose budget is reached is refused until its limit rises.

## Access profiles and authorization revisions

Portable rows store participants, memberships, channel capabilities, history cutoffs, reusable access profiles, immutable or historically interpretable profile revisions, exact resource grants, assignments, approvals, authorization revisions, and revocations. Command receipts stay device-local, because a retry happens on the device that sent the command.

Historical runs retain the revision and target under which they were authorized. A later profile edit does not retroactively change that meaning. A reduction may revoke active work, but a more permissive revision does not silently upgrade it.

Participants, AI teammates, teammate policy revisions, access profiles, and profile revisions replicate. Revision rows are immutable and carry no stored number: the displayed revision counts the rows of the teammate or profile in `(created_at, id)` order. A teammate and a profile name their current revision with a pointer that the command writing a revision sets, together with the revision's safety mode or folder capability ceiling, so concurrent edits resolve to the more restrictive revision (a Custom safety mode ranks least restrictive, because the provider's own configuration governs it); readers use the pointed revision, or the newest arrived one while it is missing, except that approval coverage then follows the safety mode the pointer copied. A pointer whose copied safety mode or capability ceiling disagrees with the revision it names, which only a corrupt or dishonest operation can write, gives its teammate or profile no effective revision, so the teammate is refused until an honest edit replaces it; the materialize hook revokes the affected teammates' authorizations and logs the pointer instead of failing the apply, which would stop every later apply. A teammate records the device that created it as its home device, which executes its assignments. Commands refuse a teammate or custom profile name the device already holds, but devices that edit concurrently can end up with equal names, so readers tell them apart by id. After sync applies these rows, a materialize hook creates the device-local access state of arrived teammates, bumps the audience and access counters an arrived profile revision affects, and revokes authorizations a narrowing revision no longer allows, deciding by the safety mode a teammate's pointer copied while the revision it names has not arrived, so a concurrent newer revision the pointer did not choose cannot revoke work and a revision that never arrives cannot hold revocation back; on desktop the revocation drain then stops their runs.

Conversations, channels, conversation memberships, AI channel memberships, and working folder grants replicate too. Memberships and grants carry a `sync_key` derived from their key columns, so devices that add the same membership or grant concurrently write one row; opening a vault converts older rows to derived ids and keys before sync starts. Local commands refuse a folder grant outside its conversation's project, while sync applies any such row, because refusing it would stop the apply. Authority is therefore checked where it is consumed: a grant counts only when the conversation, the grant's `project_id`, and the folder's project all match, a mismatched grant reads as revoked, an active authorization under one is revoked, and saving access that keeps the folder granted rewrites its project to the conversation's. Scratch promotion applies the same match, and refuses a channel whose project differs from its conversation's. Concurrent edits of one membership or grant keep one whole value: a removal or revocation first, then the access that explicitly clears more of history reading, participation, and full history or the lower folder capability, then the stricter runtime approval override. Inherited values rank as the widest they can resolve to: an inherited capability as granted, and no approval override as less strict than any explicit one. That holds for the channel override, which falls back to the teammate's default and can only narrow it, but a folder or scratch override replaces the channel override, so when a pass decides a folder grant whose kept explicit override is looser than the channel override a concurrent clear would inherit, the Chat hook settles the grant to that stricter override as an ordinary write that converges on every device. The priority cannot rank the access profile a channel membership names or an inherited scratch override, so the hook settles concurrent channel membership edits onto the narrowest of each part: the profile with the lowest folder capability ceiling, every capability any version clears or resolves to off, the latest history boundary any version reads from, and the strictest channel and scratch overrides any version applies. A concurrent narrowing therefore survives a concurrent widening of another part of the same membership. A profile whose effective revision has not arrived keeps the winner until it does. An edit made after seeing a removal replaces it, so a re-add converges to active. A concurrent archive of a channel or conversation outranks an unarchive. After sync applies membership or grant rows, the materialize hook bumps the conversation audience and the teammate's access counter, and revokes the teammate's active authorizations that the current rows no longer cover, resolving the approval override that governs each one in the runtime's precedence (scratch or folder override, then channel override), so a widening or a repeated apply revokes nothing. A deleted membership, grant, or conversation, including one removed by a cascade, no longer names its teammate, so the hook checks every teammate with an active authorization the same way. Deleting a conversation also cascades away the authorizations it was the destination of and their runs, so no revocation job can name them; the hook reports the deleted conversation, a local command whose delete cascades into conversations wakes the drain after committing, and on desktop the revocation drain stops every active run whose host-tool scope names an authorization that no longer exists, keeping the scope until the provider's shutdown succeeds so a failed shutdown is retried. Android never holds an active authorization, because runs execute only on desktop.

Standing push approvals (`chat_push_approvals`) replicate with the grants. Each names a teammate, working folder, push URL, and destination branch, keyed by a `sync_key` derived from them, and records the approval policy and teammate safety mode a later push must still match, the approving person, and `revoked_at`. Revoking keeps the row. Concurrent edits resolve a revocation first, so a concurrent re-approval stays revoked, while an approval made after seeing the revocation is active again. Local triggers refuse an approval whose approver is not a person, and revoke the matching approvals when the teammate is archived, its safety mode changes, or a grant, channel membership, or access profile that let it publish narrows; sync applies rows without them, and the revocation they write replicates like any edit. Deleting the teammate or folder deletes its approvals. The push rules are in [Chat security](../security/chat.md#push-requests). Push request claims (`chat_push_request_claims`) are device-local: one row per request that this device began pushing, with the claiming process token (null once released), the commit being pushed, and whether it reached the remote.

The channel timeline replicates as well: reply threads, conversation items, communication messages, their immutable revisions, message references with their target rows, and conversation and reply thread read cursors. Items order by `(order_key, id)` within the root timeline or one reply thread, so concurrent posts that take one order key read in the same order on every device. An item's scope and kind never change, while its order key and `created_at` (when it entered its scope) are one register group: the executing device that delivers a person's steer or queued reply, or turns it into a follow-up, moves it after the last item of its thread and sets that time, and the message keeps its posting time, so every device reads the same placement and a device that has the item before its input shows it where it was posted until the input arrives; page, unread, history, and channel reference range comparisons use that pair. A history granted from a point stores the order key after the channel's last root item, and a channel reference range stores its lower and upper positions. Reply counts are counted, and revision display numbers count the message's revisions in `(created_at, id)` order. Read cursors carry a derived `sync_key` and only move forward, so a concurrent earlier read never moves another device's cursor back. A revision's Markdown is bounded to 128 KiB and its rich content to 192 KiB so one revision fits an operation; projected provider output longer than the Markdown bound is cut at a character boundary and its rich content marks it truncated, which the timeline shows. Search rows follow local writes through insert triggers that stay quiet while sync applies, the Chat materialize hook rebuilds them for applied messages and revisions, and a deleted message leaves the index on every path. Mention targets keep unchecked ids, so a deleted folder leaves its targets to render their label snapshots.

Resource IDs and references are not grants. Every privileged service resolves current effective authority from the stored relationships and device-local target state.

## Drafts, attachments, and context

Drafts belong to an exact organizational scope and may reference managed attachments. Imported bytes live in the `chat/attachments` asset class of the active vault, named `{sha256}.{ext}`, so attachments with equal bytes share one file; source absolute paths are not persisted. A message revision holds at most 20 attachments as rows owned by the revision, each carrying the attachment by value (id, working folder, kind, display name, content type, size, and digest), so the attachment travels with the revision and its file moves as a managed asset; an empty text attachment names no asset. `chat_attachments` rows are device-local: the materialize hook creates one for each attachment an applied revision names whose working folder this device holds, and opening a vault renames older files to their digest names.

A draft save names the stored version it was based on, and Rust refuses it when another window has saved since. The composer then shows the stored version and says that it replaced recent local edits. A send stores its snapshot unconditionally because the send already acted on it. Each save tells the other windows of the vault, and a composer showing that draft reloads it while it has no unsaved edits.

Thread and channel mutations carry revision checks. After one succeeds, the window tells the other windows of the vault which threads and channels changed, and they reread those records and the open channel and reply thread. Receiving windows never announce the reread, so windows do not echo each other.

Message, scheduled message, draft, and queued reference rows control attachment retention. Chat never deletes attachment files: deferred cleanup removes a `chat_attachments` row only when no reference names its digest, and the sync asset sweep removes a file once no replicated reference and no device-local attachment row names it. Browser artifact cleanup still removes its files, rechecking current references first, treating an already missing file as a recoverable result, and recording bounded retry state.

Context packages, mentions, workspace file references, channel references, and selected Notes or tasks store identity and provenance. Resolving them repeats current authorization. Materialized provider context records enough scope and revision to support revocation and continuation disposal. Each agent run records when it is inserted why it started (fresh, continuation, handoff with its reason, or retry), the instruction and model selection digests it was launched under, whether it received the full context or a delta of only the sources its continued session had not received, and the bytes sent, and these values are fixed once the run leaves starting (a continuation whose provider opens a new native session records a handoff with the full context before that); `chat_agent_run_delivered_sources` lists each context source and content digest a run that started received. A package source is the trigger, a thread root or reply, a channel message, an attachment, a resource, or a channel note, and the package counts the channel notes it left out alongside the replies and channel messages; a removal delivery records that a session was told a note it received was deleted.

## Checkpoints, review, and restore

Git checkpoints, changed-file review, patches, and restoration retain exact run, thread, working-folder, authorization, and Git-storage identity. They do not identify a repository only by remote URL, branch name, or mutable path.

Checkpoint capture and restore use bounded native work around explicit database phases. A failed filesystem or Git operation leaves a recoverable status and cleanup record rather than falsely committing success.

Review artifacts are derived from authorized repository state. Persisted patch or preview data is bounded and scoped. Restoring an older checkpoint does not roll back organizational messages, membership, approvals, or unrelated vault data.

## Terminals, previews, and workspace observation

Terminal sessions belong to one channel and working folder; browser previews, internal file tools, and workspace observers retain exact thread and execution-target identity. Native process handles, ports, absolute paths, and watcher state are device-local runtime data. Saved terminal layouts (`chat_terminal_layouts`) are keyed by channel and working folder, follow both on deletion, and stay device-local, because the terminals they describe run only on this device.

Only one mutable provider driver generation owns an active thread at a time. Stopped or mismatched generations cannot append ordinary projection events. Workspace observation coalesces bounded semantic events and uses typed invalidation on overflow instead of persisting an unbounded path stream.

Preview and terminal metadata retained in SQLite is organizational evidence or resumable presentation state, not ambient process authority. Restart requires fresh target and authorization checks.

Each model preview tool call in a direct session has an app-owned audit row keyed by its turn, with the tool name, an argument hash, the outcome, and the result size; the rows also hold that turn's call and byte budget and are deleted with the turn. Organizational host tool calls keep their own audit rows keyed by the authorization revision.

## Coordination and command receipts

Scheduling, follow-ups, interaction responses, handoffs, and other coordination commands have stable request or receipt identity where retry can occur. Replaying the same accepted command cannot duplicate a message, assignment, or provider action, even when the duplicate arrives while the first is still being claimed. Completed and failed command receipts are pruned a week after they settle, which is far longer than any client retry. A queued follow-up keeps its thread for life: saving it again replaces only that thread's still queued follow-up, and a sent or cancelled one is never revived.

Work assignments, their inputs, semantic updates, and scheduled messages replicate. Each assignment and scheduled message records an immutable executing device: the teammate's home device when it can write Chat, else the desktop that posted the trigger, and for a scheduled message the device named on its row, which may differ from the device that wrote it. A scheduled post is attributed to that executing device's writer. An assignment's id derives from its trigger, teammate, and the assignment it follows, so concurrent Starts of one mention merge. Active work whose executing device can no longer write Chat, as after an unlink or a revoked writer, is taken over by a device that can: unstarted work moves to a successor assignment with its pending inputs, and started work fails with a reason that Retry resolves by rerouting it; Start reroutes a stranded assignment only while it is still active. Every reroute derives its successor id from the stranded assignment, so takeovers on two devices merge. A delegated assignment carries an immutable parent, depth below the root (at most 2, exactly one more than its parent when written locally; a device delegating from synced work first checks the stored chain), objective, expected result, and folder ceiling, and is deleted with its parent; a concurrent narrowing of the parent's authority cancels the child before it starts, because the starting device clamps it against the parent's current grants. A successor of delegated work keeps those fields. A delegated assignment that completes, asks for review, fails, or is cancelled reports the outcome in the parent's reply thread, queued as a continuation input while the parent accepts one; its ids derive from the child, so copies written on two devices merge. Cancelling a parent cancels its open descendants with the reason `parent_cancelled`, and the device that revokes a parent's authority, other than by settling or moving it, cancels them with `parent_authority_revoked`, since authorizations stay device-local; the replicated state stops each one on its executing device. A deleted assignment cascades away its runs and authorizations, and the hook reports it so the executing device stops the run. Only that device dispatches, writes active states, delivers inputs, answers approvals, and sends; when the mentioned teammate's home device is elsewhere or unknown, other devices store the mention, and a Start command on a desktop creates the assignment with that desktop executing it. Any device can settle an assignment or cancel a scheduled message, and concurrent states resolve cancelled, then failed, then completed, then ready for review, then the rest, with the review outcome, reviewer, and review time riding with the state and present only on completed work, and the reviewer bounded as a participant id (at most 128 bytes, no control characters); the executing device stops a run whose assignment settled remotely. The assignment and the participant reference target keep model override columns (a schema version and a selection) that replicate but are never written, because a post carries no model choice and work runs with the teammate's model. Table constraints hold both rules: the review outcome, review time, and reviewer are all null or all set on completed work, and an override's schema version and selection are both null or both set on the assignment and on the participant reference target. An input's id derives from its message, so rerouting it updates the row instead of replacing it. A delivered input records the message revision the run received, which for the trigger of an assignment is the revision its context package froze, and concurrent delivery states resolve delivered, then failed, then ignored, then pending, so a cancel that crosses a delivery loses to what the run already read. Only the local author edits a pending input, as a new revision of its message, and editing or cancelling an input that left pending is refused. A follow-up input, the trigger of its own assignment, is never edited or cancelled, because its frozen context already holds its text; stopping that assignment is how it is withdrawn. An input is a steer, delivered into a working run, or a queued continuation, which no running turn receives. Any member can hold a pending steer or continuation, which no delivery path takes until it resumes, steer one now, or reorder the waiting ones; the hold flag and the ordinal are separate merge groups, so a concurrent hold and reorder both survive, and a reorder reuses the ordinals the waiting inputs already held so the inputs around them keep their place. A follow-up of a reviewed assignment, or of completed work that holds queued replies when its turn ends, whether a post, Start, turn end, a queued reply that sync brings after the turn ended, or restart recovery creates it, carries those pending replies behind its trigger as steers of its first turn; only inputs whose message belongs to the reply thread trigger or follow, and others stay undelivered on the settled assignment. A scheduled message's request is bounded to 256 KiB and 256 references so it fits one operation, and sending it posts under ids derived from its command id and deletes it in the same transaction, so a retry or a second device cannot post it twice. A repeating scheduled message has one recurrence row, keyed by its message, holding its rule (an interval of 1 hour to 30 days, or a local minute on chosen weekdays in a named time zone, with a quiet period policy) and its progress (the next occurrence and the count posted), which the executing device advances and an edit of the rule or time moves, keeping the count; an edit concurrent with an advance resolves to one whole progress value, which can repeat or drop that one occurrence, accepted because the edit is an explicit reschedule; each occurrence posts under ids derived from its command id and occurrence key, and the same transaction advances the progress only while it still names that occurrence, so the message stays and no occurrence posts twice. A series with the defer policy holds an occurrence while its executing device is in a quiet window or a Focus phase and posts it when that ends, skipping it instead when the following occurrence comes first. An occurrence missed by more than 10 minutes, counted from the end of any quiet hold, is skipped without posting, and the skip count and hold stay device-local; a cancel on any device removes the series with its message over any concurrent progress, and quiet period preferences stay device-local. A confirmed schedule proposal becomes a scheduled message whose ids derive from the proposal item, so confirming it on two devices yields one message, and dismissing a proposal is recorded only in device-local state. An edit made on another device while the executing device sends is lost: the posted message carries the content the executing device had, and the concurrent edit lands on a deleted row whose content opens no recovery offer. This is accepted because it needs the editing device to reach the executing device only after the scheduled time, and offering the edit would make scheduled content a recovery root with its own discard flow and a manifest change. Dispatch claims, attempts, and send receipts stay device-local, as does the execution target a post chose for work that waits for Start here on its executing device, or for the follow-up of a pending reply to work ready for review, so the work runs there once accepted. A kept target that no longer resolves is dropped when the start fails, so the next start resolves the target again.

Canonical organization state commits before process notifications. If process delivery fails, the retry state identifies the intended command without inventing another organizational event.

## Cleanup and retention

Provider sessions, attachments, scratch generations, checkpoints, browser artifacts, and native processes have different retention and cleanup requirements. Cleanup records state the exact logical target, reason, attempt state, and safe retry information without exposing secrets or unnecessary absolute paths.

Deletion of a provider continuation does not cascade into the channel. Archiving a channel does not by itself delete provider-native state.

Chat foreign keys into Projects (projects and project working folders) cascade on delete, so deleting a project removes the same Chat rows on every replica instead of being refused by whichever row a device happens to hold. Removing an external working folder is still refused while Chat references it, through an explicit in-use query. Audit rows (authorization revisions and their sources, scratch generation sources, and scratch promotions) stay immutable while their parents exist and are removed only by that cascade. The command that deletes projects collects their browser artifact paths before the transaction and removes those files after it commits, keeping any path a remaining row still names; their attachment files are left to the asset sweep.

Revocation cleanup has priority over convenience retention. A continuation that materialized restricted context is stopped and discarded or quarantined before reuse, as specified in [Chat access control](../access-control.md).

## Device-local boundary

The active vault database may store provider-native continuation IDs, organizational identities, and portable execution history. It does not store secret values, provider homes, executable paths, probe process state, external absolute folder bindings, native terminal handles, or ephemeral loopback credentials. Agent run attempt columns and `chat_agent_run_delivered_sources` are device-local execution evidence: they describe what this device sent to its native sessions and never replicate. `chat_agent_run_usage` holds one row per run with the tokens, cost, and working time the executing device counted from provider usage reports; it never replicates, and the thread totals it keeps let a later run on the same provider thread count only the increase of a cumulative report. Working time counts only while the run is working, never while it waits for an answer or approval. Secret requests (`chat_secret_requests`) are device-local rows with a label, purpose, state, and expiry; they never hold the value and never replicate.

The platform app config directory stores device-local bindings and nonsecret runtime bootstrap data. Provider configuration, credential references, remembered composer selections, working folder provider preferences, and panel sizes live in the `chat` entry of the device preference file there, while Chat behavior (send key, reasoning summaries, folding, timeline density, terminal scrollback, idle timeout, thread restore) is portable `chat.behavior.*` vault preferences that replicate, as are the notification switches for waiting work, review-ready work, failures, and background announcements, because what deserves attention is personal policy. The multiline terminal paste confirmation and notification content inclusion share that path but are device preferences, because a safety prompt must not follow a peer and what a lock screen may show depends on the device. Secrets are resolved from the operating-system credential store only at the native boundary that needs them.

LAN sync replicates Chat identity and policy rows (participants, AI teammates, policy revisions, access profiles, and profile revisions) and conversation access rows (conversations, channels, memberships, AI channel memberships, and working folder grants), the channel timeline (reply threads, items, messages, revisions, references, and read cursors), and coordination (work assignments, their inputs and semantic updates, and scheduled messages with their owned references and recurrences); replicating the rest of the portable organization and authorization records is later work. Device-local bindings, process state, and credentials never replicate.
