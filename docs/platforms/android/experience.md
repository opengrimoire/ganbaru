# Android experience

## Adaptive shell

Phones use a labeled bottom bar within thumb reach for the open [workspace tabs](../../features/workspace-tabs.md), and a slim top bar. Its leading side holds the active destination's context switcher, or, where there is no context to switch (Calendar), the destination icon and name in the same pill without the open affordance; its trailing side holds the utilities: a Pomodoro ring, which carries the remaining time in its accessible label rather than as visible text, as on desktop, then linked devices, Quick notes, Music, and Settings. The keyboard slides over the bottom bar, which hides once it is covered so editing keeps the space. Larger windows use a navigation rail instead of the bottom bar. Both bars share the content surface color, so a screen reads as one page rather than stacked bands.

The shell uses touch-sized controls, visible selection, localized accessible names, system safe areas, and the current theme. It does not spend scarce phone width repeating the active destination label.

Loading indicators sit on the content surface color. Startup shows a single loading indicator until the database, Calendar, Pomodoro recovery, and the Pomodoro and linked-device controls are ready. Once Calendar paints, the remaining destinations are prepared in prioritized background batches rather than on first interaction, so opening them later rarely waits. Heavy detail workflows stay lazy only where desktop also defers them.

## Hierarchical navigation

Projects, Notes, and Chat share one context model. On phones, the top bar shows a single switcher with the current project, its icon, and an open affordance, because a full group, project, and note path cannot stay legible at phone width. Selecting it opens a full-height touch selector at the current level: the open note's siblings in Notes, the project's channels in Chat, or the group's projects otherwise. Because the switcher names only the project, the Chat action row names the open channel, such as #general, after the sidebar button and the Projects view switcher. Only one hierarchy level is visible at a time, and Back moves toward the group root before dismissing the selector. The row below the top bar holds only actions for the current view, such as the sidebar entry, Back from an open note, the open database or Chat channel, and page, view, or project settings actions, and it collapses when it has none. Creation lives in the sidebars and views rather than this row, except that the Projects view switcher, which names the open view and lists the project's views like the Calendar span button, ends its menu with an Add view row that expands the view types in place, because switching views is frequent and otherwise needs the sidebar. A project's Notes and Chat views open inside the Projects tab as the phone Notes and Chat workspaces scoped to that project, with the same switcher in their action row to return to another view. All action rows share the top bar icon columns, so their buttons line up under the top bar buttons from either edge. Projects, Notes, and Chat open their sidebar from a sidebar button in the action row as a floating panel shaped like the selector, with a title, close, search, and touch rows over the current view; the backdrop and Android Back close it. Holding a sidebar row still lifts it for the same drag reordering as desktop, while a swipe scrolls. Projects also rename, reorder, and remove views there. With no note open, Notes shows the same explorer rows in place as its landing level. Opening navigation or switching a channel does not summon the keyboard until the user selects Search or the composer.

## Feature surfaces

- **Calendar** starts in day view with direct touch navigation and editing. Gestures do not conflict with event drag or resize, and active-event protections match desktop. The event panel is a bottom sheet over the live grid rather than a full screen: it slides up from just above the system navigation to a peek that shows the title and time, and dragging the sheet moves it between that peek and full or closes it. Changing a field never moves the sheet. Close, delete, and save stay in its header at every height. The event shows round knobs on its edges from the moment it is drawn; while it is edited they resize it and its body moves it at a touch, while other events still need a long press to move. While the user moves or resizes the event on the grid, the sheet collapses to an up chevron over the event title so the time range stays visible, and it opens fully when a section needs room. A new draft is never discarded by the grid: swiping its sheet down or scrolling the grid collapses the sheet to that strip, which a tap opens again; tapping the grid moves the draft to the tapped half hour, keeping its length, and a long press redraws it.
- **Projects** starts in List and reuses the canonical List, Dashboard, Kanban, Calendar, and Gantt views. Wide views pan natively in both axes. Selection and task-detail controls stay visible on coarse pointers instead of depending on hover. Filters, sorting, columns, grouping, and settings open in touch-sized sheets.
- **Notes** reuses the page, block, database, history, and navigation contracts. Working-folder Markdown controls are absent, and managed images and files use bounded document-input flows.
- **Chat** reuses the responsive canonical workspace. Channel navigation replaces the conversation while open instead of covering it with a desktop overlay. Provider setup, terminal, files, Git, local review workspace, and execution diagnostics are absent. Message actions (reactions, copy, and more) appear when the user holds a message still, since touch has no hover, and a tap elsewhere, a scroll, or Back hides them. Holding a message therefore does not start a native text selection; Copy copies the whole message.
- **Pomodoro, Quick notes, and the compact Music player** float above the active destination within the visible safe viewport. The Music library builder expands to a full-screen workspace.
- **Settings** keeps the desktop category structure where a shared preference or Android equivalent exists and omits unsupported controls, including keyboard shortcuts. Anti-distraction settings include shared usage limits, Android selected-app rules and access status, and read-only browser and desktop configuration from the portable vault.
- **Date and time pickers** that open from a field show as centered dialogs instead of anchored popovers, and every calendar uses touch-size days and turns pages with a swipe in any direction. Times are picked on a clock dial: a press or drag picks the hour, the dial then turns to minutes, where a tap lands on the nearest five minutes and a drag or hold reaches any minute, and a keyboard button swaps the dial for typed hour and minute fields. Nothing changes until OK.

## Linking with a desktop or server

The linking protocol, snapshot copies, and data protections are owned by [device linking and synchronization](../../data/sync.md). Android adds these interaction rules:

- First use starts with localized welcome screens (a language screen, then one per feature, each with a short looping scene of the real UI, starting with Calendar and Focus, then blocking distractions during Focus, daily limits across devices, Music playlists that projects play for work and breaks, adding and editing project tasks in the List view, the event defaults a project sets, which a new Calendar event takes once the project is picked, a Notes page whose database gains a row in its table and then shows as a board, Quick notes filtered down to a tag, where a note written in the editor takes that tag, and a Chat prompt that Claude answers at a raised effort after reading the project, then an about screen whose scene stars the public source repository, with the full AGPL 3.0 text, acknowledgments, and the source link, and finally the vault choice, whose primary action starts from zero in private storage, with restoring a backup or importing a folder as text actions under the private storage path), with the navigation fixed at the bottom and Back on every screen after the first, then creates or restores the private vault, completes the Android access review, and shows the linking screen. The access review and the linking screen keep the same bottom navigation, with Back between access screens and from the linking screen to the last access screen until a device links; a screen whose access is already on says so and only continues. A missing or invalid configured vault leads to vault recovery instead.
- The linking screen offers the same sources as the desktop one except a phone, since two phones cannot link directly: **your computer** or **a server**, each as numbered steps. In onboarding each source opens its rear-camera scanner, which requests camera access in context; the user can switch to pasting the code instead, and Data settings starts with the code field. A camera that cannot start falls back to the code field.
- The computer source decodes the desktop's QR invitation or its pairing code, which carries the private-LAN endpoint and pinned coordinator identity. The user never types an address or configures a server. After a scan, the phone shows a confirmation code and waits until the desktop user approves the matching code there.
- The server source joins the vault an anchor server runs from the QR code `ganbaru-server anchor setup` shows, or its pasted text code, optionally with the recovery kit ([Server](../server/README.md#adding-a-device-through-the-server)). The copy replaces the phone's vault, backed up first unless it is the untouched first-run vault. A server that runs no vault yet is refused, because a phone cannot found a vault on a server; a desktop adds that server first.
- An untouched first-run vault is replaced directly by the initial desktop snapshot. **Continue without linking** finishes onboarding with an independent vault and permanently disables that shortcut. Closing the linking screen without choosing either leaves onboarding unfinished.
- A linked-device control placed after Pomodoro lists linked devices and opens fresh copy, unlink, and recovery actions. With no relationship it opens the same linking screen. Data settings is the fallback management surface.
- Before the phone holds a copy of the linked vault, the linking flow offers `Copy vault to this device`, which copies the vault from the coordinator after confirmation. Once copied, the phone writes like every other linked device.
- Emergency local-copy recovery appears only in Data settings, for a linked device whose coordinator is gone, and keeps the local copy as a standalone writable vault.

Scheduled Calendar alarms and the last accepted distraction rules keep working while the phone is offline or backgrounded. Desktop Calendar changes reach Android notification scheduling after the next successful sync exchange.

## Insets, keyboard, and input

A native bridge publishes system-bar and display-cutout insets, with CSS safe-area values as a fallback. Layout reacts to orientation, navigation mode, cutouts, and window changes without hardcoded device dimensions. Controls stay inside the visible viewport.

The app draws edge to edge and the WebView keeps its full size under the soft keyboard. The native shell reports the keyboard height on every frame of its slide (Android 11 and later; earlier versions report it once the keyboard settles), and only the surface holding the focused field follows it: the page when the field is on the page, so bottom-anchored controls such as the Chat composer ride directly above the keyboard, or the innermost modal dialog holding the field while the page and dialogs behind it keep their size. A dialog that fills the screen, such as a sheet, ends above the keyboard; a centered dialog or anchored popover keeps its size and position, and moves up only as far as needed when the keyboard would cover it. When the system reports a keyboard change without animating it, the shell plays a short slide so surfaces never jump. The page stays still while the keyboard slides over the bottom tab bar and follows it only once the bar is covered, so content never drops below the bar as the keyboard opens or closes. The focused field and its caret stay visible while the keyboard opens, resizes, or rotates. Dismissing the keyboard does not leave the current feature.

The keyboard opens only when the user asks to type: by selecting a field, or through an action whose purpose is typing, such as creating a page, event, or item, renaming, or Search. Switching destinations, opening a page, note, channel, or task, restoring a previous caret, and loading data never focus a text field on a phone.

Selected text shows the app's own selection handles, the same on every phone rather than each device maker's, and the caret shows no insertion handle under it.

## Android Back

A serialized frontend Back controller intercepts only when the UI has consumable state: dialogs, menus, pickers, full-screen builders, navigation levels, editor layers, task details, Notes contextual pages, and utility sheets. The topmost layer closes first. With no layer open, Back returns to the first workspace tab, and on that tab the listener yields, so Back follows native Android behavior. Two layers cannot consume the same press, and a stale closed layer cannot trap the app.

Predictive Back still needs validation on newer devices; the state model must stay compatible without inventing a separate navigation history.

## Accessibility

Touch controls expose localized names, selected and expanded state, and sufficient target size. Keyboard and switch-access users can reach navigation, overlays, hierarchy selectors, editing, Save, Cancel, and recovery actions. Motion is restrained and respects user preferences. Status is never communicated by color or animation alone.
