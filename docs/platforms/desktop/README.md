# Desktop platforms

Linux and Windows host the complete local application, including native coding-agent execution, authorized working folders, terminals, Git, desktop media, browser native messaging, and platform-specific anti-distraction adapters. The browser native messaging host never opens the vault: it writes block events and usage to a spool in the app config directory, and the app moves them into the vault. On Linux, coding-agent providers run in a user systemd resource scope when one is available and start directly otherwise ([execution and workspace](../../features/chat/execution-and-workspace.md#runs-and-provider-threads)).

Shared feature behavior lives under [features](../../features/README.md). Cross-platform frontend and native composition are documented under [architecture](../../architecture/README.md). Desktop-specific documents:

## First use and device linking

The linking protocol, snapshot copies, firewall authorization, and data protections are owned by [device linking and synchronization](../../data/sync.md). Desktop adds these interaction rules:

- With no active vault, setup starts with a localized language screen and then the vault choice, whose still illustration shows the default folder and what it holds. On the vault choice the primary action continues with the default folder, while choosing another folder or importing an existing one are text actions under the default path and any error about the folder. A missing or invalid configured vault also leads to vault selection, with neutral inline recovery guidance. Once the setup screens open a vault, the linking screen follows, so a device that joins an existing vault does so before anything else in onboarding writes to it, and then the welcome tour (one screen per feature, each with a short looping scene of the real UI, starting with Calendar and Focus, then blocking distractions during Focus, daily limits across devices, Music playlists that projects play for work and breaks, adding and editing project tasks in the List view, the event defaults a project sets, which a new Calendar event takes once the project is picked, a Notes page whose database gains a row in its table and then shows as a board, Quick notes filtered down to a tag, where a note written in the editor takes that tag, and a Chat question that mentions the Opus agent, which answers in the message's thread after reading a chapter, then a card for each coding agent this computer can run, checked when the screen opens, with the same state, CLI version, account, and plan limits Settings shows, a refresh action, and a setup dialog with the install and sign-in steps or the full setup form, then an about screen whose scene stars the public source repository, with the full AGPL 3.0 text, acknowledgments, and the source link). Quitting during the tour starts it again from its first screen at the next launch. A vault the setup screens create always gets the tour, while an existing one picked to recover from a startup error, such as a vault that was moved, and a vault opened any other way skip it. A linked copy that replaces the vault keeps the pending tour. Every screen keeps the navigation fixed at the bottom with the same progress dots, and Back on every screen but the language screen; on the linking screen and the first tour screen Back shows disabled, because the vault is already open and the screens before cannot be chosen again.
- The first desktop is the administration device and runs the embedded private-LAN coordinator. Its linking screen shows a short-lived phone pairing QR invitation. Its primary action, **Continue without linking**, moves on without linking, and becomes **Continue** once a device links; closing the screen without choosing leaves onboarding unfinished.
- Data settings creates further invitations. Phones scan the QR in Ganbaru. Another desktop pastes the complete pairing code copied from the coordinator into its own Data settings, then becomes a client and stops its own coordinator. While a device enrolls, the coordinator shows its name and confirmation code in place of the QR, and Data settings opens that approval on its own. A desktop with no vault yet can instead join the vault an anchor server runs, from the same connect dialog, with a setup code the server printed ([Server](../server/README.md#adding-a-device-through-the-server)).
- A linked-device control placed after Pomodoro lists devices and opens linking actions without adding a permanent warning row. Queued work uses a stable status indicator; only an explicitly running foreground action animates.
- On Linux, the linking screen detects active UFW and firewalld configurations and offers one scoped permission action for the coordinator and LAN discovery on IPv4 and IPv6 after explaining why it is needed. The packaged app applies every rule through its root-owned helper in one authorization; a development build uses the helper Cargo builds next to it the same way. Addresses on bridges without a default route, such as Docker and libvirt bridges, are neither reported to other devices nor opened. Unsupported firewall managers show a truthful manual-action state. A linked member desktop gets the same scoped action for its member listener, offered as the Local network access switch, with the same TCP and UDP scopes on the same port; until the person confirms a rule saved for another network, the member listener refuses LAN peers that reach it there, exactly as the coordinator does.
- On Windows, the app adds no firewall rule. The first time the coordinator listens on the local network, Windows Defender Firewall asks whether to allow the app; allowing it creates the operating system's usual rule for the whole program on the chosen network types, not a rule scoped to the linking port or subnet. The coordinator listens on the IPv4 and IPv6 wildcard addresses and starts only when linking needs it, and every connection still passes the listener's address policy, budgets, and mutual TLS. The program rule is expected to cover both listener sockets and the DNS-SD responder on UDP 5353; physical acceptance confirms it, and without discovery linked devices still follow address changes through the endpoints the coordinator reports. Users who want a narrower rule can edit it in Windows Defender Firewall.

## File drops

Desktop windows keep Tauri's native drag-and-drop handler, which takes file drops before the webview sees them: WebKitGTK reports a dropped file only as its address, so an HTML5 drop would insert that address as text or navigate the page to it. Because desktop windows host their pages as child webviews, drops arrive as webview events. Rust records the paths of the latest drop on each webview, and a feature that accepts drops listens for the drop event while its target is open and asks a command to import that drop. The command reads only paths the operating system delivered, claims a drop once, and refuses drops older than a minute, so the webview never names files to read. Quick note images accept drops this way; other HTML5 file drop targets, such as the Chat composer, do not receive desktop drops yet.
