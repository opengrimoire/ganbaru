# AI provider runtimes

Status: Implemented on desktop for Codex, Claude, Cursor, Grok, and OpenCode. Adapters live in `crates/ganbaru-chat-providers/`.

Each adapter normalizes provider-native events into stable Ganbaru contracts while keeping enough native detail for inspection and recovery.

## Shared contract

Each adapter supports exactly the capabilities its metadata advertises; anything else stays absent or disabled. Provider direct actions are not offered in teammate threads, where commands only insert text into the message. Ganbaru never simulates approval, continuation, cancellation, interactive input, model selection, or reasoning controls that the provider cannot truthfully perform. Organizational runs treat a provider that silently starts a fresh session in place of the one they continue as a lost session and resend the full context package.

All transports apply bounded parsing, payload limits, timeouts, cancellation, process-tree cleanup, redaction, and stable error categories. Short probes (version, account, and catalog queries) read each output stream only up to a fixed limit and stop the whole process tree once a stream exceeds it or the probe times out. Provider output is untrusted input: unknown events may be kept for diagnostics but never become typed application state without validation.

Usage reports carry provider facts only. Context fill is the size of the newest root model request measured against the main model's context window, turn and thread counts are the totals the provider reports, and cache writes appear only when the provider sends them. Every provider's counts follow one convention: input excludes cache reads and writes, and output includes reasoning. Each report names what its counts cover: one model request (OpenCode), the running turn (Claude, which reports before the turn ends so failed and interrupted turns still count), or the thread's lifetime total (Codex). A report with no documented scope, such as an ACP context update, is shown but never counted toward usage. Rate limit status carries the windows and reset times the provider reports; a provider that reports none shows none.

Users may set any launch arguments, environment variables, and provider settings their CLI accepts. Values on a per-family allowlist (formatting and locale variables, telemetry, timeout, and context window switches, inherited API key variables, and a few cosmetic flags) apply immediately. Anything else, including values typed in settings, applies after one native confirmation on this device, and arguments that duplicate options Ganbaru manages (protocol mode, output format, session selection and continuation, permission and approval transport) are always rejected. Claude teammate runs accept no launch arguments at all, so a provider instance with launch arguments cannot run teammates. Executables and provider homes chosen with the native picker, or the family default command, apply without asking. Default commands and Settings discovery search only absolute `PATH` entries, the usual user install folders, and Homebrew on the platform that has it, and skip any program that every local account can write or that sits in a folder every account can write, so a planted copy never becomes a provider silently. See [Chat security](../../data/security/chat.md#provider-configuration-and-secrets).

## Discovery and model catalogs

Native discovery owns provider readiness, model identities, and capability options, including cached catalogs. The frontend validates the catalog and never infers capabilities from model IDs or labels; distinct routing aliases stay selectable even when they share a display name.

Discovery is lazy. App startup and vault preparation load cached Chat history and settings without launching provider processes; opening Chat or Chat settings starts automatic discovery once per vault, and explicit refresh is always available. Probes, catalog queries, and thread lifecycle calls outside a session run in a fresh empty directory that only the user can access, so project configuration in the folder the app was launched from never loads. A failed probe leaves local history usable, and late results never overwrite settings from another vault or a newer load. A status check never authenticates or creates a session; model refresh does.

Rationale: provider probes spawn external processes, so they must not slow startup or block reading local history.

Each device keeps the newest plan limits it observed per provider instance and when it last used that instance. Ganbaru never polls for limits: a status probe of a signed-in Codex account, or of a Claude account with a plan, reads them once over the connection the probe already opened, without starting a turn, and Claude turns refresh them from their rate limit events. The first time Chat opens in an app session, enabled providers that have gone an hour without a successful probe or limit report get one status probe each in the background, so limits and sign-in state are current without visiting Settings. The Claude read uses the CLI's experimental usage request, so a CLI that lacks it or changes its reply only leaves the last observation in place. The agent profile card lists the 5-hour and weekly windows with the share left and the reset time, and the Settings provider header shows one ring per window, each with its own details on hover; both say when the reading is older than an hour. Model pickers order providers that are ready first, then providers limited until a future reset, then providers that need setup or sign-in, breaking ties by most recent use; the Settings provider list keeps a stable order.

Rationale: extra provider requests could look automated to the provider and cost memory and battery, so limits are read only where a probe or turn already talks to the provider.

## Codex

Codex uses its native app-server protocol. Ganbaru owns the process, thread association, event ingestion, interaction requests, cancellation, and workspace authority. The app-server thread identity is an execution detail and never replaces the Chat conversation or agent identity. Provider-supported model, reasoning, approval, and sandbox choices are recorded with the run. Teammate instructions join the thread when it opens or resumes. A checkpoint restore rewinds the native thread to the restored turn, so the provider context matches the restored conversation; a turn Codex no longer has fails the restore before any workspace change. Codex rate limit updates are sparse, so Ganbaru merges them per metered limit and reports every known window together.

## Claude

Claude uses its native bidirectional stream-JSON protocol. Ganbaru speaks that control protocol directly instead of through the TypeScript Agent SDK, because the SDK wraps the same CLI protocol and would add a Node runtime and its dependency tree; replay transcripts and compatibility ranges catch protocol drift. Ganbaru owns the process and translates streamed messages, tool activity, permission requests, questions, and completion into canonical events. Session identity stays provider-local, and resuming a session must keep its authorized project and execution target; it can never silently resume in a different folder. Subagent frames stay out of the root stream and never move the resume cursor. Teammate runs load only an allowlist of built-in file, planning, and question tools beside the internal server, and stop when the CLI reports any other built-in tool; see [Chat security](../../data/security/chat.md#project-provider-configuration). Teammate runs load no Claude settings files, but they keep the user's choice to turn off the 1M context window (`CLAUDE_CODE_DISABLE_1M_CONTEXT` in the host environment or in the `env` of the user settings file), so they use the same window as the model picker shows; that value can only shrink the window. Teammate instructions join the system prompt when a session opens or resumes, inline or through an owner-only file when they exceed 16 KiB. On CLI versions that record the system prompt of a conversation (2.1.267 and later), Ganbaru turns that record off for launches with instructions, so a resumed session follows the current instructions and not the ones it first opened with. A turn whose instructions differ from the running session's fails with a retryable conflict instead of changing them silently. Effort and Fast mode change in the running session without a restart. Host proxy and CA certificate variables reach the CLI. Claude reports each rate limit type separately, so Ganbaru merges them per type and a request stays limited until every rejected type resets. Rate limits and root API retries become typed notices; the timeline does not render them yet.

## ACP agents

Cursor, Grok, and any other agent that speaks the official Agent Client Protocol (ACP v1) run on one bounded ACP runtime. Cursor and Grok keep provider-specific executable discovery, credentials, model handling, interactions, continuation, and diagnostics; a generic ACP agent instance names its own executable. Capabilities such as native resume and image input come from the initialize negotiation. Host tools reach a generic agent only when it advertises HTTP MCP server support; otherwise its sessions run without them. A status probe sends only initialize. Teammate instructions travel with the first prompt of each native session, and again only when they change; a session loaded to continue a reply thread under an unchanged continuation key already holds them, so its turns omit them. Loading a native session for resume suppresses the history the agent replays, because the provider already restores its own context and the Ganbaru timeline is the history the user sees; permission requests that arrive during the load are cancelled.

## OpenCode

OpenCode runs as a local server reached through its HTTP and event-stream interfaces. Ganbaru reconciles streamed and fetched history, deduplicates events, keeps events whose own or nested session ID names another session (such as a subagent) out of the thread, reconnects within bounds, and keeps cancellation and session ownership explicit. When the user allows a request for the session, Ganbaru keeps that grant for the session and answers each later matching request once itself; it never writes the grant into OpenCode configuration. An event stream that stays silent for 180 seconds while a turn is busy reconnects and reconciles history; idle time does not count.

## Compatibility

Recorded bidirectional replay transcripts and focused tests define the supported protocol surface. Each provider has a minimum version, a newest tested version, and optionally a ceiling where a protocol line Ganbaru has no runtime for begins. A version below the minimum or at the ceiling is refused with a recoverable error, and a newer untested version below the ceiling runs with a notice. Codex accepts 0.156.0 and later, is tested through 0.167.1, and stops at 1.0.0. OpenCode takes its range from its compatibility range table (`OPENCODE_COMPATIBILITY` in `crates/ganbaru-chat-providers/src/opencode/cli.rs`), and releases at its ceiling, prereleases included, are refused until a runtime for that protocol exists. When a provider changes its protocol incompatibly, the adapter and its fixtures are updated without weakening the shared authorization boundary.

Dependency choices and rejected alternatives are recorded in [Chat dependency decisions](../../architecture/decisions/chat-dependencies.md).
