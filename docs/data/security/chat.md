# Chat security

The local coding-agent Chat starts native provider processes and operates on user-selected repositories. Provider CLIs, protocol events, model output, repository instructions, terminal output, URLs, Git metadata, and errors are untrusted. Rust is the policy boundary.

Organizational authorization is specified in [Chat access control](../access-control.md). This document covers how native boundaries enforce it.

## Provider lifecycle

Rust owns provider discovery, startup, transport, cancellation, event ingestion, and shutdown. The frontend selects a configured provider and sends typed commands. It cannot spawn an arbitrary executable, choose an arbitrary provider home, or connect directly to a provider's local server.

Owned local OpenCode servers are always authenticated. Every start generates a fresh 32-byte password from the operating-system CSPRNG, passes it only through the child environment, keeps it in memory for basic authentication, and never persists it. Startup fails closed unless a request without credentials to a protected route returns 401, because loopback ports are reachable by every local user. Only an owned, authenticated server receives the internal MCP endpoint and its bearer token; external OpenCode servers never do.

One driver generation owns an active thread. Events from a stopped, settled, or mismatched generation cannot enter the projection stream. Shutdown rejects new commands, flushes bounded pending events, and enforces deadlines even when a provider hangs. Reads, interrupts, approvals, and status checks use an existing runtime owner and never create one; owners are created only by sends, restores, and forced stops of existing threads, and a stopped owner that nothing references is evicted after the idle timeout.

Provider-native approval, trust, sandbox, or workspace state is defense in depth. It never widens folder, channel, runtime, or internal-tool authority granted by Ganbaru.

An approval answers the tool call the provider asked about. Claude approvals forward the provider's own tool input, and a replacement input from the webview that differs from it is rejected, because no approval flow edits tool input. Question answers are assembled in Rust from the offered option IDs. A future edit flow must validate the edited input against that tool's schema in Rust. Codex and OpenCode approvals list the write root or permission patterns that "Allow for session" approves, and withhold that option when the grant cannot be shown in full.

In-app confirmations for permanently deleting a thread (typed title), closing a running terminal, recreating a deleted file, cleaning up scratch folders, and starting a preview recording guard against mistakes in the UI. They are not a control against a compromised app webview, which the command ACL limits to the app-owned windows; each of these effects is reachable through other commands that window may call. Security-relevant consent that must hold against a compromised webview is minted in Rust, such as terminal start grants, provider launch confirmations, and preview origin grants.

## Provider configuration and secrets

Provider configuration (nonsecret values and opaque credential references), executable paths, provider homes, discovery caches, and process state are device-local: provider configuration lives in the `chat` entry of the device preference file and never replicates or travels with backups and handoffs.

Folders Ganbaru creates for provider homes, the Codex shadow home, and provider files are private to the current user (mode 0700 on Unix), and an existing Codex shadow home owned by another account is refused.

Portable runtime values that can run code, widen permissions, or redirect traffic (launch arguments, environment entries, and non-cosmetic provider settings) apply only after the user confirms them in a native dialog on this device. Rust classifies each value, stores the approved per-value SHA-256 digests in device-local state, and gates every provider launch, probe, model refresh, and provider-file access on them. A stored value whose digest this device has not confirmed is paused and listed in Settings until confirmed. Per-family allowlisted values and the family defaults apply silently. Typed executable and provider home paths are confirmed at save or test, and the confirmation warns under a typed program that another account owns or a group other than the user's own can write, while native picker selections are vouched for by short-lived in-memory receipts that are never persisted. Arguments that would duplicate managed transport options are always rejected.

Plaintext environment values stay valid, but a value whose name looks secret-like (a whole `KEY`, `TOKEN`, `SECRET`, `PASSWORD`, `AUTH`, or similar segment) shows a warning with a one-click move to the credential store, and runtime confirmations hide such values. Name matching cannot tell credentials from settings like `MAX_THINKING_TOKENS`, so it never rejects.

Rust derives each provider credential reference from the instance ID and environment variable name; the webview never names one. Before reading the store, materialization rejects any reference that is not the derived one for that instance and variable, so an edited or imported configuration cannot read another instance's secret. Source-control tokens use a separate credential-store service from provider secrets.

Secrets are resolved from the operating-system credential store immediately before the operation that needs them. Temporary provider environments are not persisted in diagnostics or DTOs. Replacing or removing a credential invalidates affected probe and model caches, and cleanup errors do not expose secret values or credential-store details.

The provider-file settings portal is a narrow exception for user configuration and instruction files. Rust resolves fixed file names from the family default home, the app process environment, or provider homes and environment values confirmed on this device; the portal refuses to open until the instance's runtime values are confirmed. A custom OpenCode configuration named by `OPENCODE_CONFIG` must be a JSON or JSONC file in an existing folder, and only the provider home may be created on save. The webview receives home-relative display paths. Reads and writes reject symlinks, invalid UTF-8, null bytes, traversal, oversized data, stale revisions, and unsupported files; saves use restrictive permissions and sibling temporary replacement. These files may contain secrets and are never copied into the vault, SQLite, diagnostics, or logs.

## Project provider configuration

Project provider configuration in a working folder can run commands as soon as a provider starts, so it follows the folder trust record described in [Git and hosted CLIs](#git-and-hosted-clis). Trusted folders load it exactly as the CLI does in the user's terminal; only folders without trust are restricted. Each provider family has one rule:

- Claude: the provider digest covers `.claude/settings.json`, `.claude/settings.local.json`, `.mcp.json`, and the `.claude/skills`, `.claude/agents`, and `.claude/commands` trees. A start in a folder whose current configuration no decision covers asks once and retries; an unattended assignment turn starts restricted instead. Restricted launches pass `--setting-sources user`, which with the pinned Claude version drops project settings, hooks (including skill hooks), project MCP servers, skills, commands, agents, and project `CLAUDE.md` while keeping the user's own settings, hooks, and MCP servers. A `--setting-sources` launch argument the user confirmed on this device overrides this. Direct runs do not use `--strict-mcp-config` or `disableAllHooks` because they also drop the user's own servers and hooks. Organizational runs (teammate assignments) load no settings at all: they pass `--restricted`, which ignores user, project, and local settings, refuses `bypassPermissions`, refuses file access outside the working folder even when approved, and disables auto memory, cross-session messaging, and cloud sessions; `--setting-sources ""`; `--strict-mcp-config` with only the internal server; `--tools` with the built-in allowlist of the target scope (Read, Glob, Grep, ExitPlanMode, AskUserQuestion, and TodoWrite for a conversation or read grant; Edit, Write, and NotebookEdit added for an edit grant; Bash added for execute, publish, and scratch targets); `--disallowed-tools` naming Task, Agent, WebFetch, WebSearch, and every built-in tool the scope leaves out, as defense in depth; `--settings` with `permissions.blockReadsOutsideWorkingDirectories` and `permissions.blockWritesOutsideWorkingDirectories`, plus `permissions.ask` for Bash and `useAutoModeDuringPlan: false` when the scope loads the shell; and the `default` or `plan` permission mode, so edits ask the person, and they refuse every configured launch argument, because any CLI flag could select another session or widen tools, settings, agents, plugins, the system prompt, or folders. Before the session is ready and again at the start of every turn, the driver checks that the internal server is connected, no other MCP server is loaded, and every listed built-in tool is on the allowlist, and stops the process otherwise. Bash is never pre-approved or offered for the session, so every command reaches Ganbaru as a permission request. Where the Linux command sandbox is available, every command of a scope that loads the shell runs under it through `CLAUDE_CODE_SHELL_PREFIX` (see [Confined shell commands](#confined-shell-commands)), and Ganbaru answers a command itself only in a full access Build turn whose folder Git metadata is unchanged, asking the person otherwise; without the sandbox, such a scope requires Ask for approval and the person approves every command. Ganbaru also denies, without asking the person, a permission request for a tool outside the scope or for a file path or Glob pattern outside the working folder, and organizational approvals offer no session grants. An unconfined approved command reaches whatever the person allowed, and a publish target reaches its remote through the push request host tool (see [Internal MCP host tools](#internal-mcp-host-tools)). Because no settings load, user settings, `apiKeyHelper`, and settings `env` do not apply to organizational runs; credentials come from the Claude configuration directory or the provider instance environment, and host proxy and CA certificate variables are inherited. Teammate launches need Claude Code 2.1.314 or newer, which includes `--restricted` (2.1.248), its messaging fix (2.1.290), the fix for tools registered late (2.1.295), and `blockWritesOutsideWorkingDirectories` with a `--setting-sources` value that ignores left-out files (2.1.314); an older CLI is refused for teammates with an update hint while direct threads keep the family minimum, so one instance can be healthy for direct runs and refused for teammates. Confined commands need Claude Code 2.1.325 or newer, the version the shell prefix was verified with; below it, commands stay unconfined under Ask for approval and other safety modes are refused for a scope that loads the shell. The allowlisted Read tool stays inside the working folder, and the pinned Claude version also refuses the process environment under `/proc`.
- Codex: the provider digest covers the `.codex` tree. Codex loads project `.codex/config.toml`, hooks, and rules only for folders its own configuration trusts by path, and worktrees of a trusted repository inherit that trust, so a path the user once trusted in Codex would load whatever a handoff or provider later writes there. Restricted launches in a folder with a `.codex` entry pass `-c projects={"<launch directory>"={trust_level="untrusted"}}`, which takes precedence over a trusted path or parent repository for that launch only and never changes the user's Codex configuration. Folders without `.codex` keep Codex's own trust and defaults. MCP status reads without a live session start restricted rather than asking. Organizational runs launch with a Ganbaru permission profile whose workspace root is read-only for conversation and read targets and writable otherwise, with network off, and with the shell tools off except for execute, publish, and scratch targets, whose commands run in the Codex sandbox; Ganbaru reads the effective configuration, profile, and thread back and refuses to dispatch when anything differs, including rules a trusted project configuration merged into the profile. Accepting a Codex approval retries the operation outside its sandbox, even when it names no wider root, so Ganbaru declines every native approval of an organizational run, from subagent threads too, and approve-for-me runs use the `never` policy because the automatic reviewer approves writes outside the folder. Commands therefore count as confined rather than person approved. On Linux, Ganbaru checks once per app run that the Codex sandbox can start (`codex sandbox` with the organizational command profile, without a model thread); where it cannot, for example when AppArmor restricts unprivileged user namespaces, Codex reports conversation support only and refuses folder and scratch sessions instead of running unconfined.
- Cursor and Grok: the provider digest covers `.cursorrules` and the `.cursor` and `.grok` trees. Both also load Claude hooks from `.claude/settings.json` through their documented compatibility, Cursor loads skills from `.claude/skills` and `.codex/skills`, and Grok loads `.mcp.json` and `.cursor/hooks.json`, so those covered paths count for them too. Unconfined, Cursor holds no folder boundary, because it writes files itself without asking the client and a project `.cursor/cli.json` allowlist runs the shell unasked, in every mode and with `--sandbox`; it holds read and edit authority only under the Linux command sandbox and never runs teammate commands (see [Cursor teammates](#cursor-teammates)). Unconfined, Grok holds none either, because its subagents and workflows write files directly, `agent stdio` ignores its tool deny and subagent switches, and a trusted Grok folder starts project hooks and MCP servers; it holds folder authority only under the Linux command sandbox, which stops all of these in the kernel (see [Grok teammates](#grok-teammates)).
- OpenCode: the provider digest covers `opencode.json`, `opencode.jsonc`, and the `.opencode` tree, and OpenCode also loads `.claude/skills`. No restriction is verified for direct runs, so OpenCode has no restricted launch; local server starts in a restricted folder still set `OPENCODE_DISABLE_PROJECT_CONFIG=1` as defense in depth, which the gate below does not rely on. Organizational runs need an owned local server reporting OpenCode 1.19.5 or newer, which with that variable ignores project permission rules, MCP servers, plugins, and tools, and they also turn off formatters and language servers. Their session permission rules start by denying everything, and OpenCode applies session rules after user configuration: reads stay allowed, an edit grant asks for each edit and denies `.git`, outside directories, web, subagent, skill, and language-server tools stay denied, and only execute, publish, and scratch targets load the shell. Where the Linux command sandbox is available, an owned local server runs every command through it by naming the helper as OpenCode's `shell` setting (see [Confined shell commands](#confined-shell-commands)), and commands ask in Ask for approval and Approve for me and run unasked in full access; without the sandbox they ask and require Ask for approval. Internal host tools ask unless pre-approved, other MCP tools are denied, provider commands are sent as plain text because their templates can run commands, and Ganbaru rejects out-of-scope requests without asking and offers no session grants. Unconfined, network access therefore goes only through commands the person approves, and the user's own global OpenCode plugins still load.

Each driver declares whether it enforces a restricted launch. A provider that does not must never start where restriction is needed and the launch folder has any covered entry: the start is refused with `trust_decision_required`, naming the files found, instead of loading content the user never accepted. A user start asks first, as above, and a folder the user trusted or that holds no covered entry is unaffected. Declining leaves the folder refused for these providers, and the next start asks again. An unattended assignment fails with that reason, and the user can trust the folder in Project settings and retry it. New drivers default to refusing. Scratch folders are device-local and created by Ganbaru, so this gate does not apply to them. Each driver also declares which covered paths it loads, and new drivers default to all of them. A covered path whose tree passes the digest bounds (file count, entries per folder, depth, or file size), such as `.opencode` once OpenCode installs plugin packages into `.opencode/node_modules`, is digested as exceeded rather than read: Git actions and providers that do not load it continue, and every start of a provider that loads it is refused with `configuration_invalid`, trusted or not, because the digest cannot vouch for that content. Removing what the provider does not need below that path lets it start again.

Isolated worktrees live in a device-local app data folder that only the current user can open, because they copy project source. They load project configuration only when the folder is trusted and every configuration file in the worktree matches the trusted folder's; otherwise they start restricted without asking. Edits a provider makes during a turn change the digest, so the next start asks again. A provider with no restricted launch is refused in a worktree holding configuration the bound folder lacks or holds with different content, including a worktree of a folder with no configuration. No decision about the folder can admit that content, so the refusal asks nothing, and it names those files and the recovery: remove or restore them, copy them to the folder and trust it, or use a new worktree. Claude permission suggestions accepted with "Allow for session" stay in the session and are never written to the folder's settings files. Rust reduces them to allow rules, extra directories, and accepting edits, rescoped to the session; deny or ask rules, rule replacement or removal, directory removal, and other modes such as bypassing permissions are dropped. The approval panel shows exactly those grants, and the decision forwards exactly them, so nothing is granted that the user did not see. When none remain, the request does not offer "Allow for session". Ganbaru never launches editors, so editor folders such as `.vscode` in a received project stay inert until the user opens the folder in their own editor.

## Working-folder authorization

Portable working-folder identity contains no external absolute path. Managed folders resolve to a real directory directly inside the vault `projects/` directory, named by a project ID that must be one folder name; links below the vault root are refused (see [Access control](../access-control.md#working-folder-authority)). External folders resolve through a device-local binding scoped by vault, device, and logical folder ID.

Rust validates the opened directory's filesystem identity (device and inode on Unix, volume and file identity on Windows, with reparse-point escapes rejected). Git-sensitive operations separately validate the Git common-storage identity. Missing directories, stale paths, replacement, traversal, absolute injection, symlink escape, vault nesting, and unbound devices fail closed. Remote URLs, branch names, and mutable Git configuration do not participate in authority; how Ganbaru runs Git against that configuration is described in [Git and hosted CLIs](#git-and-hosted-clis).

The same authorization service serves provider startup, terminals, attachments, Markdown operations, file tools, mentions, previews, watchers, Git, checkpoints, and restores. No adapter reimplements a weaker path check. Known residual races between identity checks and later opens are recorded in [Unsafe Rust](unsafe-rust.md).

## File reads and writes

Workspace operations accept validated relative paths below the authorized root. Listing is on demand and applies Git ignore rules plus bounded exclusions for common generated or secret-bearing directories.

File tools, mentions, previews, and saves never touch Git metadata (`.git` at any depth, as a directory or gitfile), top-level credential folders (`.ssh`, `.gnupg`, `.aws`), top-level environment files other than `.env.example`, or provider credential files. Names are compared per component the way Windows and macOS resolve them: case folded, trailing dots and spaces ignored, alternate data streams and 8.3 short names mapped to their base name, and HFS+ ignorable code points dropped. A directory walk also refuses any directory whose file identity is the folder's `.git`, and Windows rejects reserved device names. `.github`, `.gitignore`, `.gitattributes`, and `.gitmodules` stay editable.

Text preview rejects binary content, invalid UTF-8, symlinks, traversal, and oversized files. Hard-linked regular files preview and promote like any other file, because package stores such as pnpm `node_modules` are built from hard links; a hard link to a file outside the folder can only be created by something that already runs as the user on the same filesystem with access to that file, so it grants no read the creator lacked. The webview receives bounded text and relative metadata only. Opening a file externally repeats authorization immediately before delegation. Folders and document types whose default handler never runs them as programs (an allowlist in the Tauri-free crate) open directly; any other type, an executable file without an extension, or a folder with an extension (macOS bundles) opens only after a native dialog that names the file, because a repository or agent can plant a script whose default handler runs it. The dialog shows bidirectional and control characters as visible placeholders, and trailing dots and spaces cannot hide an extension.

Writes use expected-revision checks where user edits could race provider edits. Temporary replacement stays inside the authorized parent under hidden names with a random token, so a process sharing the folder cannot predict and pre-create them to block a save, and a tool cannot create a symlink or use a renamed ancestor to escape the root.

Provider-reported changed files are hints. Ingestion keeps only verified, deduplicated relative paths inside the root.

## Workspace observation

One native watcher serves the current authorized target, and switching targets stops the previous generation first. Output is coalesced into bounded invalidations without absolute paths; overflow emits one refresh-required invalidation. A watcher event never proves authorization or file existence, so every later read repeats validation.

## Terminals and processes

A terminal is bound to one authorized thread, execution target, runtime approval, and process generation. Rust constructs the working directory and environment; the frontend cannot supply a host path or environment variables. The shell inherits the environment the app was launched with, so it behaves like the user's own terminal, minus the AppImage runtime variables and path entries inside the mounted image; variables the app or its libraries set after launch do not reach it. On Windows the shell starts from an absolute path (`ComSpec`, or `cmd.exe` in the system directory), never a bare name the app's current directory could complete; inside the shell, `cmd.exe` keeps its usual current-folder command lookup (such as `gradlew`), as in the user's own terminal. Terminal IDs are canonical UUIDs, and saved terminal layouts and preview server discovery from terminal output pass the same thread and folder authorization as terminal input.

Starting a terminal needs a start grant held in Rust memory for the vault, working folder, and execution environment. Only an OS-rendered confirmation that names the folder and shell creates it, so a compromised webview cannot open a shell on its own. The grant lasts for the app launch and is never persisted, because a stored grant would leave that folder's shell open to a compromised webview on every later launch. Unbinding, rebinding, archiving, or removing the folder and revoking an authorization that ran in it drop the grant; archiving one thread does not. Terminals require a persisted open thread in the requested folder or an unsaved draft thread that Rust reserved for that folder; unknown thread IDs are rejected. Unbinding, rebinding, archiving, or removing a folder also stops its terminals, and removing a worktree stops the terminals started in it first. An archived thread or folder starts no new terminal; because thread archive is reversible, terminals already running in an archived thread keep running and stay reachable from it.

Input, output, scrollback, event queues, and process lifetime are bounded. Pasted text loses control and escape characters before it reaches the shell, and Rust rejects input that closes bracketed paste anywhere but at its end, so clipboard content cannot leave paste mode and run as typed input. Live output reaches only the views attached to that terminal, each through its own channel, and a view that stops acknowledging output stops receiving it and later replays scrollback, so no other window sees the output and a stalled view cannot queue it without bound. Terminal output is untrusted display data; escape sequences and link detection must not trigger an unreviewed native action. Hyperlinks that output declares (OSC 8) open only credential-free HTTP and HTTPS targets, through the same Rust-validated path as Chat links, and hovering one shows its real target, which can differ from the visible text. Stopping, revoking, changing target, or closing the owning scope terminates or quarantines the terminal, and a stale handle cannot attach to a newer run. A running terminal blocks vault transfer, restore, and rollback, and no terminal starts while a vault operation holds the vault, so a shell cannot write into a vault that is being copied or replaced.

ACP agents run commands through terminals Ganbaru starts for them in the session's authorized folder. These terminals refuse dynamic loader injection variables (`LD_PRELOAD`, `LD_AUDIT`, `LD_LIBRARY_PATH`, and every `DYLD_` variable) in the environment the agent asks for, and each runs in its own process group (a job object on Windows), so releasing or killing it also stops the background processes it started. ACP file writes are refused while the turn is in Plan mode.

### Linux command sandbox

On Linux, `ganbaru-sandbox` (installed at `/usr/lib/ganbaru/ganbaru-sandbox`) confines a teammate process for a provider that holds no boundary of its own. The helper restricts itself with Landlock (ABI 4, Linux 6.7, required) to the listed read, execute, and write paths and either no network or TCP connections to listed ports, adds a seccomp filter that refuses the socket families and local socket calls the mode leaves out and `io_uring`, and then executes the program, so no restriction ever applies to the app. It refuses to run anything when the kernel cannot enforce the whole policy, a writable path contains the helper, or the process inherits a descriptor beyond the standard streams, so an inherited descriptor cannot carry access past the policy; a `--probe` run checks enforcement on the device. A teammate that needs the sandbox is refused folder and command access where the helper is missing (including the AppImage) or the probe fails. Grok and Cursor teammates launch through it (see [Grok teammates](#grok-teammates) and [Cursor teammates](#cursor-teammates)), and Claude and OpenCode teammates run each command through its shell mode (see [Confined shell commands](#confined-shell-commands)). Abstract Unix sockets are unreachable in every mode, because the filter allows no local socket that can connect, only connected pairs from `socketpair`, so the gap on kernels without Landlock ABI 6 is that signals stay unscoped. Other known limits: UDP stays open in TCP mode for name resolution, and the execute right on the dynamic loader lets any readable ELF file run through it.

### Grok teammates

A Grok teammate holds folder authority only when the Grok process runs under the Linux command sandbox: the helper must be found and its probe must pass when the app starts, so on Windows, Android, and Linux devices without an enforcing helper it holds conversations only, and a folder session fails to open rather than running unconfined. Under the sandbox Grok reports these boundaries, and the send gate in [Access control](../access-control.md#working-folder-authority) admits a scope only when all it needs are reported:

- Shell denied: the Grok process may execute only its own executable, so its built-in shell, subagents, hooks, and stdio MCP servers fail in the kernel and every command must go through `terminal/create`.
- Read-only folder: the working folder is readable to the Grok process and never writable, so its subagents and workflows cannot write files directly.
- Writable folder: edits reach the folder only through `fs/write_text_file`, which checks the grant, refuses any `.git` path component and symlinked path, and is refused in Plan mode; commands write the folder from confined terminals.
- Confined commands: each `terminal/create` runs under the helper with write access to the working folder, a private temporary directory that is also the command's home, and `/dev/null`; execute access to the system program folders, the folder, and the toolchain folders on `PATH`; read access to `/etc` and `/proc`; and no network. Toolchain homes are used in place under their app variable or default location (`CARGO_HOME`, `RUSTUP_HOME`, `PNPM_HOME`, `NVM_DIR`) and passed to the command: rustup, pnpm, and nvm homes are read and executed whole, while Cargo's home grants only `bin`, the `registry` and `git` caches, and its configuration, so registry credentials stay unreadable. Caches stay read only, because a later unconfined build would run what a command wrote there, and only Cargo's package cache lock files are writable, as files; a home that is, holds, or lies inside the home directory, the folder, `~/.ssh`, or `~/.gnupg` is left out. Offline builds from what is already cached work, such as `cargo build --offline`; installs that write a shared store, such as `pnpm install`, fail. A `PATH` entry that contains the home directory or the folder is dropped, so a toolchain installed elsewhere fails closed. The environment is cleared to `PATH`, the temporary home, locale and terminal variables, and the variables the agent sends, which `env` sets inside the sandbox so no loader variable reaches the helper. Read and edit grants are not offered `terminal/create` at all, and in every safety mode but full access Ganbaru holds each command and asks the person to run it once or decline, whether or not the agent asked first.
- Network boundary: the reported network is a fixed allowlist the kernel enforces, here TCP to port 443 for the provider API and the loopback port of the session's internal MCP endpoint, with web search and web fetch turned off and telemetry off; it does not mean no network.

Publication is claimed only through the push request host tool, since confined commands have no network, and person-approved commands are not claimed as a boundary, since the sandbox is the command boundary.

The read list is the confidentiality boundary. The Grok process reads the system trees, the working folder, and its own Grok home (`GROK_HOME`, or `~/.grok`), never the home directory, `~/.ssh`, the vault, the app config directory, or other providers' homes. Because the whole Grok home is readable, a Grok home that is or contains the home directory or the working folder is refused, and a custom `GROK_HOME` must be a folder used only by Grok. Inside the Grok home it writes only `sessions`, `logs`, and an existing `managed_config.lock`; its configuration, credentials, trust records, hooks, and bundled files stay read-only, so a session cannot change what later Grok runs load or trust.

A confined command can still write `.git` in the folder, which could plant a hook or configuration that a later Git run executes. Ganbaru detects this and does not prevent it: before and after each command, and after each file write, it digests the folder's Git configuration, `hooks`, `info`, and redirection files (skipping history folders only directly inside a Git directory), and on a change it ends the turn and the session with `acp_git_metadata_changed`, refuses every later command and file write of that session, and reports the change in the thread. The change is never reverted. Ganbaru's own internal Git runs never execute hooks or fsmonitor, and the changed configuration no longer matches the folder's trust record, as described in [Git and hosted CLIs](#git-and-hosted-clis). Nested repositories inside the folder are not watched, and a folder whose Git metadata is too large to digest cannot open a command session.

Known limits: TCP 443 reaches any host, including HTTP MCP servers a project `.mcp.json` names, so a compromised turn could send folder content out over it; Grok's `x_search` tool and UDP stay available to the Grok process; other folders' Grok transcripts under `sessions` stay readable; Grok saves a refreshed login by creating a temporary file in its home and renaming it over `auth.json`, which Landlock allows only with create and remove rights on the whole Grok home, its hooks and configuration included, so that right is withheld and a confined session that outlives its access token cannot save the refresh, and if the provider rotates refresh tokens the saved login may need a new sign in; command lines of other processes stay readable under `/proc`; an inherited app descriptor makes the helper refuse to start rather than run; `grok --version` and the helper probe run unconfined; Go, npm, and other toolchains without a listed home see only the temporary home; and a gitfile that points outside the folder leaves Git unusable in confined commands. The boundaries are enforced in source and covered by tests against a live helper, but a real Grok turn has not yet confirmed file reads and writes through the callbacks, a confined command, the blocked network from commands, `.git` detection end to end, or whether Ask mode prompts twice for one command (Grok's own permission request, then Ganbaru's held command).

### Cursor teammates

A Cursor teammate holds read and edit authority only when its process runs under the Linux command sandbox, and never runs teammate commands, so execute, publish, and scratch targets are refused on every device. Without an enforcing helper it holds conversations only. Under the sandbox Ganbaru starts Cursor's bundled runtime directly, in place of the `cursor-agent` launcher, for a Cursor build no older than the one the policy was verified with, and refuses any other installation layout or a custom endpoint the network boundary would not reach:

- Shell denied: the process may execute only the bundled runtime, the bundled search tool, and the dynamic loader, so every shell, hook, and MCP server Cursor would start fails in the kernel. Each launch also rewrites a configuration folder Ganbaru keeps per working folder with a deny on every shell command, removing any command-bearing file there.
- Read-only and writable folder: the process reads the system trees, the Cursor installation, the Cursor sign-in folder, and the working folder, and writes the working folder only for an edit grant, plus a private home, data, and temporary directory per launch.
- Network boundary: TCP to port 443 and the loopback port of the session's internal MCP endpoint.

Cursor writes files itself rather than through `fs/write_text_file`, so an edit session watches the folder's Git metadata and `.cursor` configuration with the guard described above and ends with `acp_git_metadata_changed` on a change. A real Cursor turn under this policy has written the folder and been refused a shell command; the app path end to end is not yet confirmed.

### Confined shell commands

Claude and OpenCode keep their own shell tools, so the provider process runs unconfined and only each command enters the sandbox. The helper's shell mode lets a provider name the helper as its shell program or command prefix: the helper reads its policy from a private file (mode 0600, refused when it is writable by its group or others or lies inside a writable path of its own policy) named by `GANBARU_SANDBOX_POLICY_FILE`, removes that variable, and runs `/usr/bin/env -i` with the cleared command environment and `bash -c` with the command, accepting only `-c COMMAND` or a single `COMMAND`. The policy is the one confined Grok terminals use (see [Grok teammates](#grok-teammates)): write access to the working folder, a private temporary directory that is also the command's home, and `/dev/null`, the same execute, read, and toolchain rules, and no network. Ganbaru writes the policy when a session of a scope that loads the shell opens, refuses a configured environment that names the variables it sets, and watches the folder's Git metadata, ending the session with `acp_git_metadata_changed` on a change.

- Claude: `CLAUDE_CODE_SHELL_PREFIX` names the helper and `CLAUDE_CODE_TMPDIR` the private temporary directory, where Claude writes the command's final directory. Every command still reaches Ganbaru as a permission request, and the permission mode is never `bypassPermissions`.
- OpenCode: the `shell` setting of the owned local server's inline configuration names the helper.

In either provider, a confined command runs without asking only in full access, the safety mode that already lets a teammate run unattended; every other mode keeps asking the person, and a custom mode is refused. The sandbox follows from the device rather than the safety mode, so an Ask for approval session is confined too. Known limits: output a provider saves outside the folder, such as Claude's file for very large command output, stays unreadable to later commands, and commands lose the provider's shell snapshot, aliases, and environment. Real Claude 2.1.325 and OpenCode turns confirmed that commands read the folder, cannot read the home directory or write outside the folder, have no network or policy variable, and use the private home, including a Claude background command; the app path end to end is not yet confirmed.

## Internal MCP host tools

Each native Chat provider session may receive an ephemeral loopback MCP endpoint with a small application-owned method allowlist, authenticated by a random bearer token and accepting only loopback hosts and origins. The endpoint keeps only a SHA-256 digest of the token and rotates it wherever a provider process starts, so the plaintext lives only in the configuration of the process that receives it. It is not a general localhost service and not an organizational participant. Because any local process can reach a loopback port, the endpoint bounds work before and after the token check: request headers must arrive within a short deadline, open connections and MCP sessions are capped, request bodies are capped, idle sessions expire, and preview tool work and resource reads stop when their request is cancelled or reaches its deadline. Organizational host tools always finish once started, so their audit rows stay complete. Claude receives the token through the `GANBARU_CHAT_MCP_TOKEN` environment variable, which its MCP configuration header expands, so the token never appears in process arguments; the CLI's MCP status report echoes the expanded header, so Ganbaru reads only server names and states from it and never logs or stores it. It runs in one of two modes.

In a direct session (a person chatting with a provider in a thread), the endpoint offers the preview tools and the thread's attached resources. The endpoint and its token live as long as the provider session, but tool calls and resource reads are admitted only while a turn the app dispatched is running. Completion, abort, interruption, a failed dispatch, and provider exit close them, so a process the model left running cannot drive the preview between turns. Listings stay open so providers can discover tools when the session starts. Each admitted preview tool call is recorded by the app with its tool, an argument hash, its outcome, and its result size, independent of what the provider reports; a result over a few MiB is refused, and each turn has a generous call and result-byte budget so a looping model cannot flood its context.

In an organizational run (a teammate assignment), every request validates the run-scoped credential, method, bounded arguments, current run and thread, channel membership, access-profile revision, execution target, and revocation state. Tools that change a folder require the source's frozen runtime approval to be auto-approve or unattended. The endpoint closes with the run, and replayed credentials or calls after interruption or revocation fail. Forking a thread that held an organizational run creates a plain direct thread: it takes the direct continuation group and the default approval mode, and copies no run, grant, or access profile, so the fork runs only with the forking user's own authority.

Every host tool belongs to one class (read, edit, destructive, delegate, ask, report, secret, or the reserved schedule class), and authorization, offering, audit, and approval follow the class rather than the tool name. Each class has its own call limit per authorization revision, so exhausting one class never spends another's budget, and an unknown tool name is audited and counted as a read. Claude teammates receive the read, ask, and report tools pre-approved through a host-built allowlist; edit, destructive, delegate, and secret tools still go through the run's approval policy, and user launch arguments cannot widen the allowlist. Delegated work runs under a folder ceiling no broader than the parent's grants at delegation time, the starting device clamps the child again against the parent's current grants, and revoking or cancelling the parent cascades to its open descendants. Teammates cannot write channel notes; the schema refuses a note whose editor is not a person. A teammate can only propose a note through its report tool, at most three per run, and nothing is saved until a person accepts it. Notes enter only the context packages of work in the channel that owns them.

Results exclude credentials, external absolute paths, and unrelated vault content, with one exception for secret requests below. A future external MCP service requires separate authorization and cannot reuse this endpoint.

### Secret requests

A teammate that needs a secret asks for it with a label and purpose; the person answers on a private card shown only on the executing device, and the request expires after 30 minutes. The value never enters events, projections, context packages, semantic updates, diagnostics, SQLite, or sync. It is written to an owner-only file in the platform app config directory, outside the vault, under a folder named by the SHA-256 of the run id, and the tool result returns that file's absolute path, the one exception to the rule that results carry no absolute paths. The value is never returned in a tool result, because Ganbaru ingests tool results as events. Before persistence, ingestion replaces every exact occurrence of a provided value in event payloads, provider references, diagnostics, and host tool arguments with a labeled placeholder; a provider that prints a transformed form (encoded or split) is not caught, which the card discloses. Values stay registered for redaction for 24 hours per provider thread, because a continued session still holds them, and a restart registers them again from surviving files. The run's secret folder is removed when the run settles and by the startup sweep, which also expires pending requests of inactive runs and removes files older than 24 hours. Secret requests are offered only on Unix desktops, where the host can verify that the file is readable only by its owner.

### Push requests

A teammate never pushes by itself. A publish target reaches its remote only through the push request host tool, an ask class tool offered only for a folder source granted publish, which reads the branch, remote, destination branch, push URL, and commit from the folder through the hardened Git runner and records them, with a digest of the folder's whole effective Git configuration in every scope (remotes, URL rewrites, and push settings included), as a question in the reply thread. A remote with several push URLs, a push URL that carries a password or names a transport other than HTTPS, HTTP, SSH, Git, or a local path, and repository configuration (including files it includes) that sets a credential helper, an SSH or proxy command, a proxy, or TLS trust are refused, so a push uses only the connection and credentials the person's own Git setup supplies. A publish grant needs a provider that classifies publication this way, because its own commands cannot reach a remote unasked: Claude and OpenCode, whose commands run in the sandbox without network or reach the person one by one, Codex, whose command sandbox has no network, and Grok under the sandbox. Every push needs a person in every safety mode, full access included: the request card on a desktop device offers Push once the asking turn has ended. Confirming pushes only while the request is open (its run completed and nobody replied since), the run's authorization revision still grants publish on that folder source, and a fresh read under the folder's mutation guard names the same commit, branches, remote, push URL, and configuration digest. A run whose Git metadata guard tripped never completes, so its request never opens. Teammate sandboxes cannot sign and often cannot write `.git`, so a request may carry a commit message instead: Ganbaru then snapshots every change under the folder (untracked files that are not ignored included) into a private index and records the tree, the person's Git author, whether their configuration signs, and the changed paths, which the card shows. Confirming snapshots again, requires the same tree, author, signing, and paths, commits that tree on the recorded commit with the person's identity and signing (never unsigned when signing is configured, and without hooks, filters, or repository signing programs), pushes it, and moves the local branch to it. The push sends the recorded or new commit id to the destination branch without force, tags, or submodules. It runs as a confirmed teammate request whatever this device's trust record says, so no trust decision is asked: repository configuration never chooses programs, no hook or fsmonitor runs (the person's global hooks included, since they would run in a folder the teammate wrote), only those transports are allowed, and a local remote's `receive-pack` runs without that repository's hooks and programs. The confirming reply derives its ids from the request, so every device shows it as pushed. The card shows the push URL, and confirmation compares it again.

## Event ingestion and diagnostics

Provider event size, nesting, sequence, identifiers, and payload shape are bounded before persistence. Unknown event kinds become typed unsupported data or safe diagnostics, never dynamically executed. Streamed message, reasoning, and plan text, including proposed plan deltas, is capped at 8 MiB per item and 32 MiB per turn, far above model output limits; the text that crosses a cap ends with a visible notice, a warning joins the timeline, and later text is not stored while the turn keeps running. Command and file change output keep their 2 MiB per artifact cap.

Diagnostics keep only identifiers, the event type, and protocol method or source names that match a strict label grammar (ASCII letters, digits, and `.`, `_`, `/`, `:`, `-`, at most 128 bytes, never an absolute path or URL); any other label is stored as a fixed marker, so free text such as prompts, tool output, or authorization values cannot reach diagnostics through a label. Provider environments and credentials are never captured. Persisted errors explain the application boundary without becoming a second transcript of sensitive provider output.

Projection changes commit before the frontend is notified, and notifications carry identity and invalidation data, not unbounded payloads.

Daily teammate usage summaries replicate counts and dates only, never prompts, provider payloads, or costs. A summary's key names the device that counted it, and a receiver holds a summary signed by any other device, so one device cannot rewrite another device's usage.

Assignment budgets replicate limits and counted amounts only. Any device may set or clear the limits of any assignment, since they only bound spend; a post carries no budget, so limits come from defaults or an explicit set. A delegated child's budget is clamped to what its parent has left, so delegation cannot widen spend past the parent's limits. The executing device enforces a reached limit in the same transaction as the provider event that reaches it and stops the provider session after commit; because working time passes without events, it also checks its working runs every 30 seconds. Nothing retries automatically after a budget or provider limit stop.

## Attachments and context

Attachment import rejects symlink sources, unsupported signatures, invalid text, traversal, and oversized files. Imports and managed reads open the file once without following a final link, check type and size on that handle, and stop reading one byte past the limit, so a file swapped or grown after a check cannot pass. Bytes are hashed and written atomically with restrictive permissions to their content-addressed name in the `chat/attachments` asset class, and an existing file is reused only after its bytes match the digest; writes, reads, and cleanup removals refuse a symlinked directory below the vault root, so a planted link cannot redirect them outside the vault. Metadata stores the managed relative identity rather than the source path, and synced references name only a digest and content type, never a path. Message, scheduled message, draft, and queued references own retention. Permanent deletion queues cleanup after a one-day grace period; a desktop cleanup pass runs at startup, hourly, and from Settings, and only while the device may write the vault. It rechecks references, removes unreferenced browser artifact files, and drops attachment rows whose digest no reference names, leaving the attachment file to the sync asset sweep. A received attachment file must match the referenced digest, size, and supported type before it is published. Attachment bytes are vault content rather than working-folder files, so viewing them needs no device binding for the folder and history images stay visible on every device; a listing names its working folder and refuses attachments from another one. When human members arrive, attachment reads must also apply the channel audience.

Mentions, workspace files, Notes, tasks, channel messages, browser artifacts, and other context sources are resolved under current authority. Natural-language instructions or provider requests cannot introduce a hidden source. Audience restrictions still apply after content is summarized or transformed. Workspace paths with control characters are never offered or accepted as mentions, because provider prompts quote mentions one per line; picked attachments keep working and show such characters in their display name as the Unicode replacement character.

## Browser previews

Preview URLs and Chat links opened externally must be HTTP or HTTPS with a host and no embedded credentials; other schemes are rejected in Rust, never offered for confirmation. Loopback targets (local development servers: the exact name `localhost`, `127.0.0.0/8`, and `::1`, classified by the same rule in Rust and in the Browser panel) open directly, and the in-app confirmation before other preview destinations is a guard against mistakes, not a security control: an external page gains model access only through the Rust-held origin grant below. Navigation stays within the opened origin and preview pages cannot open new windows. Each thread keeps a loopback origin allowlist keyed by scheme and port (every loopback host spelling counts as one origin), because another local port is another service, such as a database console or a provider server. Opening or typing a loopback URL in the Browser panel adds its origin; a page or the model reaching a loopback origin the thread has not allowed is blocked and shows a one-click approval in the Browser panel, and the model is told the navigation waits for that approval. Hosts Tauri uses for its own protocols on Windows (`.localhost` subdomains on the default port, such as `tauri.localhost` and `ipc.localhost`) are rejected even after confirmation; a `.localhost` subdomain with an explicit port is an ordinary server. App documents send `frame-ancestors 'none'` so a previewed page cannot frame the app, and app commands are granted only to the app's own webviews by label, never to preview webviews, even when a development build previews its own dev server origin. That origin stays previewable because other Tauri projects use the same default port.

Model preview tools (snapshot, screenshot, click, type, key presses, scrolling, and waits) act only on loopback pages or on external origins the user allowed for that thread from the Browser panel. Opening an external page for the user does not grant the model access to it, because a logged-in page would otherwise give a prompt-injected model the user's session. Every call resolves one tab and checks its live URL, its navigation allowance, and the last document that finished loading, so a navigation in flight never exposes the page it is leaving; waits recheck on every poll. Status reads show only scheme and host, without the page title, for pages the model may not use. Snapshots and waits read the page only through a hook that an initialization script installs in each top-level document before page scripts run, using intrinsics and DOM getters captured at that point under a per-run random name. A page that patches `JSON.stringify`, string methods, or DOM getters therefore cannot inflate or break a result: the snapshot is fitted to its byte budget inside the page (HTML shrinks first, then text, marked as truncated), and a document without the hook fails the call instead of falling back to page objects. Isolated script worlds are not used because WebView2 runs evaluated scripts only in the main world; one hook path behaves the same on every desktop engine. Origin grants are exact scheme, host, and port, stored device-locally per thread with named limits, and revocable in Chat permission settings.

Preview pages have network access, so the preview tools are a network path out of a provider sandbox. When a session's provider reports that the turn's sandbox denies network access, the first preview tool call asks the user once per native session from the Browser panel and returns a waiting-for-approval error to the model until the user allows it; the tools are never silently disabled. Calls made before the provider reports the turn's policy wait briefly for it, then return a retryable busy error.

Page permission requests (camera, microphone, screen capture, location, notifications, clipboard, and the other capabilities the engine reports by name) and JavaScript dialogs (`alert`, `confirm`, `prompt`, and the leave-page confirmation) are answered in the Browser panel, not by engine defaults. The panel names the requesting origin and the permission; a permission answer is remembered for that thread and origin until the thread's previews close, preview data is cleared, or the app exits, and listing media devices follows the origin's camera and microphone answers. Requests from opaque origins and kinds the engine cannot name are denied, autoplay stays with the engine, and each thread can have only a few waiting requests and remembered answers before new ones are refused. Dialog text is bounded and shown as plain text. Dialogs a page opens while a model click, typing, key press, or scroll is running, including one already waiting on that tab, are dismissed and listed in that tool's result, so a page cannot stall the model or trick it into accepting; the user sees every other dialog. Closing a tab or thread refuses its waiting requests. WebView2 answers are never saved in the shared browser profile. Handlers are installed right after the webview is created, so a dialog during the first page load can race them; macOS has no bridge yet.

Webview identity, port, generation, navigation events, screenshots, recordings, and cleanup are tied to the owning thread and target, so a stale preview cannot emit current events. Tab ids are caller-chosen, so opening or storing a tab whose id another thread already owns, live or only in SQLite, is refused instead of overwriting that thread's tab. Page-controlled titles and URLs are bounded to the stored limits before they reach runtime state, SQLite, or the model, and each tab persists them through one coalescing writer that skips unchanged values and logs failures. Browser artifacts are bounded managed assets with explicit references and cleanup. A model resize is clamped to the inner size of the window that holds the preview and to the capture pixel budget, and the applied size is returned; every capture checks the webview area against that budget (an 8K viewport) before the platform snapshot allocates it. Model screenshots run one at a time per thread under a rolling 24-hour per-thread count and byte quota that refuses before anything is written; user captures and recordings are not counted against the model. Cookies, local storage, and authenticated browsing are not imported into provider context.

Preview webviews never share web data with the app's own webviews (main and detached windows, the Music YouTube embed) or with another working folder. Each working folder gets a persistent data directory under the app config directory, never inside the vault, so preview logins survive restarts but a service worker or cookie set for one folder's dev server cannot reach another folder on the same port. The directory is named by a random token in Chat device state; unbinding or removing the folder, or Clear preview data in Chat permission settings, clears open tabs' data, replaces the token, and deletes the directory. Replacing the token matters because Linux keeps each WebKit web context, and its in-memory session, alive until the app exits. Directories a failed delete left behind are removed before the vault's first preview in the next app run. Each previewed folder costs one WebKit network process on Linux until exit.

## Git and hosted CLIs

Every Git and hosted CLI spawn goes through one hardened runner with a named deadline, bounded output, and process-tree termination on timeout or cancellation. Each run has an origin and the folder's trust:

- Internal runs (status, listings, diffs, checkpoints, restores, observer probes) never execute hooks, fsmonitor, or signing, and never use the `ext` transport.
- User-initiated commands in trusted folders apply repository configuration and hooks exactly as the user's terminal does.
- In untrusted folders, programs defined in local or worktree configuration (pagers, editors, diff and merge tools, filters other than standard LFS, credential helpers, SSH commands, proxies) are replaced by the user's global value or a neutral value. The same applies to the configuration of populated submodules, which Git reads when it inspects them. System and global configuration always stays, so results match the terminal.

Hosted CLIs (`gh`, `glab`, `az`) list and view change requests from a private empty directory with explicit repository coordinates, so repository content cannot steer them. Listing and creating change requests, including Bitbucket requests with its stored credential, accept only a repository that one of the folder's configured remotes points at, so the user's sign-ins act only on the repository the folder belongs to. Creation and checkout run where they need Git context. Their Git children inherit the same hardening through the environment, and `az` runs with Python path isolation. Push, pull, and fetch accept only remotes already configured in the repository and branch names that follow Git ref rules without refspec syntax, so a request cannot redirect to a URL or force-push through a `+` refspec. Error output from Git and hosted CLIs reaches the webview only after control and bidirectional formatting characters and URL credentials are removed, capped at 2,048 characters with a visible truncation marker.

Trust is a device-local record per folder holding two digests. The Git digest covers command-bearing keys from local and worktree configuration (with included files) and the hooks directory, for the folder and each populated submodule; ordinary keys such as remotes, branches, and identity are left out so everyday work never asks again. `.gitattributes` is left out because it only selects drivers that configuration defines, and branch checkouts change it. The provider digest covers project provider configuration that can run commands, as listed in [Project provider configuration](#project-provider-configuration).

- Folders bound through the native picker ask once at binding with a native dialog. Cancelling keeps the binding and leaves trust undecided.
- A folder with no repository programs, hooks, or provider settings is trusted silently, so managed folders never ask.
- A user Git action (commit, push, pull, fetch, stage, discard, clone, worktree creation, review apply, hosted change request creation and checkout) in an undecided folder, or one whose Git digest changed, asks once and then retries. Received folders with an unknown digest therefore ask before anything repository-defined runs.
- Every run recomputes the Git digest; a mismatch with the trusted digest runs untrusted, including in a worktree whose configuration differs.
- Settings shows each folder's trust and can revoke or grant it. Rebinding to a different path or repository and unbinding clear the record.

Edits to repository metadata (`.git` at any depth) are never approved automatically outside full access, because they can change what later Git runs execute. Ganbaru keeps OpenCode edits there reviewed and never approves a Cursor or Grok edit request there automatically, though both can write without asking (see [Project provider configuration](#project-provider-configuration)); Claude prompts for its protected paths, and the Codex workspace sandbox keeps `.git` read-only.

## Checkpoints and restore

Checkpoint capture and restore verify folder and Git common-storage identity immediately before mutation, and validate dirty state, changed and untracked files, repository boundaries, and the expected checkpoint revision. Stored checkpoint rows travel with the vault, so before a preview, restore, or review uses one, every object ID it names must be a full hexadecimal ID, its hidden ref must resolve to its commit, and that commit and its parent must carry its worktree and index trees; the restore preview and the restore therefore always describe the same trees.

Checkpoint indexes, review object stores and patch spools, and source-control working directories live in the system temporary directory, each in a new directory with a random name that only the current user can access (mode 0700 on Unix; Windows uses the per-user temporary directory). Another local user can neither read the repository content they hold nor pre-create or redirect them.

Working tree review measures changed files before it copies them into its temporary object store. A file over 64 MiB stays out of the copy and is listed as too large to review, with its staged state kept and whole-file actions still available; the remaining material is refused before any copy when it exceeds 2 GiB, and the finished store is refused over 512 MiB. Bitbucket API responses are read incrementally and refused at the same bound as other source-control output, so a hostile or broken server cannot exhaust memory.

Whether a finished assignment is ready for review comes from the files recorded for its turn, and in a Git folder those include the post-turn checkpoint diff, which is captured before the completion is recorded. A provider therefore cannot skip review by omitting changed files. The diff covers the whole folder since the thread's previous checkpoint, so concurrent edits by others can also mark work for review. Folders without Git rely on the files the provider reports.

Restore is a scoped Git or filesystem operation, not a database rollback. It cannot change organizational messages, memberships, approvals, or another project's files. Previewing and applying a restore are separate authority checks. Native work runs outside database transactions, and retryable cleanup records prevent a failed step from appearing successful. Every claimed cleanup job ends completed or failed; a job an interrupted run left running for more than 15 minutes is released for retry, and diagnostics count it as failed.

## Message authorship

A message's author participant and display label are claims by the writing device, not an authenticated identity, until separate human identities exist: a linked device can seal any participant or label. All people share one local owner participant, so a false author grants nothing beyond membership. Apply does not refuse a false author, because whether a row is valid would then depend on the order of an assignment and its message, and a refused row can stop apply. Sync does establish which devices created the row, from the signed operation log. An edit points at a new revision that its own device created, so the same log names who wrote the current text. The message's `Sent from` action shows the creating devices, and a `Last edited from` line when the devices that created the current revision differ from them. Devices are named from the authorization log so a removed device stays named, the action appears only when sync holds a record of the message, and a revision without a record shows no line. A device can still repoint a message at a revision that already exists, which reproduces earlier text under that revision's creator but cannot add new text unattributed.

## Revocation

When membership, history, profile, target, runtime, scratch, or audience authority is reduced, new native actions fail immediately. A continuation that already materialized restricted context is interrupted and discarded or quarantined before reuse.

Sync keeps revocation ahead of widening. When concurrent edits from linked devices change one membership or grant, a removal, revocation, or narrowing wins over any widening, as owned by [Chat schema](../schema/chat.md#access-profiles-and-authorization-revisions). Native work runs only on the device that executes it, which keeps its approvals and execution state; after sync applies authority rows there, that device revokes the active authorizations the merged rows no longer cover and stops a run whose assignment settled on another device. Those rows include the teammate itself: a synced reduction of its approval behavior revokes the authorizations it no longer covers, whichever row arrives first, and a synced archive revokes all of its authorizations, because the archiving device cannot see work running here. A later widening or restore does not revive them. A scratch run rechecks the same teammate approval and archive state before it dispatches or reuses a generation.

Known limit, to resolve before a release that enables Chat on linked devices: a history granted from a point is stamped with the order key after the last root item the granting device holds. A post another device wrote before the grant, but the granting device had not received yet, takes an order key at or above that stamp and becomes visible to the teammate. Fixing it needs a converged anchor (stamping on one writer, or restamping when earlier items arrive), and a creation time bound is not sound because device clocks differ and offline posts take keys out of time order. The exposure is limited to posts written concurrently with the grant on another linked device.

Archiving the project or a run's folder, unbinding that folder, or rebinding it to another directory revokes the active runs that execute in or were granted the folder and stops their providers. Provider events are checked against the same live authority; the first event that fails it, rather than a database error, revokes the run and stops the provider instead of only rejecting the event. Plain text deltas may reuse a passing check for up to half a second while no authority change happened on this device, and any authority change forces the next event to be checked.

Provider stop, tool shutdown, terminal, preview, and scratch cleanup have bounded deadlines. Incomplete cleanup persists as a retryable record without weakening the revocation or exposing native paths. Scratch removal walks relative to open directory handles and removes links without following them, so a provider process still running in the scratch cannot redirect deletion outside it.

Settings lists the provider and Chat terminal processes started during this app launch, with their child processes up to a fixed bound. Stopping one row is a confirmed native action that signals the process group only while the process ID still names the registered process with the same kernel start time and still leads its own group, and it never signals the app itself or process 1, so a reused process ID cannot redirect the signal. Stopping a single row is available on Linux; other desktop platforms list processes and keep the stop-all action.

A Linux resource scope needs the user bus address and runtime directory to reach the user systemd manager, so only the scope launcher receives them, and the scope removes them, together with the invocation ID it sets, before the provider starts. The provider therefore keeps its allowlisted environment and gains no session bus access through the scope. The scope launcher is found only at fixed absolute paths, never through `PATH`.
