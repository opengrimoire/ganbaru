# Chat conversations

## Organizational vocabulary

- **Group:** the top-level local organizational container.
- **Project:** a durable work area with channels and optional authorized working folders.
- **Channel:** a durable project conversation, beginning with `#general`.
- **Reply thread:** focused discussion attached to one message; AI work assignments run inside reply threads.
- **Provider run:** one bounded execution session linked into a conversation.
- **Direct message** (planned): a durable conversation with stable participants.
- **Task discussion** (planned): a conversation attached to one project task.

Provider thread IDs and model names are never conversation or participant identities.

## Navigation and lifecycle

The sidebar shows project channels, personal sections, and search, following the [shared Notes and Chat sidebar design](../notes/pages-and-navigation.md#shared-notes-and-chat-sidebar-design). Channel membership is durable vault data. Personal sections and the last selected channel are device-local presentation state. Channels and sections can be starred, which lists them first; after that, the sidebar orders them by a custom order, name, last activity, or creation using the global Chat setting or a per-project override from the project's Chat settings. The default channel has no fixed position. Direct messages are planned as a separate tab rather than a sidebar section.

Above the sections, the rail shows a Needs you section with the [review queue](agents-and-coordination.md#results-and-review) when it is not empty, with the same collapsible heading as the other sections; desktops can select reviews to accept together, and Android shows it read-only. Channel rows mark a channel whose work waits for an answer, an approval, or a review with an accessible label; working and queued work show no marker. At its end, a channel row counts unread top-level messages plus new replies in threads the person started or replied in, and shows a red dot after the count while the channel holds a failure the person has not seen; opening the channel clears both. When work in another reply thread starts waiting for the person, a polite screen reader announcement names the agent and channel, follows the same Focus and quiet period deferral as notifications, and can be turned off.

The header breadcrumb shows the group, project, and channel whether or not the channel rail is open. The header project navigator searches channels by name or topic across the listed projects, grouped by project. In the custom order, a mouse or pen drags channels among their siblings in the sidebar and the channel picker, and drags personal sections in the sidebar; a touch does the same after a stationary hold, so a swipe still scrolls. Dragging a channel onto another section moves it there. Starred items stay ahead of the rest. Row and section menus move an item up or down for keyboard users. Reordering is off while searching. Each project keeps its channel order in the vault config, and channels without a saved place follow by name; section order stays device-local with the sections. An eye button beside the channel picker sort lists archived channels after the active ones, marked with a muted archive icon and left out of reordering; channel pickers opened from a project row follow the same choice, and opening an archived channel shows its readable history.

One channel dialog, opened from the sidebar, edits the name, topic, personal section, and members together. The local person is always the first member and cannot be removed there; leaving a channel is an action on the channel itself, and the last person cannot leave. Members are grouped as People and Agents, added through the shared participant picker, and changes apply on save. An added agent takes the channel's access level, which the channel's Agents section sets as described in [Channel-centered agent configuration](channel-configuration.md). Removing an agent that has active work asks for confirmation with the impact.

The channel header shows the members as an avatar stack with a count. It opens a details panel with the topic and the member list, where members can be added or removed by someone who may manage members and the channel dialog can be opened. A channel never shows an in-feed prompt to add agents.

Archive hides a conversation from normal navigation without destroying its messages, links, drafts, or review history, and stops its provider session, interrupting a running turn. Restore returns it to its project. Permanent deletion is explicit and includes a cleanup plan for owned execution resources.

Search uses bounded, paginated reads over active or archived conversations according to the selected filter. Opening a result restores the conversation and position without loading its complete history.

## Messages and replies

Messages are durable participant-authored records. They can include text, validated attachments, references to tasks, projects, folders, and files, replies, mentions, and provenance for generated or transformed content.

Reply threads keep detailed work from overwhelming the main channel. A message that mentions a person (including yourself), an agent, or a channel opens its reply thread when it is posted, so it shows a reply link at once; folder, file, and environment references alone open none. A provider run started from a reply posts concise state and results to the main timeline; detailed execution stays inspectable in the linked run. Beside the channel feed, the reply thread column resizes from its separator by pointer, keyboard, or double-click to fit, like the secondary panel, and this device keeps its width. On desktop, an open reply thread can move into a workspace tab of its own, which shows only the thread header, its timeline, and its composer at the channel feed's width, with the thread icon and the channel in its title. That tab always stays on its thread without a lock; it detaches into a window and restores like any tab, and closing the thread closes the tab, or turns it into its channel when it is the only tab.

Channel notes are short facts a channel keeps about how its work goes, such as a style rule or a decision. Any person in the channel can add, edit, or delete one; AI agents cannot write notes, but an agent can suggest up to three per run, which a person saves as suggested, saves with edited text, or dismisses. When one device deletes a note while another edits it, the deletion wins.

Linked devices can all post and edit. A post written offline syncs when its device reconnects and takes its place after the messages that device had seen, so it can land above messages another device already read. Two devices can create channels with the same name at once; both channels stay, and either can be renamed. When two devices edit one message, the name or topic of one channel, the wording of one channel note, or one agent's profile at once, one version shows and Settings > Chat lists the conflict so either version can be kept.

## Composer

Channels and reply threads share one composer, which supports drafts, attachments, replies, explicit agent mentions, provider interactions, and scheduled sends. A scheduled send can repeat daily, on weekdays, weekly, on chosen days, or every few hours; a repeating occurrence its device missed is skipped rather than sent late. The list of scheduled messages shows each one as it will post, with send now, copy, edit, and cancel actions; editing loads its text, references, attachments, time, and repeat rule into the composer in place of the draft, saving replaces the message in place on every linked device, and editing is refused while it is being sent or after it was sent. A message can be sent without invoking AI, and plain conversation never silently becomes an execution request. Typing an agent name without `@` suggests a mention chip on this device only; the text stays prose until the chip is chosen, and nothing runs until Send. A long paste becomes a text attachment instead of message text, a paste over the attachment limit is refused, and pasted invisible direction and zero-width characters are removed with a notice, leaving the rest of the text unchanged.

Formatting follows Slack: selecting text with a mouse or keyboard shows a floating toolbar for bold, italic, strikethrough, numbered and bulleted lists, quotes, inline code, and code blocks, each also reachable by Slack's shortcut (listed in Settings > Shortcuts). The message is stored as Markdown, so lists, quotes, and code blocks are written as their Markdown line syntax, and underline is absent because Markdown has no underline. Touch selections and the Android shell keep the platform selection menu instead of the toolbar.

A reply sent to a thread with active work waits as a pending input of that work: Enter queues it and Mod+Enter steers it, while Enter sends as usual when no work is active. Steer reaches the agent's current turn while it works; on work that is not working yet or waits for the user, it queues instead and the reply says so. Queue waits until the current turn ends, then the work continues with the queued replies in order, including a reply that reaches the executing device through sync after the turn ended; work that was cancelled or failed keeps them pending. A scheduled message cannot choose either. Its author can edit or cancel it until a run receives it, and an edit or cancel that arrives after delivery is refused as already delivered. A waiting reply shows only in the queue; when a run receives it, it enters the thread after everything already there, showing the time it was received, a cancelled reply never enters it, and a reply still waiting on work that failed or was cancelled shows where it was posted. A reply that started its own work cannot be edited, and cancelling it stops that work.

A queue attached to the thread composer lists the replies that still wait, failed to reach the run, or changed after the run received them. A waiting reply can be steered into the current turn, removed, held, resumed, or moved by drag or keyboard; a held reply keeps its place and is never delivered until it resumes, delivery takes the first reply not held, and hold and order sync to every linked device. Editing a waiting reply replaces the draft until the edit is saved or discarded; attachments, references, and scheduling stay unavailable during that edit. While work runs, a card above the thread composer summarizes the agent's latest structured plan (steps done, one bar segment per step, and the step in progress) until every step is done. Each working run ends its activity in the thread with its own Stop working control (also reachable through the stop shortcut and `/stop`), so a reply can always be sent while work runs. A post carries no folder control and chooses a model only through `/model`: work runs in the folder and on the model the channel resolves, as described in [Channel-centered agent configuration](channel-configuration.md), and the reply thread names the working folder of its newest run only when that run's project has more than one active working folder (or says it runs without a folder when none applies). An agent's context usage shows in its identity card within the run's activity, and provider limits show in `/status`; both come from the provider session of that run, and a phone that reads the run from the executing desktop shows the context usage its turn reports.

Slash commands are discoverable actions, not an alternate security model. They can change presentation, select an interaction mode, or start a typed application action, but cannot bypass project, folder, provider, or confirmation boundaries. The composer lists workspace commands only from command folders that resolve inside the workspace, so a repository link cannot point the catalog at other folders; user-level command folders may link anywhere. In channels and threads, `/` offers the app commands that apply there (schedule, attach images, stop work, status) with the agent provider's commands, and `$` offers its skills; both insert text into the message, and provider actions that act on a session directly, such as compacting it, are not offered there.

When a message looks actionable but lacks an authorized target or a clear objective, Chat keeps it as conversation or asks for clarification. It never guesses a working folder or broadens authority.

## Timeline

The timeline combines organizational messages with normalized run events in canonical order, with stable anchors and enough provenance to show who requested work, which provider executed it, what authority applied, and what it produced. Live changes reread only the rows that changed, so older history a reader scrolled to stays loaded. Channel messages and replies render the same safe Markdown as provider output, and mentions and references stay interactive inside it.

Routine low-level provider events can fold after settlement. Errors, interactive requests, decisions, file changes, checkpoints, and final results stay easy to find. Folding is presentation only and never deletes history. Long tool output loads in full only when it is opened; until then a shortened preview, the newest output for commands, says it is shortened.

## Attachments

Images and bounded text context are copied into managed vault storage. The attachment record keeps original display metadata and its owning conversation or message; external absolute paths are never portable attachment identity.

Unsupported, oversized, missing, or unsafe files fail explicitly. Previewing an attachment does not grant the provider access. A run receives an attachment only when its typed request and authorization include it. A free-form answer to a provider question can carry images and pasted text attachments, which reach the agent as references it reads through its thread; an answer in a thread without a working folder on this device cannot attach. A device without local execution, such as a phone, attaches only to the project's primary working folder, and agent work accepts a message's attachments from any folder of the project it runs in, so work in another folder still receives them. An image whose file has not synced yet shows its name, and opening it reads it again.

## Responsive behavior

Desktop and mobile use the same conversation model. On narrow screens, channel navigation replaces the conversation temporarily instead of covering it with an ambiguous overlay. Android Back unwinds navigation, reply, request, and composer layers before leaving Chat.
