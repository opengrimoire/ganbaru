# Device linking and synchronization

**Status: Partial.** Every linked device writes the whole vault. Quick notes, portable preferences, user themes, contacts, the Music library, Projects with working folder bindings, Calendar, distraction rules, daily distraction usage totals, distraction block history, closed Focus runs with device Focus activity, Chat organizational content (identity, policy, channels, conversations, memberships, folder grants, messages, scheduled messages, and work assignments), and the Notes structure and databases (folders, pages, page aliases, blocks, databases, properties, values, views, templates, comments, suggestions, and assets) replicate concurrently between linked devices as signed operations through the coordinator desktop and directly between members on the LAN, with conflicts and recovery entries where the domain surfaces them (contacts resolve silently by fixed precedence). Enrollment, removal, roles, and anchor handover follow an anchor-sequenced authorization log with admin keys, a recovery kit, removal cutoffs, and late changes; this is implemented in source. Secure LAN pairing through one administration desktop gives each linked device a whole-vault snapshot copy to start from; there is no vault owner and no read-only copy. Physical multi-device acceptance is pending. Text merging, operation encryption, and delivery beyond the LAN are planned.

This contract links one person's devices; multi-person sharing is later work. The phone must provide full offline access to portable Notes, Projects, Calendar, and other synchronized content. Each device runs its own Focus sessions with no controller ownership; execution and evidence rules live in [Focus authority](../algorithms/pomodoro/focus-authority.md).

Related documents: [Sync engine decision](../architecture/decisions/sync-engine.md) explains why the engine is built this way, [Sync topology and authority](../architecture/decisions/sync-topology-and-authority.md) why authority is ordered by one anchor per space, [Sync merge rules](../algorithms/sync/README.md) owns merge semantics and worked examples, and [Sync schema](schema/sync.md) owns the engine tables.

## Implemented device linking and snapshot bootstrap

Source: `apps/client/src-tauri/app/src/vault/handoff/` (pairing, enrollment approval, the coordinator that serves first copies, the bootstrap client, snapshot staging and activation, and the transports), with the wire protocol, pairing state, and Linux firewall authorization in `crates/ganbaru-handoff/`. Linking pairs devices and gives each one a whole-vault copy, including the operation log, to start from; after that every domain replicates concurrently and every linked device writes. There is no vault owner, write transfer, or read-only refresh.

### Pairing and transport

The administration desktop runs one embedded coordinator that listens on every local IPv4 and IPv6 address, so a new lease or network needs no restart, and coordinates up to 32 enrolled desktops and phones for one vault. Phones link by scanning a short-lived, single-use QR invitation; desktops paste the complete textual invitation. The QR form is a compact binary projection because module density limits reliable scanning distance. Every device authenticates with its own certificate and pins the coordinator fingerprint from the invitation, and mutual TLS protects all later traffic. The link accepts only TLS 1.3, and the coordinator admits a client certificate only when it is byte for byte the certificate of a device it linked or revoked, with no certificate chain. Device certificates are self-signed, carry a fixed common name that names no device, and are trusted only by pin, so their validity dates never decide trust and a long-linked device never expires. A certificate fingerprint has one form everywhere it is scanned, stored, or received (the SHA-256 of the certificate as 64 lowercase hex characters), and pins are compared exactly; any other spelling is rejected rather than normalized, so two encodings can never name one identity. There is no account, hosted service, relay, internet traversal, or general remote procedure interface.

A linked device reaches the coordinator through every address it knows, not only the one in the invitation. Each sync state carries the reportable listener endpoints the coordinator has now (private IPv4, IPv4 link-local, unique local IPv6, global IPv6, then overlay, at most eight), and the device stores them with its coordinator pin. The vault's discovery key comes from the authorization log: the charter names the first one, and every removal names a fresh one, so a removed device stops recognizing advertisements. Each sync pass follows the current key into a device-local file that also keeps the replaced key, which devices still browse for 24 hours after first seeing the rotation. A dial tries the last endpoint that answered, then the reported ones, then the invitation endpoint, each under the same address policy as any other dial target. It starts the next candidate whenever the pending ones have not finished within 250 milliseconds, and the first to complete the pinned handshake wins and becomes the last endpoint, so a coordinator address change costs one slower dial instead of relinking. When every candidate fails and a sync pass has read the discovery key, a linked desktop browses the local network for the coordinator over DNS-SD for at most 3 seconds, at most once a minute, and dials the discovered endpoints it has not tried yet under the same address policy. Discovered endpoints stay dial candidates in memory for 10 minutes and are never persisted; only one that answers is stored, as the last endpoint. The desktop coordinator advertises while its listener runs and the active vault has a linked device, under an instance name that is an hourly member tag derived from the discovery key and its certificate fingerprint, so only devices holding the key recognize it (see [Network and privacy](security/network-and-privacy.md)). An Android background pass that reaches no candidate browses the same way for 3 seconds and runs one more pass with the discovered records; the foreground app on Android does not browse.

An invitation alone links nothing, because it can leak. The enrolling device and the coordinator both show a confirmation code derived from the invitation id and both certificate fingerprints, so a request from another device holding the same invitation shows a code that does not match the one on the device the user is linking. The coordinator verifies the request, then persists no peer and sends no vault data until its user approves on the screen that shows the code; that screen replaces the open QR invitation. One request waits at a time for up to 120 seconds. Declining spends the invitation; a timeout or a closed connection keeps it, and creating a new invitation cancels the waiting request.

Enrollment is idempotent for the same device identity and coordinator. A linked client must unlink before accepting an invitation from a different coordinator, vault, or certificate. A reinstalled app has a new device identity and stays a separate membership until the old entry is removed. Memberships are device-local and recorded per vault: only the active vault's linked devices count, so a new or switched vault starts unlinked. Enrolling a device under another vault replaces its earlier membership, and at the stored limit, enrollment revokes the oldest memberships of other vaults first.

Device labels follow the display text rule in `ganbaru-contacts`, which person names are meant to share: labels are bounded and reject control characters, directional marks, embeddings, overrides and isolates, and invisible separators, while the zero-width joiner and non-joiner that emoji and several scripts need stay valid. Enrollment rejects an invalid label before spending the invitation. A stored label that fails the rule is rewritten locally on load (offending characters removed, or the device ID if nothing remains), because labels are unsigned display data and the link should keep working. If saved pairing state still cannot be loaded, linking is disabled for that run with a visible reason instead of stopping the app, and the vault stays writable.

On Linux, when an active host firewall blocks the coordinator, the app explains the request and opens the operating system authorization agent; it never receives the administrator password. Installed Debian, RPM, and AUR packages use a named PolicyKit action that runs only a separate root-owned helper binary with no GUI libraries, which revalidates every argument; development and portable builds use a generic authorization fallback. The action asks for the administrator password on every run and never reuses an earlier authorization, so no other process in the session can run the helper silently; each grant or removal hands all its rules to one helper run, so it asks once. The app and the helper run authorization and firewall commands only from fixed system paths that only root can replace. The app manages only its own rules, for every IPv4 and IPv6 address the coordinator reports and every active firewall that filters that family, scoped to the interface under UFW or the zone of that interface under firewalld. A listener rule admits TCP 43821 for production (43822 for development so both can run) from the connected network of a LAN address to that network; an overlay address, including unique local IPv6 on an interface without a default route, admits its whole overlay block on its own interface. A discovery rule admits UDP 5353 to the multicast DNS group from the connected IPv4 network or from IPv6 link-local addresses; overlays get none, and a failed discovery rule never blocks linking. The opened source range never extends past the private, link-local, unique local, or overlay block that holds the local address, or the /64 of a global IPv6 address, using the same address rule as linking dial targets; a broader connected route is narrowed to that block. The helper accepts no other port, protocol, destination, or source, and grants a global IPv6 source only when it is the /64 of one of the host's own addresses, which the helper reads itself instead of trusting the caller. Each rule is recorded before it is applied, so removing access also removes a rule whose grant failed or was interrupted. Rules match addresses rather than networks, so the app records the networks the user allowed each rule on, identified by the hardware address of the interface's default IPv4 gateway, which its IPv6 rules share. On another network that reuses the same addresses, the coordinator closes LAN connections on either family before the TLS handshake until the user allows that network, which needs no administrator authorization; a network without a resolvable gateway counts as allowed. It never disables the firewall, and the user can remove its rules from Data settings. Removing the installed package removes every rule the app added, found by its shape in each firewall rather than in per-user state; upgrades keep them.

Every invitation, copy request, and archive declares the handoff protocol and a fingerprint of the embedded SQLite migration set. A mismatch is rejected before snapshot preparation with a request to update both devices. Package versions are included only for diagnosis, because equal versions do not prove an equal data format.

### Snapshot copies

Every linked device writes every domain, and the engine below merges the changes. A whole-vault copy only gives a device a starting point: the first copy after linking, and a fresh copy when a device fell behind compaction (see [Replacing and recovering vaults](#replacing-and-recovering-vaults)). Every copy follows one bounded path:

1. The serving device flushes its pending distraction usage totals, briefly fences new writes, drains current writes, isolates database access, seals pending changes, and creates a consistent SQLite snapshot. Writers resume as soon as the snapshot exists, and running Chat terminals keep running because the serving vault stays intact on disk.
2. It archives the complete portable vault without live WAL or SHM files, and the receiver streams it into device-local staging.
3. The receiver validates identities, bounds, archive size and hash, paths, required files, the current migration set and schema, and SQLite integrity. The hash is the sender's own digest, so it catches corruption, not tampering; authenticity comes from the pinned mutual TLS connection, and the content checks apply whichever linked device sent it.
4. The receiver fences its own vault, carries forward the changes it has not delivered yet (see [Carry-forward across replacement](#carry-forward-across-replacement)), atomically activates staging, reopens through normal startup, and acknowledges. An unacknowledged copy is acknowledged on the next link pass.

A failure or cancellation before activation leaves the vault in use untouched and releases the fence. Running Chat terminals block a replacement, backup restore, and database rollback, and no new terminal starts while any vault operation holds the vault.

The coordinator prepares one copy at a time. A request that finds it busy keeps polling for up to 90 seconds and then reports busy without changing anything; a busy member desktop makes the request move on to the next source. Each linked device can start only a fixed number of copies per sliding hour, counting new requests but not polls of a pending copy, so a device that keeps requesting and cancelling copies cannot keep writers paused. Copies are rebuilt for every request rather than reused, because no change marker can prove an older archive is still current.

The archive carries only the documented vault layout: `vault.json`, the SQLite snapshot, the skeleton directories (`notes`, `diary`, `projects`, `reports`, `assets`, `templates`) with their contents, and only folders directly below `projects`. Creation leaves anything else out, extraction skips it with a log line instead of failing, and activation moves the receiver's own entries outside that layout into the new vault, so a planted `.git` or provider folder at the vault root never arrives and local files there are never lost. Managed project folders travel whole, including `.git` and provider configuration, because Git-kind working folders and checkpoints need them; Ganbaru's internal Git never runs repository-defined programs, and user Git actions and provider launches follow the device-local, digest-keyed folder trust in [Chat security](security/chat.md#git-and-hosted-clis), so a round trip with unchanged content asks nothing and changed or new content asks once. External music and project folders, credentials, executable and provider paths, operating-system permissions, the active-vault pointer, device keys, pairing records, and live process state stay device-local. Chat provider configuration and runtime approvals are device-local too and never travel in the archive.

A linked device keeps its copy and writes it whether or not the coordinator is reachable. While its copy is missing, the link loop retries every 30 seconds and the device reports that a first copy is required; a copy never starts by itself, because it replaces the vault in use. After activation, Android reruns startup reconciliation, rebuilding Calendar notification schedules and republishing distraction rules; later changes reach them through incremental sync. A whole-vault copy is an explicit operation and must never run after every mutation as a substitute for incremental sync.

### Replacing and recovering vaults

Linking never merges two independent vaults. Every first link starts with a snapshot bootstrap: a newly linked device copies the linked vault from the coordinator in one confirmed action before it exchanges any operation, and the coordinator serves its own copy because every domain the snapshot carries is current there. The confirmation states where the vault in use will be kept. On a computer, the linked vault goes into a folder the user may choose in the linking flow; without a choice it uses the default platform folder when that is missing or empty and otherwise an empty sibling named after the vault, numbered when the name is taken. A chosen folder must be missing or empty. The previous vault folder is never touched and stays in the vault picker; the chosen folder stays in native state and never comes from the webview. On Android, a vault other than the linked one is first written as a portable backup into the app-private replaced-vault set, which keeps the two newest; Settings > Data lists them with Restore, Export to Downloads, and Delete. Restore places the copy like a restored backup and is refused while the phone is linked, as the link status reports it. When that backup cannot be written the link is refused with a storage message, and only after it is written is the replaced folder discarded. An untouched Android starter vault is replaced without a backup. Native code alone decides that: a device-local record names the vault the app created during first-use onboarding, and entering the app with it or selecting any other vault clears the record for good. Linking does not need the starter: any Android vault may be replaced this way. Desktop never takes this path: when a computer replaces a folder that holds another vault, it keeps that folder whole beside the linked one. Once the linked vault has been activated, linking is scoped to its vault ID: while another vault is open, the device neither receives nor serves copies, and the coordinator serves copies only of the vault it has open, so switching vaults pauses linking instead of retargeting it.

Every device keeps what a copy replaced. When an activation replaces the same vault, its database moves into the device-local `.database-rollbacks/` set as a replacement copy instead of being deleted; a bounded number of the newest replacement copies is kept, apart from reset copies. A replacement that holds less than half of the data it replaces (used database pages plus files in the vault layout, once the previous vault holds at least a megabyte) is accepted but flagged: that copy keeps the whole previous vault, a notice appears on that device at startup, and Settings > Data restores it in one action or dismisses the notice. Flagged copies have their own bound, so ordinary replacements never push them out, and dismissed flagged copies age out after a month. Restoring replaces only this device's database, as a backup restore does. A failure to measure or retain never deletes data: the previous folder is kept as a visible sibling instead.

Unlinking never merges or discards a copy. Any linked device, the coordinator included, can be removed while unreachable. The coordinator keeps a bounded revocation record; on reconnect the removed device is denied, clears its link, and keeps its copy writable. Network and TLS failures never clear membership. If the coordinator itself is permanently lost, an explicit recovery action unlinks this device from the coordinator and every peer and keeps its copy as a standalone writable vault; the copies do not merge.

A snapshot copy is deliberately not the concurrent synchronization system: it carries no conflict resolution and never runs in both directions. Merging belongs to the replication engine below.

## Implemented concurrent replication

Source: `crates/ganbaru-sync-contracts/`, `crates/ganbaru-sync/`, `crates/ganbaru-sync-replica/`, and `apps/client/src-tauri/app/src/sync/`. **Status: Implemented** in source for Quick notes and their tags, portable preferences, user themes, contacts, the Music library, Projects with working folder bindings, Calendar, distraction rules and block history, Focus history, and the Notes structure, databases, comments, suggestions, and assets; physical multi-device acceptance is pending. User-facing behavior is owned by [Quick notes](../features/quick-notes.md), [Themes](../features/themes/README.md), [Contacts and invitations](../features/collaboration/README.md), [Music](../features/music/README.md), and [Calendar](../features/calendar/README.md), and the network surface and key storage by [Network and privacy](security/network-and-privacy.md).

### Table classes and domains

- Every table has an explicit classification in the engine manifest: replicated, owned children, derived, local, or engine. A test fails on any unclassified table or column, and an unknown table never replicates. Domains may register [materialize hooks](../algorithms/sync/README.md#materialize-hooks) that keep hook columns and derived tables current after remote changes.
- Owned row ids are unique only within one owner's value, so a domain mints fresh random ids for owned rows. An operation that gives a second owner an existing id makes the apply that would materialize it fail and roll back, with the error shown in sync status; this is accepted because only a paired writer can produce it. See [owned tables](../algorithms/sync/README.md#owned-tables).
- The manifest is a registry of sync domains. Each domain declares its table id range, replicated, derived, and local tables, and the policy of every trigger on its tables.
- Replicated tables travel as operations and are writable on every linked device. Local tables and local columns hold device state: they never travel as operations, snapshot copies empty or reset them, and a replacement restores them from the receiver's live database.
- Projects replicates, including group deletion, and project icons travel as the `project-icons` asset class. Applied Projects rows notify open Projects windows, which reload what they show. A deleted group, project, section, status, or task with edits the deletion missed is offered for recovery. Restoring it inserts a new row with a new id and its retained values, together with its deleted descendants and its links to Calendar events that still exist, as ordinary local writes: a project returns to its group or the first group with a new managed working folder, a task whose section or status is gone moves to the first one of its project, a subtask whose parent is gone or is now itself a subtask becomes top-level, a dependency that would close a cycle with the current dependencies is left out, and a section, status, or task whose project is gone is refused, leaving the offer to be discarded or restored through the project.
- Calendar replicates, including task and event links. Applied Calendar rows rebuild iCalendar projections, refresh the Focus Calendar context, and tell open Calendar windows to reload. A deleted event with edits the deletion missed is offered for recovery and restored as a new event with its owned rows and its links to tasks that still exist; it returns to its calendar or to Local when that calendar is gone. A removed calendar is not recreated: restoring its offer brings its edited events back into Local, and the calendar itself comes back by adding or subscribing to it again. Preserved iCalendar source rows cannot be restored, only discarded, because they come back by importing the file again.
- Distraction rules replicate. Edits resolve silently, with no surfaced conflict, because they are low-stakes toggles. Applied and restored rule rows republish the rules to the desktop blocker, the browser host, and Android exactly like a local edit, and tell open Settings windows to reload. A deleted custom category or usage limit with edits the deletion missed is offered for recovery and restored under a new id; a category whose name is taken gets the lowest free number from 2. Runtime snapshots stay on the device.
- Distraction usage replicates as one daily total per device, source, and local date, never as raw samples. Usage samples are local: each device keeps its own journal and writes only its own totals, so the key carries the device id and totals merge by maximum without conflicts. A device flushes a total at most every 5 minutes while limits are read, and forces every stale total out on desktop exit, when Android moves to the background, and before a vault snapshot, because snapshots empty local tables. Limits add other devices' totals to this device's own samples. Totals are never deleted; reads keep the 400 day retention window. Desktop usage first enters a bounded device-local spool that drains into the journal. Simultaneous use on disconnected devices can briefly exceed a combined limit, and a cloned installation that shares a device id undercounts.
- Focus history replicates, and every linked device runs Focus and owns its own runs. A run replicates only once it is closed: closing it publishes the run with its segments and run events in one seal, while open runs and heartbeats capture nothing. Execution and adaptive state stay local. Each device also publishes one activity row, keyed by its device id and written only on start, phase change, pause, resume, and stop, which expires 10 minutes after the planned phase end while running or 30 minutes after the pause began. Automatic admission skips an occurrence another device's fresh row is focusing on, an explicit start asks for confirmation naming that device, and applied Focus rows refresh the Focus Calendar context and open Calendar windows. Concurrent runs on one occurrence are kept side by side because each run belongs to its device.
- The Notes structure, databases, comments, and suggestions replicate and are writable on every linked device: folders, pages, page aliases, and blocks with whole-group block content, so concurrent edits to one block's text surface a conflict rather than merging by character, and databases, data sources, properties, options, property values, relation edges, views, templates, with each template's content as one snapshot, and comment threads, anchors, comments, reactions, and suggestions, and the asset rows of page icons, page covers, and Notes files with their bytes. Remote rows refresh hook-derived parents, block and comment pages, plain text, reminders, mention candidates (a mention already due on arrival settles as delivered without a notification), and cached rollups and asset references (an asset row that arrives after the rows naming it refreshes those owners), drop the search and link index fingerprints so the next read rebuilds them, and queue page history snapshots. After an apply each device runs the Notes structure repair described in [Notes and Projects](schema/notes-and-projects.md#sync), and an open page reloads around unsaved local edits; title, block text, value, discussion status, and comment body conflicts are resolved on the page, as described in [Editor](../features/notes/editor.md#persistence), while property and template conflicts keep the displayed version. Every Notes table that can root a recovery entry has a restorer. Restoring a page, block, discussion, comment, data source, or template inserts it with a new id and its retained values together with its deleted descendants, out of the trash, as ordinary local writes: a page returns to its data source or the workspace (a page nested in a block returns in place when that block is restored) and keeps its project while the project exists, a data source to its database with its properties, pages, views, and templates, a block to its page in its retained position (a nested page or database comes back with the block that holds it), and a discussion or comment to its block or discussion. A row whose parent, block, or discussion is gone is refused, a database deleted without its block is refused because it returns through that block, a descendant that no longer fits (a property value whose property is gone, a relation to a page that stayed deleted) is left out, and Discard always closes the entry. Notes text merging is later work.
- Distraction block events replicate with the Focus run they happened in: an event without a run publishes at once, an event of a run publishes in the seal that closes the run (or right away when the run is already closed), and deleting a run deletes its block events on every device. Events and their single rule snapshot are written once and never change, and an event names a segment only together with its run. No process other than the app writes the vault; the native messaging host writes the spool only, and the app moves spooled block events into the vault.
- Chat conversations, channels, memberships, AI channel memberships, and working folder grants replicate with Chat identity and policy, and a concurrent removal, revocation, or narrowing always wins over a concurrent widening, so sync never restores access a device took away; the rules are owned by [Chat](schema/chat.md#access-profiles-and-authorization-revisions). A post written while its device was offline can take an order key below another device's read cursor, and that device then counts it as read. Message attachments travel with their revision as owned rows and their files as the `chat/attachments` asset class; scheduled message attachments stay with their scheduled message until it replicates. Chat rows are editable on every linked device: participant and teammate profiles, channel details, and message text surface conflicts, and a deleted Chat row is not restored, not even with its project, so its recovery entries can only be discarded. A recovery entry lists the text of rows of other domains that were written unseen by the deletion and that restoring it does not bring back, such as posts written offline in a deleted project, so they can be copied first. Execution and its approvals stay on the device that runs the work.
- Every device opens its vault read-write; linking never makes a vault read-only.
- One process at a time opens a vault, because two processes would each run the engine on one database. Before its first pool connects, a process takes an exclusive advisory lock on `vault.lock` in the vault root and keeps it until it switches vaults or exits; another Ganbaru app, such as a development build pointed at the same folder, is refused with a localized error. A replacement locks the staged vault before the swap and releases the old lock after it, so the fence never lapses. A file system that refuses locks opens the vault anyway, and Data settings warn that another app cannot be detected there. Backups and snapshots never carry `vault.lock`.
- Pairing and every copy check the migration set, so a device whose schema differs cannot link or take a copy until both devices run the same app version.
- Link status reports whether the device is linked, the pinned coordinator, and whether a snapshot bootstrap is required or running.
- Chat behavior preferences (`chat.behavior.*`) are portable preferences and replicate with them. Chat provider instances, remembered composer selections, working folder provider preferences, and panel sizes live in the device preference file, so they, like every device preference, never travel.

### Capture and sealing

- Capture triggers, rendered from the manifest and verified against it by a conformance test, record which rows and field groups changed in the same transaction as the domain write. Imports, restores, background jobs, and every command are covered without per-command code.
- Value guard triggers enforce operation bounds on every local write, so any locally valid row seals into a valid operation. Published row keys are never reused: a deleted key cannot be created again.
- The sync service seals pending captures into signed operations from current row values after a short debounce, before every exchange, and before snapshot preparation. Applying remote operations first seals the captures of the rows they touch, and every capture other than a held delete in a touched table whose unique, tree, or acyclic edge constraint reads several rows, because repairs read merge state only. One seal transaction, including a seal inside an apply, takes at most 256 operations of at most 16 changes each and 1 MiB of changes, and sealing continues at once while captures remain. One apply transaction takes at most 16 operations, and no further operation once the operations it took carry 16 changes, so a receiver applies a large seal over several transactions that each stay within the apply budget. An apply whose seal would exceed that applies nothing; the service seals in batches and retries the apply while the captures shrink. Changes that hold only whole seal first, in operations filled to the wire limits: writes and deletes in constrained tables, cascaded deletions with their root, a published parent with its `published_with` children (a closed Focus run with its segments and run events), the changes they depend on, and repairs. Their operations form one apply group, flagged in each operation header (operation format version 4): a receiver stores the group without applying any of it until every operation is stored, then applies it in one transaction past its caps, because the repairs it seals at the end of each transaction must never see a create before the change that frees its unique value, a task nested before its parent moved, or a deleted root whose cascaded rows are still live. A group ends at its 64th operation or at the operation whose bytes reach 1 MiB whatever its flags say, so every receiver splits a larger set at the same place, and a writer that flags every operation holds back only its own later operations. A larger set (a dense Music library refresh of 6,000 items spans about 1.2 MiB in 9 operations) applies as a chain of such groups: a receiver applies no group of a chain until the whole chain is stored and closed (at an operation that does not continue, before its writer's cutoff or an excluded or invalid operation, or at its 256th operation), then applies its groups in consecutive transactions. Between two groups of a chain, a receiver that can seal defers every repair and lists the rows it materialized as stale, across a restart too, so a state between two groups of one edit never becomes a repair; after the last group, each transaction takes back at most 4,096 of those rows, plans them with the rows that reference them, and seals their repairs, and a seal continues while rows remain. A receiver that can seal starts one chain at a time, and only once the rows the previous one deferred were taken back, so repairs wait for at most one chain and every deferral ends. Of the chains that could start, the one whose last operation the receiver stored first starts, by a per-space storage order that a wall clock step cannot reorder, so a paired writer that keeps sending chains with low clocks cannot keep another writer's chain from starting. A chain that never closes applies nothing and holds back only its writer, and a hold for a newer manifest keeps the chain waiting. One transaction for the whole set would instead take about a minute at the bounds, at roughly 1 ms per change. See [apply groups](../algorithms/sync/README.md#model). A captured group equal to its uncontested winner is not sealed again, and merge state keeps a winning value only once, in the domain row, when that row holds it. Saves never wait for sealing or the network.
- When a table starts to replicate, vault open seeds it before the sync service starts: every existing row that satisfies its [publication predicate](../algorithms/sync/README.md#publication) is captured once as a create, and the table is recorded so later opens skip it.
- A local delete on a table that holds deletes can stay unsealed for at most 10 seconds so domain Undo can restore the row; see [deletion holds](../algorithms/sync/README.md#deletion-holds).
- Sealing runs only while the vault is linked and a writer exists. A standalone vault keeps coalesced captures, at most one per changed row, and seals them when it first links.
- A process runs one sync pass at a time, whether the app service, a headless pass, or the seal before a vault transition runs it. A headless pass needs no Tauri runtime: it seals, exchanges, applies, and moves managed assets, then returns without a long poll. When the app service of the same process is running, the headless pass asks it for a pass and waits up to 60 seconds instead of running a second one. On Android, background work calls it through a native entry and repeats it at most four times while the exchange reports more to move.

### Writers

- Every installation signs with its own Ed25519 writer key, certified by its installation device key (certificate version 2). The certificate binds the writer key, device key, device id, and creation time; a replica accepts it only while the authorization log enrolls that device key and has not removed it. A writer's first operation carries its certificate, so certificates travel with the log.
- Desktop keeps writer keys in the operating-system credential store. Android keeps them, the person key, and the device linking TLS key in app-private files excluded from backup and device transfer, each sealed with AES-256-GCM under a non-exportable Android Keystore key (one per vault for sync and person keys, one per device for the linking key) and bound to the vault and key it holds. Android never stores sync or person keys unsealed: when the Keystore is temporarily unusable the key is not written and the pass retries. An unsealed key file found at startup unlinks a linked device first, since it may have been copied, and is then deleted. The linking key is created in the private pairing state file and moves into its sealed file on first use; it stays in the pairing file while the Keystore is unusable. Only the bridge reporting a sealed file that can no longer be opened (its Keystore key was lost or permanently invalidated, or the file is damaged) counts as a loss, never error text (the pairing store matches only its own local key store errors, which carry no remote content), and only after a throwaway Keystore key seals and opens, so an unusable Keystore is retried rather than read as a loss. A loss stops counting once its Keystore key seals or opens again or, for the linking key, once its file is removed. A device revoked by its coordinator counts as unlinked, so a loss only removes that vault's keys. A linked device then unlinks and records the reason in the pairing state until it links again, but only when it lost its linking key or the keys of a vault it is linked for; the keys of another vault are removed without unlinking. The key files of the affected vault and that vault's Keystore key are removed, and so are the linking key file and its Keystore key when the linking key was lost on a linked device; other vaults keep their keys. An unlinked device whose linking key is lost creates a fresh linking identity on its own. Writer keys are never recovered, so the next link enrolls a fresh writer.
- A device-local writer record holds a sequence reservation made durable before signing and the last committed sequence. At service start and after every database replacement, the record is checked against the operation log. A restored database, a database copied from another installation, or a lost key retires the writer and creates a successor, so one installation never signs a sequence twice. A record whose writer ids are not in the canonical form this installation writes is refused before any key is read or removed.
- A full-disk clone copies the key itself, so two machines can sign the same sequence. Two signed operations of one writer at one sequence are fork evidence when both decode and neither claims an authorization revision below the shared operation before them, so a fork never freezes at a revision it cannot prove: every replica that receives the pair stores it, forwards it, keeps the writer's chain through the shared prefix, and refuses anything past it. Every replica except the writer's own device excludes both branches, undoing applied effects and restoring the displaced versions as a removal does, but leaves no late changes. Each installation of the device keeps its own branch, rotates to a successor writer, and re-seals the branch under it, so both histories survive; an installation destroyed before it re-seals loses its branch. The anchor, and a member once the anchor confirmed storing a branch, retain nothing that branch displaced, so its exclusion can leave the branch value with no version behind it. The anchor therefore re-seals, with its own writer, the current value of every live group the branch it stored wrote, and every replica converges to the anchor's state whether or not either installation ever re-seals; the exclusion itself never reverts. A fork of a writer of the anchor device freezes the anchor epoch at that writer's last authorization record below the fork: the anchor re-seals only domain changes, and authorization continues only after a handover.
- Each installation creates its Ed25519 device key before pairing and sends it in the pairing request. Desktop keeps it in the operating-system credential store and Android in app-private files. A device seals nothing until the authorization log it has received enrolls it; its captures stay pending and seal on a later pass.
- Each installation also keeps a static X25519 device encryption key per vault (desktop credential store account `device-encryption-key:{vault_id}`, Android sealed app-private file) and publishes its public half in a `device key` entry signed by its device key; the anchor sequences one only for an enrolled device that is neither removed nor quarantined. The anchor generates key epoch 1 when it sequences the first `recovery key` entry, and every later removal, recovery change, or kit `set role` in a space with a key epoch is sealed in one transaction together with the `key epoch` entry that follows it: a fresh random space key sealed by HPKE to every live device with a published key and to the recovery key, plus the previous epoch key wrapped with XChaCha20-Poly1305 under the new one. A removed device receives no envelope, so it opens nothing sealed after its removal. A removal in such a space takes authority effect only once the stored set holds that `key epoch` at the next revision; until then it is pending, which is neither a fork nor a freeze, and the anchor that holds the current epoch key completes it. While a removal is pending the anchor sequences only that `key epoch` and its own `device key`, so an anchor reached by handover before it published its key can still complete the removal. An anchor that cannot open the current epoch (through its own envelope or the recovery envelope) refuses to rotate rather than seal an epoch nobody can open. Before any key epoch exists, a removal applies alone. Plaintext epoch keys stay in memory only. Relay records and relay asset chunks are sealed with subkeys of an epoch key and opened only with an epoch key from the device's own envelope; [Sync encryption](../architecture/decisions/sync-encryption.md#relay-formats) owns their formats.
- Sealing waits while the person key is unavailable, status reports waiting for identity, and the key is requested from the coordinator as described in [Contacts and contact requests](#contacts-and-contact-requests).
- The coordinator founds the space on its first linked pass: the person key signs a charter naming the coordinator as anchor with its device key, admin key, and recovery commitment. The anchor's device and admin keys live in the operating-system credential store and survive Reset sync state, so a new charter names the same keys. The pairing response carries the charter and the person public key over the pinned TLS session; the new device verifies and pins both and installs that charter on its first pass, refusing any other. The anchor seals an `enroll` entry when it approves a pairing, before it replies, and a `remove` entry when a device is unlinked. Each pass also compares linked devices with the selected log and queues an admin-signed enroll or remove proposal for each difference, so a crash between pairing and sequencing is repaired on the next pass. Proposals wait in a device-local outbox (bounded to 256 proposals, signature-checked on load, deduplicated by hash) until the selected chain holds them or the anchor rejects them finally; the anchor sequences its own outbox each pass, and an admin device sends its proposals to the hub with `SyncPropose`, which the anchor's pass sequences before answering. Before sealing each entry the anchor records its revision and entry hash in the device-local writer record, and successors carry that high-water mark. A removal revokes the device's writers at the cutoff the entry records: what the anchor had stored of each writer, or nothing for a writer it never saw. Every replica except the removed device stores up to 1,024 operations per writer past the cutoff, holds them as excluded, and forwards them; it refuses later ones, except up to 1,024 more authorization entries right after them, which stay evidence for chain selection. Applying a removal undoes the merge effects of excluded operations it already applied and restores the versions they superseded, which a member keeps until the anchor confirms storing the superseding operation, so the result equals never having applied them. Operations of other writers stay applied. Excluded operations derive late changes the same way on every replica; an admin restores or discards each through a `resolve late` entry, and a restore writes the late values as ordinary changes. Authorization entries that excluded operations carry still count for chain selection, so competing chains settle the same in any arrival order. A device that a newly selected chain no longer enrolls keeps its applied operations, and its new ones wait until an enrollment is selected again. In an epoch a handover opened, members may have released versions an earlier anchor confirmed, so the anchor re-seals the current value of every live group excluded operations wrote, as it does for a fork; it records each such restatement locally so that restoring a late change does not treat it as a newer edit. Only the anchor holds that record, so a restore by another admin may count the restatement as a newer edit and keep the anchor's value for that group instead of the late value. In the charter epoch no earlier anchor exists and nothing is re-sealed. A replica that applied operations while it was the anchor, and so released the versions they displaced, records per writer the highest sequence it applied and, when it later excludes those operations even as a member, re-seals and records the current value of every live group they wrote in the same way. A row whose every creating operation is excluded stays hidden, with any honest changes kept, until an operation creates it again.
- A linked desktop sends its admin public key at pairing, so the coordinator can propose making it an admin. An admin desktop that a complete exchange left current with the coordinator can take the anchor: it seals a handover to itself, opening the next epoch, with the per-writer maximum of its own stored vector and what the coordinator reported storing, less the writers of devices it quarantined, as the old anchor vector, and refuses removals as `catching_up` until it knows every writer that vector names. An outbox keeps a proposal the chain holds until a later epoch still holds it, so a proposal the old anchor sequenced after the new anchor's starting revision, which the handover supersedes, waits again and reaches the new anchor. The coordinator keeps the hub, pairing, and first copies, so members keep dialing it and learn the anchor from the log; it holds the proposals it receives for the anchor in its outbox, and the anchor collects them with `SyncForward` and reports final rejections in its next request. Members also reach a new anchor directly through [LAN peer exchange](#exchange), while the coordinator pin stays. A device that forked in an earlier epoch is not frozen when it becomes anchor.
- When the anchor is lost, a forced handover needs no answer from it. A linked admin desktop seals a handover to itself with its admin key, frozen or not; a linked desktop that is not an admin derives the recovery admin key from a kit code in memory and seals the handover with it, then seals, right after it, a recovery-signed `set role` making itself an admin with its own admin key. The engine accepts a handover to a desktop that is not an admin only when the recovery key signed it, and the new anchor must still be a live enrolled desktop, so a kit cannot make an unenrolled computer the anchor. A forced handover carries no old anchor vector, so entries only the lost anchor had sequenced lose to the new epoch and their proposals return from outboxes. Only a linked device forces a handover; the coordinator keeps its own anchor path. Quarantining the lost anchor with it adds the old anchor to this installation's quarantine and proposes its removal to the new anchor. A kit forced handover continues from the highest ranked entry where the forcing desktop is still live, which may lie below a stolen anchor's removal or demotion of it, and the new anchor then removes the old one. Before sealing anything, a forced handover is refused unless, at the entry it continues from, the space has no key epoch yet, the log names this desktop's encryption key, or, for a kit, the log names the kit's recovery encryption key, so a printed kit replaced by a newer recovery key cannot leave an anchor that opens no epoch; the user is told to use the newer code or to sync the desktop first.
- Anchor handover follows one authority state computed from every stored entry before a chain is selected; nothing read from the selected chain changes validity, enrollment, removal, holds, pins, or contests afterwards, so every replica selects the same head in any arrival order and under any writer ids. A handover is a take: its target signs it with the admin key it holds. Only the printed kit's key (the kit lineage key, which only a rotation it signs itself replaces) may hand the anchor to any live enrolled desktop, and an installed recovery key may do the same only while its installer is the anchor or in the epoch its own handover opened. Only the anchor installs a recovery key, which is how Settings makes one; it never replaces the kit lineage key. A kit or recovery handover demotes every other admin to member, which disarms admins a thief planted. Two handovers out of one epoch, or a take that the epoch's own continuation objects to by removing or demoting its signer or target, contest the epoch. A single unobjected take stands, also beside a writer fork of the old anchor, whose freeze is waived on the take's ancestry. A contest resolves when a contestant signs a `yield` (kind 5) naming the other handover, or the anchor withdraws its objection the same way; with crossed yields the lowest hash wins. A kit handover pins its whole ancestry and wins every contest on it, and a kit rotation that a leaked older kit contests is refused. Otherwise the epoch freezes at the common ancestor of the contending handovers, lowered below a writer fork of its anchor when one lies under it: entries past that point and beside it take no effect, the anchor stops sequencing, and only a yield or the kit continues. A device that any branch of a frozen epoch removes is held for data: its row changes are stored but neither applied nor dropped, it is served authorization records only and no managed assets, and once the contest resolves the removal cutoff of the winning branch decides its held changes. Chains are ranked by kit handover count, epoch, epoch root, revision, and hash. Authority reads only the record store: every authorization record, writer certificate, and fork twin a replica ever received, stored by content hash and never refused or deleted, so the selected head is a function of the stored set alone. A record counts only when its writer has a certificate naming the record's anchor device under the key that device's enrollment names at the record's parent; a writer certified under any other key, even one the old anchor holds, carries no authority, and a device id is enrolled once for the life of the log, so its key never changes: a removed device id is never enrolled again, and a returning device enrolls under a new id. Two records of one writer at one sequence lower the freeze of each epoch instance that writer carries to its last record there below the fork, and its records past the fork count only as ancestors of records other writers carry. A contestant seals its yield, and the anchor its objection (a removal of the take's signer or target) or the withdrawal of one, at its own branch head; a writer with fork evidence, or of a removed device, is retired and replaced by a successor its device key certifies before it seals again.
- Known limits of anchor handover: any former admin or former anchor can force one freeze, a denial of service, per kit cycle, but never take over, and a kit use disarms every key whose forks fall into its ancestry. A planted admin's take while the anchor is offline stands until the anchor returns and objects. Planted members stay enrolled, with no authority, until removed. The printed kit is the only key that rotates the kit and the only tiebreaker: losing the paper loses kit recovery for good, and a recovery key made in Settings recovers a lost single admin only when uncontested and never settles a contest. A held device learns the discovery keys in the authorization records it is served, so it can recognize the vault's LAN advertisements until a later rotation it is not served; its data sessions stay closed. Row changes a replica applied before a contest became known stay applied until the contest resolves. A frozen contest blocks enrollment, removal, and role changes for the whole vault until a yield or the kit. Any holder of a once-valid admin key, a removed admin included, can enroll puppets on its own fabricated branches and grow the record store without bound; authority is not affected, since puppets contest by the ordinary rules and the kit resolves them, but the kit cannot shrink the store, and storage is reclaimed only by founding the space again. A planted live member, or an admin before its removal, keeps the normal exchange budget and can push every replica to the storage backstop in about 45 minutes per link; that forces the kit and a user action before data sync resumes, a denial of service with recovery, not a takeover. Removed and held devices are served authorization records, which carry the discovery keys in plaintext. Junk can delay honest records but not reorder the classes below, and walk CPU grows with the store up to the backstop. An attacker can plant refetch hashes no peer can satisfy, one pending envelope of transport each, which the request list keeps asking for with backoff; they count toward the backstop like pending junk. The key of the anchor at the local selected head, such as a puppet admin a stolen anchor enrolled, can carry a kit record that continues from that head once per kit proposal in total outside the epoch instances kit handovers opened, however many epochs it opens by taking the anchor from itself, and so draw on the kit reserve that much; a record it sends at the head ahead of the honest one takes that slot from it. The selected head moves, so an honest kit record that is neither an enrollment nor a handover and lies outside an epoch instance a kit handover opened loses kit class once the head passes it, and then travels in its sender's class, which only delays it. A writer can store two data operations at one sequence as fork evidence; only its lowest such pair is kept from a batch, so pairs it seals at ever lower sequences grow the store only within the ingress budgets and the backstop.
- The anchor's writer record names the charter, epoch, revision, and entry hash of the last entry it reserved, and every sequencing step records the writer's committed sequence. A record one revision ahead of the selected head is a rolled back seal unless the writer lost part of its committed chain; a record further ahead or in a later epoch means the database was restored. A restored anchor, the coordinator or a linked desktop, moves to a successor writer before it seals anything, so no operation reuses a sequence of the entries members still hold. It answers proposals `not_anchor` and waits up to ten minutes (not at all without linked devices) for members to push back the log, then seals a handover to itself with no old anchor vector, so entries only it had seen lose to the new epoch and their proposals return from outboxes. A log holding only its charter cannot be continued; content keeps syncing and linking the devices again founds anew. A database without a charter beside a record that names a high-water lost the log, to a backup from before founding or to Reset local data, so the coordinator refuses to found a new charter over it until a database holding the log is restored or Reset sync state drops the high-water. A record of an earlier epoch than the selected head is current, because a handover sealed elsewhere superseded what it sealed later.
- A kit code derives, through distinct HKDF labels, both the recovery admin key and the recovery X25519 key that key epochs seal to; the seed is held zeroized and only in memory while a kit flow runs. A desktop vault that is not linked yet can create its kit from the device linking panel: the seed waits in the credential store and the vault database keeps the two public keys (`sync_recovery_kit`), and the first link founds the charter with them. Founding without a stored kit generates a seed, or reuses one still waiting. The seed stays in the credential store until the user confirms saving the kit by typing its last group, compared in constant time, then is deleted; a later charter without stored keys gets a fresh kit, and a kit the log does not name yet cannot be confirmed on a linked vault. While the seed waits, the kit state command returns its code and QR on every call, so the code stays readable until the user confirms it. The anchor desktop can make a recovery key, which Settings calls a recovery key rather than the kit and which leaves the printed kit as the tiebreaker: a `recovery key` entry naming the new encryption key is proposed before the `set role` naming the new admin key, so both rotations it starts (one for each entry) seal to the new key and the replaced key opens no later epoch, and both proposals enter the outbox before the new seed is stored, so a full outbox or a failed store changes nothing, and a waiting key that the log names or whose proposal still waits is never overwritten. Only the anchor makes one; other desktops are told an admin computer must. Using the kit on an enrolled desktop derives the key in memory and proposes making that desktop an admin, so it can then take the anchor.
- Quarantine is a device-local list kept beside the outbox, across Reset sync state. Hub and client store nothing from writers of a quarantined device and keep paging past them, a client remembers what its pulls turned away until the list changes, the listener refuses a quarantined device after the TLS handshake, and a device never exchanges with a coordinator it quarantined. An unreadable list is reported and the listener keeps the last list it read, so a damaged file never locks out every linked device. On an admin desktop quarantining also proposes removing the device. Lifting the quarantine lets the operations arrive again; quarantine never excludes anything.
- A space admits at most 64 writers per device over its lifetime and 4096 in total, the bound of a wire version vector. Honest devices mint a successor only after a restore, a copied database, a lost key, or a clone, so the caps sit far above real use. A genesis past either cap is refused as `writer_limit`, the device keeps its changes locally, and status explains the limit.
- An operation lists at most 256 dependencies. When more writers advanced since a writer last sealed, sealing first emits operations without changes that only advance dependencies, 256 at a time in writer order, so sealing never stops because of how many writers exist.
- Every linked installation seals its writer's genesis on its first sync pass after its enrollment arrives, not only when it first captures a change, so the coordinator knows the writer and can count what it applied. A device whose person key is not released yet has no writer.
- Every operation acknowledges its causal context. A signed acknowledgement (kind `3`, no changes and an empty body) is sealed at the end of a pass when the writer applied a non-acknowledgement operation of another writer beyond its own last context, at most once per 10 minutes, and as a keepalive when the writer's newest operation is older than 7 days. Acknowledgements never trigger acknowledgements, so the traffic settles. Kind `3` keeps operation format 2: older builds hold it as `newer_format`, and protocol 11 and later refuse them before any exchange anyway.
- Operation format 3 defines kind `4`, an authorization log entry for the [anchored authority](#topology-and-authority): an admin-signed proposal (enroll, remove, set role, resolve late rows, or handover) plus what the anchor adds when ordering it, chained by entry hash from a space charter the person key signs. The signed header carries the entry hash and the revision before the entry, so the body may hold a handover's full version vector. Entry kinds the build does not know round trip unchanged. Writer certificates version 2, vouched for by a device key instead of the person key, and recovery kit codes that derive the recovery admin key are defined too. The anchor produces kind `4` entries for founding, enrollment, and removal, the engine lets the admin desktop a handover names seal it as the first entry of the next epoch from the head it continues, frozen or not, and lets a handover the recovery key signed name any live enrolled desktop, and every replica verifies and applies the chain. Kind `2` is unassigned and version 1 certificates are refused.

### Exchange

The coordinator desktop is the main hub. Sync requests, including content-addressed asset transfers, share the existing mutual TLS listener under handoff protocol 16, with one request and one response per connection. Every request names the vault and device and is authenticated as an enrolled peer before it reaches the hub. The personal space id derives from the vault id.

Before the operation lanes, every session exchanges authorization records in pages (`SyncRecords`, `SyncRecordGet`, `SyncRecordPush`) with every paired peer, including removed, held, and not yet enrolled devices, which are served nothing else; quarantined devices get nothing. Pages serve, in order, kit records, yields and objections, ancestors and certificates a peer named as missing, records of live devices, and the rest, with a share of each page kept for the rest. A record the kit key signs is a kit record only when its carrier writer's certificate names the device key the signed content or the local selected chain fixes: the key an enrollment enrolls, the key of a handover's target, or, for any other kit record, the key of the anchor at its parent when that parent is the local selected head or lies inside an epoch instance a kit handover opened; otherwise it travels in its sender's class, which only delays it. Each kit record spends its entry, its parent and proposal, and its proposal once per epoch instance a kit handover opened or once in total outside them, read from every verified stored record whether or not it is a node, so a spent slot stays spent. The slot outside them goes to the first stored record that binds there, or else to the first one a batch sends, so a rewrap at an older parent does not take it from a record at the head that arrived first. An envelope that is neither a record nor a certificate is kept only as a fork twin of a verified stored envelope at its writer and sequence, as one of two such envelopes of one batch that both verify under the writer's certified key (only the writer's lowest such pair, and only below every pair the store holds of it; a store keeps the two halves of each pair next to each other in its order, so a page splits at most one pair, and a replica sends the data envelopes a page left unpaired, up to twice the largest operation, again with the next page from the same peer on the same stream, pulled, asked for, or pushed, charging them to that peer's budget again; an empty push admits nothing), or as the envelope such a pair continues from; when a pending twin is purged, evidence kept beside it is purged too. A replica keeps asking every peer for the parents and certificates its stored records reference, with doubling backoff per peer up to an hour that a new or reconnected peer resets for itself only; keys in backoff do not count toward the 256 keys of one request. Requests to each peer rotate through the wanted keys and refetch hashes, resuming after the last key the peer answered, so every key is asked within a number of answered requests bounded by their count. When they do not fit one request, the ancestors of kit records that took kit class and of yields whose signer is an admin at their parent and at the local selected head fill up to half of it first. An envelope whose writer has no stored certificate waits pending; when the certificate arrives, a pending copy it does not verify is deleted and its hash stays on the request list until a verified copy is stored, since the envelope hash leaves out the signature and an honest copy that arrived while the bad one was held was dropped. A peer that is removed, held, or not live at the local head may send 64 KiB and 64 envelopes per 10 s, a live peer 8 MiB and 2,048. A page that starts within the budget is taken whole, and its overspend is debt later windows repay. The storage backstop stops the operation lanes once records take 2 GiB or 2,097,152 envelopes, or free disk space falls below 512 MiB; records of the first three classes keep arriving from a 256 MiB reserve, 64 MiB of it only for kit records and the ancestors and certificates they reach, and everything stops below 128 MiB free or once a kit record no longer fits the reserve. Every limit restarts when the vault changes. Settings shows the stop with a resume action, and alerts when one device's records pass 64 MiB, all records pass 1 GiB, or a writer has two certificates or a fork. Status: the backstop bounds, alerts, backoff, request rotation, and kept unpaired data envelopes are device-local and reset on restart. Free space on the vault volume is read on Linux and Android; on Windows and other platforms only the byte and envelope bounds apply. No preference raises the bound or lowers the low budget (its floor is 16 KiB and 16 envelopes).

Members also exchange with each other over LAN peer exchange:

- Every linked member desktop runs a sync listener on the coordinator port while sync runs in the active vault, and stops it when sync stops or the desktop starts coordinating. A linked phone runs the same listener only while the app is in the foreground: the app pass starts it after the frontend reports the app visible, and hiding the app stops it before the report returns. A phone listener binds IPv4 only, reports only the source address of its default route, never advertises, and never answers `SyncPropose`, because a phone never anchors; WorkManager background passes only dial. It serves only sync requests and, on a desktop, vault copies (see [Bootstrap, assets, backup, and compaction](#bootstrap-assets-backup-and-compaction)), and refuses pairing, other handoff, and contact requests with a typed code; only the listener of the device the log names as anchor answers `SyncPropose`, and no member listener answers `SyncForward`. Pairing stays with the coordinator, because a pairing link is also the link that serves the first copy: it proposes the `enroll`, and the anchor sequences it like any proposal. A proposal is settled only by the anchor: a sequencing appears as a signed log entry, and a final rejection is unsigned and trusted only from a link pinned to the anchor's enrollment or from a coordinator that handed the anchor over, which relays only the rejections the device the log names as anchor reported. Mutual TLS accepts exactly the certificate fingerprints of devices the local selected authorization log enrolled and did not remove and this installation did not quarantine. The handshake may use an admission read up to 5 seconds earlier, so connections that never authenticate cannot force a log read each, and every authenticated connection is checked again against a fresh read. Every refusal is typed and logged without keys or certificates.
- `SyncHello` carries the endpoints the sender listens on, and `SyncState` reports up to 32 member endpoints with their device and observation time. Each device keeps them in a device-local peer book under its app config directory, bounded, written atomically, validated on read, and pruned to the live members of the log, and rewritten only when its content changes; a damaged book starts over, since it only holds address hints. A reported observation time is clamped to when the report arrived, and endpoints a member announced in its own hello outrank reported ones when the bounds evict, so no member can push real endpoints out with future times.
- After its coordinator exchange, or when the coordinator is unreachable, a pass exchanges with other members, at most three at once on a desktop and two on a phone, not counting the coordinator: the anchor first while reachable and not the coordinator, then members found on the LAN, then the peer book's newest endpoints. A member desktop advertises its listener over DNS-SD under its own hourly member tag, with the current discovery key only, while the listener runs; before planning, a desktop browses for the tags of the live members' enrolled certificates under the current key and the replaced one, at most once a minute and for at most 3 seconds, and keeps what it finds in memory for 10 minutes. A phone neither advertises nor browses for members. Each member is dialed pinned to the certificate its enrollment recorded. The long poll goes to the coordinator, or, while the coordinator is away, to a non-coordinator anchor that answered a complete exchange in the same pass, held at most for the fallback interval. A coordinator exchange that fails, including while moving managed assets, still lets the pass exchange with members. Pages follow arrival order, so the anchor's authorization entries reach a peer before the geneses they enroll; what a member refuses, such as an operation of a writer it does not know yet, is retried on the next pass and never becomes this device's status.
- After a handover the log names the new anchor. Each device keeps a device-local anchor pin, separate from the coordinator pin, with the anchor's device id and the certificate fingerprint its enrollment recorded; every pass rewrites it from the selected log, which always wins, and it stands in only while the log cannot be read. The pass dials the anchor through the peer book, pinned to that fingerprint, without relinking and without changing the coordinator pin or its generation. What the anchor reports storing in that direct exchange records anchor marks, so displaced versions it holds are released, and once it answered, the pass sends waiting proposals to it directly instead of to the coordinator, also while the coordinator is away. A member listener relays the geneses of other members it stores, which the receiving engine admits only for devices the log enrolled.

| `SyncPush` | `SyncPushResult` | Upload operations the hub lacks, stored up to the first refusal |
| `SyncPull` | `SyncOps` | Download operations the device lacks, in per-writer order |
| `SyncWait` | `SyncState` | Long poll that returns when the hub stores more, when a newer wait from the same device arrives, or before the control timeout |
| `SyncHashes` | `SyncHashList` | Consecutive operation hashes of one writer, to locate a fork point |
| `SyncForkEvidence` | `SyncForkPair` | Offer up to two operations of a forked writer and receive the fork evidence the hub stores; `SyncState` lists each forked writer with its fork sequence |
| `SyncAssetQuery` | `SyncAssetPresence` | Which referenced files, by class, digest, type, and size, the hub holds |
| `SyncAssetPut` | `SyncAssetReceived` | Upload one chunk of a file the hub lacks; the answer says where the next chunk starts |
| `SyncAssetGet` | `SyncAssetChunk` | Download one chunk of a file the hub holds |

- Operations travel as base64url pages sized to fit the 1 MiB control frame; a page always holds at least one operation of the maximum size, and building one reads the pending operations of each writer in small chunks, so a peer that knows nothing cannot make every page read the whole log. One exchange moves a bounded amount of operations in each direction and applies what it pulled before the next exchange continues, so a long backlog never waits unapplied in full.
- Push refusals are `gap`, `fork`, `revoked`, `invalid`, `unknown_writer`, `newer_format`, and `writer_limit`. The hub accepts a writer's genesis only from the device its certificate names, and other operations only for writers whose genesis it already holds.
- The hub only stores and serves. Its own sync service applies what it stored, so apply runs in one code path on every device. An operation is acknowledged only after it is committed; a hub receipt means delivery, not that another device applied it.
- The coordinator's service pass recomputes stability, the operations every counted device holds, and every `SyncState` reports it as `stable`, never beyond what the hub stores. Counted devices are the anchor and every other device the selected authorization log enrolls, has not removed, and does not find dormant; a device's link time is the stored time of the entry that enrolled it. A device acknowledges the context of the newest operation with a known context of its newest active writer, so a device without an active writer acknowledges nothing and holds stability at nothing. A device is dormant when the coordinator's clock is more than 90 days past the newest receipt of any of its writers' operations, or, without operations, past its link time; receipt time is used so a skewed device clock cannot make others dormant. A device whose enrollment time is unknown is neither counted nor dormant, and Data settings asks to link it again. Dormancy and stability are derived on every pass and never stored, so a returning device counts again at once. Clients keep the last `stable` vector they received.
- Compaction runs at the end of a service pass, in batches of 256 operations within 200 ms, each committed on its own. It empties the bodies of applied change and acknowledgement operations at or below the stable vector, keeping their headers, and first hydrates every row version that still refers to an elided body. A writer's head, genesis, and revocation are never compacted, and a device's own active writer is compacted only up to the head the hub last confirmed. A peer whose knowledge is behind what the hub compacted receives `bootstrap_required` in `SyncState` and in pull refusals, as is a fork inside the compacted range; it still pushes its own operations, but pulls nothing until it receives a fresh copy of the vault. Data settings says so and offers the fresh copy as one confirmed action, never started automatically; the copy is a bootstrap that seals pending captures, carries forward every operation the snapshot lacks, keeps a rollback copy, and keeps this installation's writer when its high-water check passes.
- An operation from a newer format or manifest, or one that fails intrinsic validation, is stored, forwarded, and held with its reason visible in status. Everything causally after it waits until an app update releases it.
- Managed assets travel as files beside the operations that reference them. Each domain declares its asset classes in the manifest, and a class fixes the vault directory of its files and their byte bound, at most 64 MiB; Quick note images and Music artwork (10 MiB), profile pictures, project icons, and Notes page icons (3 MiB), Notes page covers (8 MiB), and Notes files and Chat attachments (50 MiB) are the declared classes; Music declares its class before any of its tables replicate. A wire asset names its class, and a receiver refuses a class it does not register, a size above the class bound, and, on the hub, an upload for a domain replicas cannot write, before any file is created. A client uploads the referenced assets the hub lacks before pushing, so a peer that pulls a reference finds the file, and downloads the assets it lacks after applying. Chunks fit the control frame, each direction moves a bounded number of bytes per pass, and an interrupted upload resumes from the offset the hub reports. Received chunks stream into a temporary file beside the target while the digest is computed, so one chunk at a time is held in memory; the file is renamed into place only when the digest, size, and any check of its class (Quick note images, Music artwork, profile pictures, project icons, and Notes page icons and covers must be a supported image of the referenced type, and a Notes file with a previewable content type must carry its signature, and a Chat attachment must be a supported image or UTF-8 text of its type) pass, and a refused or abandoned transfer removes it. Temporary files that a stopped process leaves are removed when the asset store next opens, once they are older than any transfer could still be writing. A note can therefore arrive before its images; a file the hub does not hold yet is asked for again after the next pull that brings operations, or after a short delay. Presence is checked by file type and size, so a damaged file of the right size is not fetched again until it is replaced locally; verified bytes that arrive for it replace it.
- Clients exchange after debounced commits, on start, on Android resume, on Sync now, and on a fallback interval, and keep a long poll open while linked. Failures back off up to five minutes, and changes queue locally while the hub is unreachable. Outside the foreground, Android exchanges through WorkManager: a 15 minute periodic pass while linked, a one-time pass when the default network or its addresses change while the process runs, and a one-time pass when the app leaves the foreground with changes waiting. Work waiting for a network constraint covers network changes after the process ends.

### Carry-forward across replacement

Snapshot copies and backup restore never lose operations:

- The source seals pending captures under the write fence before preparing a snapshot. Snapshots carry the full operation log and engine state; the copy drops pending captures, which stay in the source and seal there, empties local tables, and resets local columns to their materialization defaults.
- Before activation replaces the vault, the receiver seals its own captures under the same fence and exports every operation it stores that the staged database lacks into a bounded device-local bundle. Captures that cannot be sealed refuse the replacement with an error that names unsealed local changes. It also copies the managed asset files of every registered class that the staged vault lacks and whose bytes match their digest, so assets not yet uploaded survive with the operations that reference them.
- The bundle is stored and applied in the staged database, then deleted. The receiver's local tables and columns are then copied from its live database into the staged one, and rows whose references the merged state no longer holds follow their declared delete action; any other action refuses the replacement. All of this runs before the staged database is renamed into place, so a failure at any step leaves the current vault in use and a retry repeats it. A bundle a failure leaves behind is included in the next replacement and imported at service start before the writer check. A bundle that is not a regular file within the bundle limit is refused before it is read, and import skips operations already stored.
- After an in-place backup restore, the writer check creates a successor writer, and captures in the restored database seal under it. An in-place restore carries nothing forward: it is allowed only while no other device is enrolled, so no operation exists elsewhere, and the replaced database stays in `.database-rollbacks/`. An independent copy starts a new space and carries nothing.

### Conflicts, recovery, and controls

- Valid operations converge to identical replicated state on every replica regardless of delivery order. Causality decides supersession; clocks only choose the displayed value among concurrent versions. The merge rules and worked examples are owned by [Sync merge rules](../algorithms/sync/README.md).
- A device whose merged edits carry clocks more than five minutes ahead of local time is named in sync status, with a prompt to check its date and time, because those edits win concurrent changes until the clocks agree.
- Surfaced groups (Quick note title, body, and images) keep concurrent versions as a conflict with a resolution. Other groups resolve silently and deterministically. A deletion concurrent with edits keeps those edits as a recovery entry that can be restored as a new row or discarded. The entry is rooted at the topmost deleted row, carries its cascade descendants, and counts them.
- A row removed under a derived key is never offered for recovery: its replacement stays live in the merged state, so adding the same key again is the recovery path.
- Resolutions, restores, and discards are ordinary writes, so they replicate and converge like any edit. A restore runs the domain restorer in one transaction and closes the entry in a second, so a failed restore leaves the entry open.
- Presentation is keyed by replicated table name. Status reports conflicted rows and recovery entries per table, the app registers one restorer for every table that can root an entry and refuses restore and discard for any other, and the frontend registry gives each domain its conflict line, recovery labels, and changed notice, with neutral sync copy for anything a domain does not provide. Quick notes and themes register conflict and recovery copy; preferences use neutral copy.
- The Quick notes trash purge is a deletion like any other, so an edit made elsewhere to a purged note becomes a recovery entry.
- Data settings show the sync state, role, last exchange, pending and waiting changes, held operations with reasons, conflict counts, and recovery entries, with Sync now and Pause. Pause is device-local, stops exchanges, and keeps sealing.
- Data settings list the enrolled devices with their role (admin or member), the anchor, removed devices, and devices this installation quarantined. Any device can quarantine another live device except the anchor and lift it later; on an admin desktop the dialog says that quarantine also proposes removal, which lifting does not undo once the anchor applies it. Discarding a late change asks for confirmation. An admin desktop can propose removing a device (a linked desktop; the coordinator removes by unlinking), the coordinator can make a member desktop an admin, and a linked admin desktop can take the anchor in a planned handover. Admin controls never appear on members or Android. A removed device shows that it was removed and that copies already on it cannot be erased.
- Proposals wait in an outbox listed in Data settings with their state; a refused proposal shows the anchor's reason. Late changes list what each removed device did to a row, up to as many as the outbox holds with a count of the rest, and an admin desktop keeps or discards each one; keeping applies the late values with the local writer before the decision is proposed.
- An admin desktop shows the recovery kit code it still holds, grouped for reading, until the user confirms saving it by typing its last group, and can print it as a page with its QR code or save it as a plain text file readable only by the current user; printing keeps the code out of browser storage, logs, and the clipboard. The anchor desktop can also make a recovery key, and a desktop that is not an admin is told only an admin computer manages the kit. A desktop that is not an admin can enter a kit code while its last exchange succeeded. Once no pass in the current app run reached the anchor, a linked admin desktop offers to take over the anchor and a linked desktop that is not an admin offers to use a kit to take it over, each with the option to also quarantine the lost anchor and propose its removal, behind a confirmation; the planned handover stays offered, since it still works while the coordinator answers and carries the old anchor vector. Each open contest shows a card with its cause, the anchor, each candidate with how it was signed and who enrolled its target, and the held devices, offering a contestant its yield, the anchor its objection or the withdrawal of one, each behind a confirmation; on desktops the kit form in a contest lets the user pick where the kit continues and review the devices to remove, with flooders and forked writers marked and devices a losing branch removed listed unmarked with who removed them.
- Status counts this device's changes the anchor has not confirmed storing, the age of the oldest, and the superseded versions kept until the anchor confirms what superseded them, and a linked device shows since when the anchor stopped answering. Settings shows these, and once the oldest unconfirmed change is 30 days old suggests taking over the anchor, only on a linked admin desktop that can do so.
- Reset sync state runs only on the coordinator, inside its service pass, from a confirmed Data settings control. It unlinks every device linked for the vault, clears every engine table (including `sync_seeded_tables`) while keeping domain rows, and removes this installation's writer keys, writer record, carry-forward bundle, and proposal outbox. The next pass founds a new charter and republishes every current row through capture seeding; every other device pairs again, because it pinned the old charter. Every proposal names the hash of the charter its log starts from, so the new anchor refuses proposals signed for the cleared log, and the anchor's sequenced high-water is cleared with it. Content a client changed but never sent before the Reset may not come back with that device's carry-forward bundle when it pairs again, because the bundle's operations belong to the cleared log. Vaults whose sync state the current build refuses recover this way. Reset keeps this installation's device key, admin key, any recovery seed still waiting, and the stored kit public keys, so it is not a remedy for keys copied from this computer; a device removed or never linked again loses its place in the new log.

## Target concurrent synchronization

### Architecture

SQLite remains the durable local store. Replicas exchange validated domain operations and immutable assets, never raw database pages, arbitrary SQL, or unclassified configuration. Foreground saves never wait for the network.

Between one person's devices, Notes text replicates per block as one value with surfaced conflicts, independent of block placement and kind. Character-level collaborative text (Rust Yrs with a compatible Yjs editor adapter, binary CRDT state canonical in SQLite and rich-text payloads as projections) is planned with multi-person sharing.

Local network linking works without an account or server. An optional user-hosted Rust relay stores opaque encrypted records for cross-network and asynchronous delivery. Hocuspocus was rejected as the relay because its normal persistence stores server-side Yjs documents, which breaks the encrypted record boundary.

The `ganbaru-sync-contracts`, `ganbaru-sync`, `ganbaru-sync-replica`, and `ganbaru-sync-relay` crates exist. The optional `ganbaru-sync-relay` binary runs in relay mode: a `setup` command prints a one-time code (endpoints, pinned certificate fingerprint, and a token valid for 15 minutes that claims one space), and the server stores sealed records and asset chunks it cannot open, admits devices with the epoch relay access key signed over the TLS session, registers only the next epoch from a holder of the current one, takes admin commands signed by the space admin set with increasing counters, and trims each space by quota and age behind per-writer floors. The relay cannot verify that a registered key is the real next epoch key, so the first registration wins and a wrong one locks the space out of the relay until an admin repairs it with a signed command that sets the current epoch and its key, even downward, and deletes every record and epoch entry above it; confidentiality is unaffected because the relay never holds space keys. Operators can list spaces, revoke unused setup codes while the relay runs, and remove a space only while the relay is stopped (the server holds a lock on its data directory), because a running relay keeps space state in memory. Unauthenticated connections are capped at 64 in total and 4 per source (an IPv4 address or IPv6 /64), and authenticated requests reserve their frame and response bytes from one 32 MiB budget, waiting briefly and then answering busy, so buffer memory stays bounded on a small server. Releases ship static Linux binaries and a container image ([Release distribution](../operations/release/distribution.md#sync-relay)). When the selected server configuration names a relay, every unpaused pass also runs a relay pass: it authenticates with the newest epoch the device holds, registers each newer epoch it opened once the relay holds the chain through the record that opened it, pushes its own sealed records at the current epoch, pulls records it can open (an epoch at or below its credential), and moves asset chunks; pulled bytes are bounded before decoding and reach the store only through the verified operation path. A live admin device keeps the relay's admin set equal to the chain's admin keys after a pull that drained the relay, and repairs a relay epoch whose registered access key differs from the one its own epoch key derives. It repairs an epoch above every epoch its chain names only after a drained pull (nothing left, no refused record, no trimmed range) and only when the relay's record for that epoch fails to authenticate as its anchor-signed key epoch record against the stored verified envelope set; an authentic record means the device lags behind a real rotation. The relay is the one dial exception to LAN-only dialing, and only for the endpoints the server configuration names; release builds refuse loopback relay addresses. Settings shows the last relay pass with records sent and received, files moved and deferred, relay storage, the last time the relay answered, and a typed problem; the undelivered count is this device's own operations the relay does not hold. A live admin desktop adds a relay by pasting its setup code, after an explicit opt-in that states the relay cryptography has not had an external review: it claims the space at the newest epoch key it opened with the chain's admin keys and the recovery key as the relay admin set, then proposes the server configuration; an admin removal proposes an empty configuration first and asks the relay to drop the space as a best effort. Other devices show the server, its reachability, and its protocol compatibility read-only. Anchor setup codes are refused until anchor mode lands. Domain adapters keep composite value codecs, intrinsic validation, and projection ownership; the sync engine owns delivery, causality, and merging. Durable replication, live presence, and executable commands are distinct protocols.

### Topology and authority

Content merges without a leader and any path may deliver signed operations; only authority is ordered, once per space. The reasons are in [Sync topology and authority](../architecture/decisions/sync-topology-and-authority.md).

| Role | Meaning |
| --- | --- |
| Coordinator | The desktop that pairs devices, serves their first snapshot copies, and runs the main hub. It founds the space and is its first anchor, and it stays coordinator after a handover moves the anchor. |
| Hub | Any member installation that stores and serves operations. Every linked member desktop, and a phone while the app is in the foreground, serves its LAN peers, authenticated by mutual TLS with the certificates its enrollment names. |
| Anchor | The one member desktop per space that sequences the hash-chained authorization log of enrollments, removals, roles, admin keys, and handovers. It never gates content. |
| Relay | **Partial.** A blind, self-hosted store-and-forward service for encrypted records. It is never an anchor. The server and the device relay pass exist in source; claiming a space from the app and physical acceptance are pending. |
| Always-on anchor | **Planned.** A self-hosted server running as an enrolled member that holds the keys, so it is also a hub reachable from every network and a backup. |

Editing and delivery continue while the anchor is unreachable; only authorization proposals wait. The implemented rules for admin keys, removal cutoffs, late changes, quarantine, fork evidence, handover, contests, and the recovery kit are in [Writers](#writers), and member listeners and record exchange in [Exchange](#exchange); the pure selection and exclusion logic is in [Sync merge rules](../algorithms/sync/README.md#authorization-and-exclusion).

### Storage ownership

Every persisted field needs an explicit replication classification before it can leave a device. Unknown fields fail closed. Device-bound state that must change atomically with vault data lives in local tables and columns inside the vault database: snapshot copies empty them, and a replacement restores them from the receiver's live database.

| Domain | Portable data | Device-local data |
| --- | --- | --- |
| Notes | Folders, pages, blocks, databases, templates, comments, suggestions, reactions, Trash, assets | Page history, editor undo, held edits, comment read and mute state, mention delivery, notification settings, block view state, search and link indexes |
| Projects, Calendar, Quick notes | Content, relationships, templates, archive, Trash, retained history, favorites | Recents, current selection, navigation, viewport layout |
| Preferences | Profile, themes, quick-toggle theme pair, language, time format, rhythm defaults, favorites, sidebar orders | Active theme, font family and scale, Calendar view mode, title bar, Notes notification delivery, update check time, recents, selection, and collapsed sidebar state |
| Distraction blocker | Rule definitions, daily usage totals per device, block history | Raw usage samples, permissions, application bindings, enforcement state, the native host spool |
| Music | Library items and metadata, roots, locations, source collections, playlists and memberships, snoozes, soundscapes and presets, assignments, artwork, and listening statistics per device | Root bindings, availability and file observations, media bytes, sessions and checkpoints, refresh jobs, current playback, volume, routing |
| Chat | Organizational content and work assignments | Drafts, review history, execution processes, provider configuration, credentials, provider homes, terminals, native trust, paths, caches |
| Managed assets | Immutable content and metadata | Transfer staging, local availability, caches |
| Focus | Closed runs with their segments, pauses, and run events; per-device activity rows | Open runs, execution state, receipts, heartbeats, adaptive state, local activity sources, native alarms and effects |

Unsent Chat drafts stay on the device where they were typed. Portable preferences live in the vault table `vault_preferences` so a preference change and its outbound record can commit atomically; each key replicates on its own, concurrent edits of one key resolve without a visible conflict, and the profile picture travels as a managed asset named by the `profile.image` value. User themes replicate one row per theme: the seed is fixed at creation, name and icon resolve to the latest edit, the editor's content merges as one unit and surfaces concurrent saves as a conflict, and a dismissed engine upgrade keeps the highest version. Device preferences, including device-local Chat settings, live in a per-vault file in the app config directory; the vault holds no configuration file.

### Transactional operation boundary

Every synchronizable mutation, including imports, restores, scheduled jobs, and native background writes, commits its canonical changes, required relational projections, and capture marks together. Sealing then turns captures into signed operations that carry stable identity, the installation writer, causal dependencies, the space, authorization revision, key epoch, and format and manifest versions. This is implemented for replicated tables; required history and asset references join the boundary as their domains convert.

UI invalidation and native effects follow commit. Incoming operations are validated intrinsically and applied in bounded transactions with capture suppressed; missing dependencies stay pending. A relay receipt means delivery to the relay, not that another device committed the change. The UI distinguishes saved on this device, received by relay, and confirmed on another device.

Authoritative connections already use WAL with `synchronous=FULL`, because WAL with `NORMAL` can lose committed transactions on power failure. See [SQLite synchronous](https://www.sqlite.org/pragma.html#pragma_synchronous).

### Conflict semantics

Valid concurrent operations converge regardless of delivery order; rejecting whichever arrives second is insufficient.

- Independent fields merge. Concurrent values for one scalar keep alternatives, a deterministic displayed value, and a visible resolution action.
- Calendar start, end, timezone, and recurrence form one coupled value. A conflict suspends automatic occurrence activation until resolved, while reminders and Android alarms follow the winning value. A background Android sync pass runs without the app, so reminders, Android alarms, and Guardian rules it changes refresh when the app next opens; until then Guardian keeps enforcing the rules it last applied.
- Notes and project placement use stable identities, a parent reference, and an order key per row. Cycles and rows past a maximum depth are repaired deterministically from merge state, as described in [Trees and acyclic edge sets](../algorithms/sync/README.md#trees-and-acyclic-edge-sets), instead of a [replicated move log](https://martin.kleppmann.com/papers/move-op.pdf) that every replica would have to undo and replay in one order.
- Deletion creates tombstones. Concurrent edits stay recoverable in Trash or conflict recovery, and old operations never silently restore deleted content.
- Database property type changes keep incompatible values for resolution.
- History restore writes a safety version and new operations against current state; it never rewinds causal history.
- Cross-feature actions such as task scheduling form one operation group.
- Scheduled messages and other executable jobs have one execution device and stable execution receipts. Receiving their records never executes them.

### Notes editing

Notes writes replace complete block payloads, and a block's text replicates as one surfaced value, so concurrent edits to the same block's text are a conflict rather than a character merge. Received changes commit with their SQL projections in the apply transaction; an open page then reloads around held local edits, rebasing an edit when at most one side changed the block's text and otherwise offering the choices described in [Editor](../features/notes/editor.md#persistence). Local undo never replays remote changes. Writer IDs are unique across installations, restored copies, and windows. Character-level merging with [Yrs](https://docs.rs/yrs/latest/yrs/), with relative selections, comment anchors, and shared UTF-16 positions, is planned with multi-person sharing.

### Keys and enrollment

Both enrolling devices show a verification code, and the existing device confirms before releasing vault keys. Direct connections use TLS 1.3 with pinned device identity, operations are signed, records and asset chunks use XChaCha20-Poly1305, and resource-key distribution uses HPKE with X25519 and HKDF-SHA256. Secrets live in native credential storage or Android Keystore wrapping. [HPKE](https://www.rfc-editor.org/rfc/rfc9180.html) alone does not provide authorization, replay protection, or downgrade protection, so the protocol composition needs review before transport is enabled.

Mutual TLS with pinned device certificates is the confidentiality boundary for direct links over any allowed private or overlay range, and it is the only confidentiality protection operations have today; their signatures give integrity and authenticity, not secrecy. Record encryption, when it lands, gates only intermediaries that store records, such as the relay or an anchor, never a direct link.

Enrollment and removal follow the anchor-sequenced authorization log described in [Writers](#writers); a removal rejects new operations from the removed device but cannot erase copies that device already holds. **Planned:** resource-key envelopes for the recovery kit, and removal rotating the affected resource keys, arrive with operation encryption.

### Contacts and contact requests

The vault's one person identity is an Ed25519 key pair, generated by the device that has no coordinator pin. That device creates it on the first sync pass after linking or on the first Contacts action that needs it, whichever comes first; other devices receive the row through sync, so Contacts sealing on them waits until then. The private key lives in native credential storage on desktop and, on Android, in an app-private file sealed under an Android Keystore key, as described for writer keys above. A linked device that holds the identity row but not the key asks the coordinator for it over the authenticated mutual TLS link. The coordinator releases the key only for the vault open there and only to a device linked for that vault, and the device stores it only when it matches the public key in its identity row. Every linked device therefore holds a copy, and unlinking a device does not erase the copy it already received. Person key rotation is not implemented. Every message the person key signs starts with a distinct, prefix-free domain (the card format magic and the contact request, status poll, writer certificate, and space charter domains), so a signature for one kind never verifies as another. Person and writer public keys that encode an Ed25519 point of order dividing 8 are refused when parsed and never verify a signature, because anyone could forge signatures under them.

Contact requests are the only messages the coordinator accepts without a client certificate. They ride the same listener and protocol as pairing: a request carries the signed requester card, the recipient's current card nonce, and a request signature, and a status poll carries a signed, time-bounded query so only the requester learns the outcome. The coordinator verifies signatures before writing anything, rejects a stale nonce as a revoked card, replaces an earlier pending request from the same key, acknowledges a repeated delivery of a stored request without writing, caps pending received requests, keeps handled requests only for a bounded time and count, and answers a blocked requester exactly as it answers an accepted write. Received requests persist only while the coordinator can write the vault. On the requester, a status answer applies only to a request that is still pending, so a cancel or block made while a poll is in flight wins, and no accepted answer ever clears a block; only an explicit unblock does. The bounds are recorded in [Network and privacy](security/network-and-privacy.md#current-network-surfaces); the user-facing behavior is owned by [Contacts and invitations](../features/collaboration/README.md).

Contacts, contact requests, and the card replicate concurrently, and every linked device may write them; the identity row does not. A contact row is keyed by the person public key, so removing a person on one device and adding them again on another settle on one row. Removing or unblocking a contact keeps the row with a `removed` standing and no trust, which readers treat as no contact; the row keeps the name and public key so the removal can merge, and a later add revives it. Concurrent standing changes rank blocked above removed above active, so a block outranks a concurrent removal, accept, or trust edit and is undone only by an explicit unblock, and a removal outranks a concurrent accept or trust edit. Within one standing the narrower trust wins, summed over both scopes: a conservative tie rule that keeps a concurrent revocation from being widened back, at the cost that a concurrent widening of one scope can lose to a narrowing of the other. A request answer outranks a pending state and acceptance outranks every other answer; a request deleted on one device while another answers it stays deleted. Concurrent card regenerations keep the higher card revision while revisions stay below 255, so every device signs the same card afterward; past that, concurrent regenerations fall back to the operation clock. Duplicate pending requests created on two devices both survive, lists show only the newest per person and direction, and an answer to one closes the others. Accepting a request verifies its stored card signature again, because the row may come from another device. Contacts changes resolve without a visible conflict or recovery entry. Polling a sent request records only device state and publishes nothing.

### Bootstrap, assets, backup, and compaction

Bootstrap transfers a consistent whole-vault snapshot carrying the full operation log over the handoff path, followed by incremental operations, staged and validated before atomic activation (see [Replacing and recovering vaults](#replacing-and-recovering-vaults)). A device asks the coordinator it enrolled with first and, for a fresh copy, then any member desktop its selected log shows as enrolled, not removed, and not quarantined, dialed through discovery or the peer book and pinned to the certificate that enrollment recorded. A first copy comes from the coordinator alone, because the log that names the other members arrives with it. A member listener serves a copy built the same way as the coordinator's only to a device its own selected log admits, asking for itself, one device at a time. Phones serve no copies. A typed snapshot with a causal checkpoint is planned. A phone with a different vault keeps it as a recoverable backup; combining vaults requires an explicit import preview.

Managed assets use immutable identities, encrypted manifests, authenticated hashes, bounded resumable chunks, and atomic publication. Filenames are metadata and never choose destination paths. Structured data syncs automatically; attachments default to unmetered transfer with explicit download and offline controls. Asset classes, content-addressed names, bounded resumable chunks, verification before publication, and atomic publication are implemented for the LAN exchange; encrypted manifests and transfer controls are planned.

Backups are implemented as encrypted whole-vault archives in the `GBBK` format (`ganbaru-sync-contracts` owns the layout). A random file key seals fixed-size chunks with XChaCha20-Poly1305, each bound to the header digest, its index, and a final-chunk flag, so truncation, reordering, and swapped chunks fail authentication. The header wraps the file key twice: under the current space epoch key, so any enrolled device opens it, and under the recovery kit's encryption key, so the kit alone opens it on a fresh install. An unlinked vault without a space key writes epoch 0 and opens only with the kit; a vault without a kit cannot write a backup. Creation holds the asset sweep lock until the archive is sealed, reads a consistent snapshot, and never puts plaintext on disk outside private staging. Plaintext zip backups are not read. Restore has two outcomes. A backup of the active space restores in place only when neither the active log nor the backup's log has another enrolled device; it replaces the database under the rollback rules and the writer check below. Every other restore produces an independent copy: a new vault id, sync state reset to a fresh genesis, and no recovery kit, person identity, or contact card. Desktop opens the copy from a folder the user chooses; Android replaces its active vault, and an Android device that is linked now refuses and asks the user to restore on a desktop or unlink first; devices its log enrolled earlier only make the restore an independent copy. No restore brings back credentials or installation state, rewinds acknowledgements, or resurrects tombstones in a live space. Compaction requires acknowledged checkpoints (operation body compaction is implemented; see the exchange rules above). Asset collection is implemented: one sweep per vault per day covers every asset class the manifest registers and deletes a content-addressed file only when no live row or retained version references it, no row of a device-only (`Local`) table names it through a manifest-declared asset column (a bare digest of one class, a `{class}:{sha256}` asset id of the classes the column lists, or a JSON path to either), no transfer touched it within a day, and it is older than a day. The sweep and every whole-vault archive (backup and handoff snapshot) share one process mutex, so an archive never reads a half-collected asset set; backups therefore need no persistent asset pins.

Vault replacement fences writers within one process; `vault.lock` keeps every other Ganbaru process out of the vault.

### Settings and Android delivery

Settings shows linked devices with their roles and the anchor, connection method, last successful sync, pending and unconfirmed changes, conflicts, recovery entries, late changes, and the recovery kit, with pause, retry, quarantine, removal, and reset, relay delivery counts while the space uses a relay, and the server with relay setup and removal. Unavailable assets and the same controls during onboarding are planned.

The sync status already carries the network class (local or overlay) and address of the coordinator a linked device last reached in this app run, and the degraded reasons the device can detect: Android background and standby restrictions, a connection refused because local network access is denied, and a Linux firewall that blocks the coordinator listener or a member listener until the person allows peers to connect, or, on a linked desktop whose browse found nothing, may block discovery. Settings shows each reason with its recovery action where the app has one.

Android background sync uses WorkManager only and never a foreground service; the app manifest removes the WorkManager foreground service. Background passes dial and never listen; only the visible app serves other members. A background pass runs only while the vault is linked and the active network has a Wi-Fi, Ethernet, or VPN transport, because cellular alone cannot reach a LAN coordinator. Background restriction by the user and the restricted standby bucket surface as degraded connectivity with a link to battery settings; battery optimization alone does not, because WorkManager still runs in Doze maintenance windows. Background service availability never establishes focus or idle activity.
