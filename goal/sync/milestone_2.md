# Milestone 2: engine generalization

**Status: Partial.** Implemented in source on `feat/sync`; only physical acceptance (step 12) is pending. Part of the [concurrent sync goal](README.md). This file is the implementation plan for turning the milestone 1 engine, which knows one domain, into an engine that every later domain milestone plugs into through a manifest file and an adapter file with no engine edits. [Device linking and synchronization](../../docs/data/sync.md) stays the owning contract; the engine contracts are [Sync engine decisions](../../docs/architecture/decisions/sync-engine.md), [Sync merge rules](../../docs/algorithms/sync/README.md), and [Sync schema](../../docs/data/schema/sync.md). The progress checklist is at the end.

## Outcome

When this milestone is done:

- A domain milestone converts a table by adding `src/manifest/vault/<domain>.rs`, `src/domains/<domain>.rs`, one line in the domain list, one line in the adapter list, its migration, and its catalog strings. Conformance tells it, by test failure, every trigger, foreign key, unique index, and column it has not classified.
- Device-bound rows (`Local` class) live in the vault database, commit atomically with domain writes, are never replicated, are writable on guarded replicas, and survive a handoff refresh or replacement on the device that wrote them.
- The engine supports every shape the remaining domains need: a per-domain replica write flag, references to any replicated table in dependency order including reference cycles and groups with several references, composite row keys, trees with deterministic cycle and depth repair, acyclic edge sets, cascade hiding of children with recoverable concurrent edits, derived keys that can be removed and added again, monotonic and parent publication, short deletion holds for Undo, generic and nested owned children, coupled groups with owned tables and references, post-apply hooks for Rust-maintained indexes and derived columns, streamed managed assets of any class up to 64 MiB, and conflict and recovery presentation keyed by table. Domain milestones never edit shared engine files.
- Winner values are stored once, in the domain row, and a group whose value equals the current winner is not sealed again.
- Quick notes behave exactly as in milestone 1, now expressed on the generic machinery, and a multi-domain simulation with a fixture domain covers every feature above.

### Decisions taken at start (2026-10-21)

- `replicated_writes` splits in two. `VaultOwnershipStatus.linked_replica: bool` keeps today's meaning (stable, linked, read-only role) and is what `database_access` (Guarded), `sync_enabled`, and the frontend's guarded-mode checks read. `replica_writable_domains: Vec<String>` lists the registered domains with `replica_writable` set, filled only when `linked_replica` is true. `require_replicated_writable` and `acquire_replicated_asset_write` take a domain name and admit the owner or a linked replica whose list contains it.
- Guards also cover replicated tables (and their owned children) of domains whose `replica_writable` flag is off, so a domain converted mid-milestone stays owner-only on replicas. `guarded_tables` takes the set of writable domains; guards render `WHEN NOT_APPLYING`, so apply still materializes them.

- Step 7 conformance also refuses an acyclic edge table whose endpoint table reaches that edge table through cascading references, the one shape where the step 5 edge cycle check would count a cascade-hidden row as visible.

## Design

### Domain registry and manifest split

- Each domain file exports `pub const DOMAIN: DomainManifest = DomainManifest { name, tables, assets }`. `src/manifest/vault.rs` keeps one `const VAULT_DOMAINS: &[&DomainManifest]` list in dependency order, one line per domain, and flattens it once into `pub static VAULT_MANIFEST: LazyLock<Manifest>` so `Manifest.tables` keeps its `&[TableSpec]` shape (today `VAULT_MANIFEST` is a plain static with explicit `derived` and `engine` name lists; the flattened manifest derives both).
- `src/domains.rs` gains `pub fn vault_adapters() -> Adapters`, one `.with(...)` line per domain. `Engine::vault()` becomes a thin wrapper over `Engine::with(manifest: &'static Manifest, adapters: Adapters, hooks: Hooks)`. The simulation and the fixture domain use `Engine::with` directly, so fixture tables never enter the vault manifest or `RECORDED_MANIFESTS`.
- Conformance checks that every adapter named by a table is registered, that every registered adapter is named, and that each domain's TableIds fall in its reserved range from the README. IDs 60000 and above are accepted only from manifests compiled under `cfg(test)`.
- `DomainManifest` carries `replica_writable: bool`. `VaultOwnershipStatus.replicated_writes` becomes `replica_writable_domains`, the names of registered domains with the flag set on a linked replica; Quick notes and the frontend vault state check their own domain name, so each domain milestone enables replica writes in its own manifest line.

### Manifest summary and version rule

- `fixtures/vault_manifest_v{N}.txt` becomes a canonical summary instead of Debug output: per table, id, name, class, key column, ordered groups with id, kind, merge flags, typed columns and bounds, owned codec choice and nested owned tables, reference columns with target and `on_delete`, resolutions, derived key, tree declaration with maximum depth, acyclic edge set, cascade declarations, publication predicate, and `published_with`. Adapter names, hooks, presentation, the replica write flag, `Local` tables, and `Local`, adapter-derived, or hook-maintained columns are not in it.
- "Changes the manifest" in the README reservation rule means "changes the summary". A step that changes the summary increments `VAULT_MANIFEST_VERSION` and adds the new fixture; on a merge conflict it takes the next number and renames its fixture. When the summary format itself gains a field (this milestone), existing fixtures are re-recorded with the default that reproduces current behavior and the version does not change.

### Local class

- `Classification::Local` for whole tables, a new variant of the existing `manifest::Classification`. `Local` columns on replicated tables keep their milestone 1 meaning: device-maintained values with a valid default on any device (revision counters, caches, availability probes); device-bound state that must survive a bootstrap goes in a `Local` table keyed by the replicated row's key.
- `local_columns` becomes `&[LocalColumn { name, materialize }]`: each declares the SQL literal materialize writes when it inserts a row from a remote create, so a `NOT NULL` column without a default needs no table rebuild.
- `Local` tables are never captured, never guarded, and never referenced by replicated tables. Every foreign key into a replicated table, from a replicated, `Local`, or Unconverted table, is `ON DELETE CASCADE` or `ON DELETE SET NULL` (conformance); a converting milestone rebuilds `NO ACTION` keys and keeps "in use" refusals as explicit command queries.
- `prepare_snapshot_copy` deletes the contents of every `Local` table and every unpublished row of a table with a publication predicate or a `published_with` parent, and writes every `Local` column's materialization value on every row (one update per table), in the same transaction that clears `sync_capture`. A snapshot therefore carries no device's `Local` state, and domains need no bootstrap reset of their own.

### Local restore on replacement

The receiver's `Local` rows are copied from its live pre-replacement database into the staged replacement before the rename, inside the existing snapshot quiescence. The retained rollback copy cannot be the source because it is not guaranteed to exist (`backup.rs:739` to 752, `database_rollback.rs:26`).

Sequence in `carry_forward_local_changes`, all before the staged folder is renamed:

1. Export the carry bundle as today.
2. Open the staged database, store the bundle's operations, and run `Engine::apply` in a loop until no waiting operation of this installation remains. The bundle file is then removed, and the service start import stays only as a path for bundles left by a crash.
3. In one transaction on the staged database: `ATTACH` the live database read-only, delete every `Local` table's contents and every unpublished row (including children of an unpublished `published_with` parent), insert the live database's `Local` rows and unpublished rows by column name in manifest order, copy `Local` column values by row key onto rows present in both databases (`UPDATE ... FROM`), then loop `PRAGMA foreign_key_check` and resolve each violation by its declared action (delete for `CASCADE`, null for `SET NULL`) until clean. Detach and commit.
4. Rename as today.

A crash at any point leaves the live vault untouched and the staging folder subject to the existing recovery. A different-vault replacement (`preserved_handoff_path`) copies no `Local` rows.

### Guard skip and domain trigger policy

- Guards render with `WHEN NOT_APPLYING`, so a replicated parent delete can cascade into Unconverted or `Local` children on a replica. Guards are TEMP triggers, so this needs no migration.
- Every non-engine trigger on a converted or `Local` table, or on an `Engine` table outside `sync_*` (milestone 4's `contacts_local_identity`), is declared on its `TableSpec` as `DomainTrigger { name, policy }` with policy `SameRow` (writes only `Local` or derived columns of the triggering row, for example self-revision), `Gated` (its `WHEN` contains the `NOT_APPLYING` expression), `ApplierVisible` (only aborts, for example an immutability check, a delete refusal, or a check that needs a parent row first), or `DerivedIndex` (writes only tables classified `Derived`, keeps firing during apply, for example the Quick notes `quick_notes_search_*` FTS triggers; it exists because milestone 1 already ships them, and new domains use `Gated` plus a hook instead). Conformance requires the declared set to equal the installed non-`sync_` triggers on those tables and token-scans each body: `SameRow` bodies update only their own table and allowed columns; `Gated` bodies contain the gate; `ApplierVisible` bodies contain no write; `DerivedIndex` bodies write only `Derived` tables.
- An Unconverted table's trigger that writes a converted table must be `Gated`. Milestone 6 drops the baseline triggers at `:489` and `:552` and moves their writes into Rust, so its conversion passes conformance.

### References and dependency-ordered apply

- A `Reference` group may target any replicated table, including its own (a tree) and earlier or later tables, and declares `on_delete: SetNull | Cascade`, matching the domain foreign key (conformance replaces the current SET NULL only rule).
- A `Register` or `Immutable` group may also hold several reference columns, each declared `ReferenceColumn { column, table, on_delete }` and resolved like a `Reference` group (redirects, duplicate hiding, cascade hiding); `MergeKind::Reference` stays the single-column case. Every foreign key column of a replicated table is declared this way in whichever group holds it, which is what the `on_delete` conformance check reads. Reference columns in a composite-key identity group are never redirected, because they form the primary key: a target hidden as a duplicate hides the row, and the target's duplicate recovery entry brings it back.
- Reference cycles of any `on_delete` are allowed. The domain list order must be a topological order of the strongly connected components of the reference, owned, and `ApplierVisible` edge graph; the apply transaction sets `PRAGMA defer_foreign_keys` once, so the tables of one component materialize together and foreign keys are still checked at commit. Owned and `ApplierVisible` edges never lie on a cycle (conformance). This covers the Calendar and iCalendar, Projects and Calendar, and Notes containment cycles.
- `domain_referrers` scans every table including the same one. No ordering within a table: deferred foreign keys make parent-first inserts unnecessary, and an `ApplierVisible` trigger that reads a parent row through a self-reference is refused by conformance.

### Derived keys

- A table may declare `derived_key: Some(DerivedKey { exists_group })`: its key is a function of content, its tombstones are never written, and its existence is a `Register` group with no domain column, declared in the table's group list with its own group id like any other group.
- `plan_captures` synthesizes the existence value: 1 for an insert or update capture, 0 for a delete capture. A delete is therefore sealed as a write of the existence group, not a tombstone, and a local insert of a known key seals every group as a write. A re-add therefore seals every `Immutable` group again and must write the same value, so on a derived-key table those groups hold only primary key columns (or the inputs of a `sync_key` or derived id); any other column, for example `created_at`, goes in a `Register` group (conformance). Materialize deletes the domain row while the existence winner is 0 and inserts it from retained values when the winner becomes 1. The recreate guard is not rendered for such tables, and conformance treats the existence group as columnless.
- A derived-key parent whose existence winner is 0 counts as deleted for cascade hiding.

### Composite row keys

- A replicated table with a single text `id` uses it as `key_column`. A replicated table with a composite primary key gains `sync_key TEXT NOT NULL UNIQUE` as its `key_column`; conformance requires it on every composite-key replicated table. Because `sync_key` is a one-way hash, every composite-key table also carries its primary key columns in an `Immutable` identity group, so a remote create can materialize them (conformance).
- `ganbaru_sync_contracts::derived_key(prefix, parts)` is the only `sync_key` encoder (a single-id table that declares `derived_key` may keep a domain formula for its id, such as Music's `stable_id`): `{prefix}:` plus the first 32 hex digits of SHA-256 over the NUL-joined parts, which keeps keys under the 128-byte bound. Domain crates call it in Rust, since SQLite triggers cannot hash.
- The converting migration fills existing rows with `'pending:' || rowid`; the domain's Rust conversion pass, run at vault open before capture seeding, rewrites every placeholder to its derived value, which is the same on every device because all replicas descend from one database. Engine startup refuses any `key_column` value that still starts with `pending:`, one generic check over the manifest. The rendered key immutability guard lets an update proceed only when `OLD` starts with `pending:`, so the pass needs no trigger juggling, and the re-create guard ignores `pending:` keys because they are never published.

### Trees and cycle repair

- A tree is a self-`Reference` group plus a `Position` group, declared as `tree: Some(TreeSpec { parent_group, position_group })`.
- In `finish`, after merge, the engine walks the winning parent of every touched tree row with a visited set. In a cycle, the node whose winning parent version has the greatest `(clock, writer)` resolves to the root; materialize writes its parent as null and keeps its order key. A sealing replica seals the repair as a write of that node's parent group, exactly like duplicate repair.
- `TreeSpec` gains `max_depth: Option<u8>`. After cycle repair, the deepest row beyond the maximum moves to the root, ties among equally deep rows going to the greatest `(clock, writer)` of the winning parent version, repeated until no row exceeds the maximum; a sealing replica writes the repair like cycle repair.
- A derived-key edge table may declare `acyclic: Some(AcyclicSpec { from_column, to_column })`. In each cycle among live edges, the edge whose creating version has the greatest `(clock, writer)` is hidden (not materialized) and surfaced as a conflict the user resolves by removing it or another edge of the cycle.

### Cascade hiding

- A row whose `Cascade` reference resolves to a tombstoned, existence-0, or hidden row is hidden: not materialized, and its domain row is removed by the parent's foreign key or by materialize. The walk keeps a visited set, so a reference cycle (step 3) hides nothing on its own.
- Repair tombstones for hidden children name their cause. The tombstone's trailing byte gains value `2`, followed by the cause's `TableId` and row key; a cause tombstone carries no redirect. An envelope carrying it uses the next `FORMAT_VERSION` (README wire versions rule), every other envelope stays at the current version 1, and readers accept both and reject the cause byte in a version 1 envelope. Older builds hold envelopes in the newer format. A local cascade (children deleted in the same seal batch as their `Cascade` parent) also names the cause. A hidden child in a derived-key table gets no repair tombstone and no existence write: it stays hidden while its cause is deleted, and grouped recovery restores it through the table's restorer, which derives its new key from the restored parent.
- The same `op.rs` change corrects the `OperationKind` comment: kind `3` is reserved for milestone 10's signed acknowledgement and kind `4` for milestone 11's authorization entry; `Revoke` (`2`) stays until milestone 11 removes it.
- `sync_tombstones` gains nullable `cause_table` and `cause_row`. A child's uncovered retained versions are evaluated against the cause's tombstone contexts, not the repair tombstone's. Recovery groups them under the cause: the parent gets an entry whenever any descendant has uncovered edits, `RecoveryEntryView` gains a descendant count, and restoring the parent restores the subtree with new ids through the table's restorer.

### Publication predicates

- A table may declare `publish_when: Some(sql)` over its columns. Capture triggers add the predicate to `WHEN`; an update that makes it true captures as a create with every group. An engine-rendered guard aborts any update that makes the predicate false for a row that satisfied it, and deletes of unpublished rows are not captured.
- An applied winner that fails the predicate is an invalid row. Replicated references to a predicate table are refused by conformance, except from a child table that publishes with it; owned children travel with the parent.
- A child table may declare `published_with: Some(PublishedWith { column, parent })`. While the parent row fails its predicate, child writes are not captured; the seal that publishes the parent captures the current state of every child row pointing at it, and later child writes capture normally.

### Deletion holds

- `sync_capture` gains nullable `held_until_ms`. Domain code calls `hold_deletes(conn, table, keys, until_ms)` in the same transaction as the delete; the engine clamps the lease to 10 s. Sealing skips held deletes until expiry; `next_hold_expiry` lets the service schedule a seal.
- Undo inside the lease reinserts the row: the insert capture trigger clears `deleted` and `held_until_ms` on the held capture row instead of replacing it as a create, so it seals as an ordinary write and no tombstone is ever sealed. Domain Undo calls `release_hold` first and refuses with its expired message when it returns false.
- Materialize skips rows with a held delete. Before applying a batch, `Engine::apply` seals the held deletes of every row the batch touches, so the incoming change stays concurrent with the delete and therefore recoverable.

### Capture seeding and batched sealing

- Engine table `sync_seeded_tables (table_id INTEGER PRIMARY KEY)`. The step 6 migration records the Quick notes TableIds, which milestone 1 seeded in SQL.
- `seed_captures(conn)` runs at vault open, after the app has run every domain conversion pass and before the sync service starts. In one transaction, for each manifest table missing from `sync_seeded_tables`, it upserts a create capture with the full mask for every row that satisfies the table's publication predicate, then records the table. It runs wherever migrations run (the vault owner or a standalone vault); a guarded replica receives seeded state through refresh, which empties `sync_capture` and carries `sync_seeded_tables`.
- Domain migrations therefore install triggers and fill placeholders but never seed captures. Milestone 11's Reset sync state clears `sync_seeded_tables` with the other engine tables, so the next open republishes every current row through the same function.
- Sealing commits at most 256 operations per transaction and reschedules itself immediately while captures remain, so a first publication of a large domain never holds the single connection for long. `Engine::apply` no longer seals everything first: before applying a batch it seals the captures of the rows the batch touches (the rule deletion holds already use), which keeps every incoming change concurrent with, or ordered after, the local edits it could overwrite.

### Post-apply hooks

- `trait MaterializeHook` in `ganbaru-sync`: `after_materialize(conn, table, changed_keys, changes: &dyn ChangeSink)` returning a boxed future, run in the engine transaction after materialize. Hooks take no `AppHandle`; the sink collects domain change notices that the caller emits after commit, so milestone 3's `SyncHost` drives the same hooks from the headless Android pass. Hooks are registered by the app at engine construction, so the engine never depends on domain crates and Rust-maintained indexes (Notes and Music full-text search) keep one implementation in their domain crates. The simulation registers fixture hooks.
- Hook-maintained derived columns are declared on the `TableSpec` outside every group: never captured, no foreign keys, defaults so materialize inserts succeed, excluded from codecs and the summary fixture, and recomputed by the domain's hook in the same transaction. Adapter `derived` stays for values computable from the row alone.

### Generic owned children

- `OwnedTable.columns` changes from `&[&str]` to `&[ColumnSpec]`, extending the existing `manifest::ColumnSpec { name, ty: ColumnType }` with `nullable`, `max_bytes`, `references`, and a `Blob` type, plus `max_rows` and `codec: Generic | Custom`. Replicated columns never use `REAL`; domains store fixed-point integers (conformance). An owned column may declare `references: Some(TableId)`: materialize skips an owned row whose target is missing, tombstoned, existence 0, or hidden, and the row stays in the group value, so it returns when the target does.
- A generic owned table is keyed `(owner, ordinal)`: its primary key is the owner's key column plus `ordinal INTEGER NOT NULL`. The generic codec is a row count followed by each row's columns in ordinal order, in the existing group field encoding; materialize deletes the owner's rows and reinserts them with ordinals from 0. Owned rows materialize under the apply transaction's deferred foreign keys, so parent links between rows of one owned table need no insert order. Conformance refuses a foreign key into an owned table from anything but its owner, its own rows, or its nested owned tables, because materialize replaces the rows. Existing `id` columns of an owned table may stay as `UNIQUE` non-key data columns carried in the row value; materialize reinserts the same ids, so readers keep addressing rows by id, and foreign keys into those ids follow the rule above. Custom codecs stay allowed (Quick notes keeps its codecs, so its version 1 operations stay valid; milestone 4 themes), but domains prefer the generic codec.
- An `OwnedTable` may own nested owned tables (`children`). A nested table's primary key is its parent owned row's full primary key (owner key plus `parent_ordinal`) plus its own `ordinal`, with a foreign key to that parent row `ON DELETE CASCADE`; the codec writes the nested rows inside each parent row, and materialize inserts parents first.
- Owned tables may sit in `Immutable`, `Register`, and `Coupled` groups beside parent columns; the group value is the columns followed by each owned table, and the group's merge kind applies to the whole value. A `Coupled` group may also hold declared reference columns resolved like `Reference`.
- `Coupled` groups, like `Register` groups, are either surfaced or silent, and may declare an adapter priority that decides concurrent versions before `(clock, writer)`.
- Every codec, generic or custom, must round-trip byte-exactly against domain rows: decode, materialize, read back, encode, compare (conformance over generated rows per owned table).

### Managed assets

- Each domain declares `AssetClass { name, max_bytes }` in its `DomainManifest`, where `name` is the directory under `assets/` (for example `quick-notes/images` or `profile`). Every class names files `{sha256}.{ext}`, with the extension from the content type and `.bin` when unknown, so the engine owns the one path function. Adapters gain `asset_refs(table, values) -> Vec<AssetRef { class, sha256, content_type }>`, so a reference can live in any group value, not only a column.
- `SyncAsset` gains `class`, validated against the receiver's registered classes and bounds, and `PROTOCOL_VERSION` takes the next number (README wire versions rule). The class is on the wire because the hub writes an upload straight into the class directory and enforces its size bound before the referencing operation arrives (`hub.rs:172` to 182).
- Transfers stream: the hub and the client write chunks to an exclusive temporary file in the class directory through `ganbaru-atomic-files`, hash incrementally, and rename on a matching digest, so memory per transfer is one chunk. `MAX_SYNC_ASSET_BYTES` rises to 64 MiB in the same protocol bump, so Chat attachments keep their 50 MiB limit.
- `ImageStore` becomes `AssetStore` keyed by class. A `ContentAddressedStore { root, class }` in the replica crate covers every class, so the replica crate drops its `ganbaru-quick-notes` dependency. `ganbaru_quick_notes::images::carry_images` (`images.rs:600`, called from `backup.rs:1010`) becomes `carry_assets` in the replica crate over every class.
- Every device fetches the assets its stored operations reference, as Quick notes images do today. On-demand fetch is out of scope for this goal. Deleting unreferenced bytes belongs to milestone 10's sweep, which counts references in live rows and every stored version, so domains declare no holds.

### Conflict and recovery presentation

- Status reports conflict and recovery counts per table name. `RecoveryEntryView` keeps its fields and adds the descendant count.
- `open_conflicts(conn, table)` returns each conflicted row key and group with its competing versions (writer, clock, decoded value); domain conflict cards and banners read it through the renderer registry, and resolution stays the milestone 1 resolve command.
- The app keeps a `RecoveryRestorers` registry keyed by table name; `ganbaru-sync-replica::recovery` takes the registry instead of calling Quick notes. Restore and close stay two transactions in that order.
- The frontend keeps a renderer registry keyed by table name for conflict cards and recovery rows, and a per-table changed-notice registry replacing the direct `publishQuickNotesChanged` import. Domain strings live in domain catalogs; `sync.ts` copy becomes domain-neutral.

### Winner elision

- Migration rebuilds `sync_register_versions` with nullable `value` (create new table, copy, drop, rename, recreate the foreign key to `sync_rows` and its indexes).
- At the end of `finish`, a pass over touched rows sets `value = NULL` on the winning version of each group when the row is live, not hidden, the group is not a `Reference`, and the row has no pending capture.
- Hydration is one function: read the domain row and encode the group when the row has no pending capture covering the group and is valid; otherwise decode the version's change from `sync_ops.envelope`. The hydrated bytes are checked against `value_hash` on every read.
- Materialize hydrates every elided version of a row before it updates or deletes that row, so a remote tombstone, a new winner, or a hiding repair never loses a retained value. A local write covers the elided winner, so sealing needs no hydration.
- Unchanged-group elision at seal: a captured group whose encoded value hashes to the current winner's `value_hash` is not sealed, when the group has no open conflict (resolving a conflict by picking the winner still needs a write that covers the loser). Calendar and Notes saves rewrite whole rows and children, so without this every save would conflict with every concurrent edit.

### Multi-domain simulation

- A fixture domain at TableIds 60000 and above: a tree table with a maximum depth and `Cascade` children, two tables in a `Cascade` reference cycle, a group with several reference columns, a derived-key membership table with a composite primary key and `sync_key`, an acyclic edge table, a predicate table with a `published_with` child and owned children on the generic codec, nested owned tables inside a coupled group with a reference column, a held-delete table, a `Local` table referencing a replicated row, a `Local` column with a materialization value reset by snapshot preparation, a hook-maintained derived column, a fixture asset class, and a fixture hook that maintains a count table. The fixture domain is replica-writable while Quick notes keeps its own flag. Each step adds the tables it needs; the simulation runs Quick notes and the fixture together with the existing invariants plus: no cycle in any materialized tree or acyclic edge set, no tree row beyond its maximum depth, no visible child of a hidden parent, hydration equals stored hash for every version, no sealed group equal to its uncontested winner, and fixture hook output equals a recomputation.
- New failpoints: `replace.before_restore`, `replace.before_rename`, `hold.before_seal`, `elide.before_commit`.
