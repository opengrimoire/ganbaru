# Notes and projects schema

Notes and Projects share project identity, navigation, task scheduling, managed working folders, assets, and history, but keep different canonical models. Notes is a document graph. Projects is structured planning data plus a logical working-folder boundary.

## Notes canonical graph

A page has stable identity, metadata, placement, trash and archive state, and an ordered block tree. Blocks have stable identity independent of their current parent and order. Mutations validate the resulting graph for cycles, stale parents, invalid project placement, and unsupported content before committing. The schema keeps only row-local checks and foreign keys; rules that span rows (folder cycles, folder placement and project, row hierarchy detachment) run in Rust inside the writing transaction. Recursive queries over pages, blocks, and folders use set semantics and a depth bound, so a corrupt parent cycle ends instead of looping.

A block row stores its text content (rich text, table cells, captions) in `text` and every other attribute in `attrs`, bounded at 256 KiB and 64 KiB; imports split oversized rich text into continuation blocks instead of exceeding the bound. Siblings sort by a fractional `order_key`, then id. Whether a block is open or its editing lock is set is device-local view state, not page content. A nested page shares its id with the `child_page` block that places it (`child_block_id`), so deleting that block deletes the page. Pages and blocks trashed together with a database carry that trash operation's token in `trash_owner`, so restore revives only what the operation trashed.

Page bodies are not canonical Markdown or HTML. Rich content is validated block data and text runs; rendered output, Markdown export, previews, and search projections are derivative. Page cover descriptors (a designed pattern with a palette slot, or an image reference with an optional focal point) are canonical and follow duplication, templates, and history, while image bytes stay managed assets. See [Page covers](../../features/notes/page-covers.md).

Trash is recoverable. Restore validates the current graph and chooses a valid destination instead of blindly reinstating a stale parent. Permanent deletion applies retention, asset, link, comment, database, and history rules through one domain service.

## Compound editor edits

Compound editor actions are one bounded native command over typed block, layout, and database operations on one page. Rust claims the SQLite writer before checking block preconditions, so the graph change, mention and asset-reference maintenance, one page-history snapshot, and the `notes_edit_receipts` entry commit or roll back together. Operations stay confined to the requested page, except copy sources and an explicit move between named source and destination pages.

Each receipt binds the operation identity to a digest of the complete request. A retry after an uncertain response or restart returns the original result; reusing an identity with different intent fails. Receipts live as long as their page. Block fingerprints are opaque equality tokens over payload, placement, lifecycle, and metadata, not clocks.

Undo is selective: it restores only changed payloads and placements from bounded preimages and never rewrites a whole page, so unrelated later edits and unloaded content survive. Limits bound operation counts, references, traversal, request and result bytes, and one copy budget across every copied source. Exceeding a limit rejects the whole action. In-memory drafts and pending editor requests never become a second canonical store.

## Placement and projects

A page is workspace-rooted, nested below one valid page, or placed through one valid project location (invariant 8 in [Data invariants](../invariants.md)). Moves update project and ancestry implications transactionally. Only a workspace page stores its project in `project_id`; a nested page stores none and belongs to the project of its nearest workspace ancestor, so a move never rewrites its descendants. Reads derive that project with a bounded ancestor walk, and the rule is enforced in Rust rather than by a schema check. Deleting a project keeps its pages as unassigned workspace pages with no folder.

Project working-folder Markdown stays file-authoritative and is not copied into the Notes graph. The project tree may show pages and files together, but their source-of-truth rules remain distinct.

## Notes databases

Databases define stable property identities, types, options, views, filters, sorts, groups, and row values. A page can be a database row without losing its page identity.

A database shell owns its data sources. A linked shell has independent views and an independent editing lock over another shell's sources; the lock is a local editing preference, not authorization. Copying a database assigns new identities to every owned object in one transaction and remaps internal references while leaving external ones intact. Trash follows owned sources and rows, never a linked shell's shared source, and records which objects each deletion changed so restore does not revive objects trashed independently.

Properties, select and status options, and row values are rows, not JSON columns: `notes_data_source_properties` (ordered by order key, type-specific settings in a config object), `notes_data_source_property_options`, and `notes_page_property_values` (one row per page and property, typed by its own `value_type`). Reads compose the schema and page properties objects from these rows. Rows whose identity is composite carry a `sync_key` derived from it; a migration leaves `pending:` placeholders, and opening a vault converts them before any command runs, while sync refuses to start on a vault that still has one.

Relations point to stable identities. A relation edge is stored once in `notes_relation_edges` under its canonical side, and `notes_relation_links` reads both directions: a two-way pair (per `notes_relation_pairs`, mutual dual configurations first, then a one-sided configuration naming an unpaired peer) shows the reverse edge under the peer property. Rollups and formulas derive from canonical values, and cached results need an explicit dependency revision and rebuild path. Property type changes need a conversion policy and keep incompatible values instead of reinterpreting them: a value whose `value_type` differs from the property's current type reads with its own type, filters and sorts treat it as empty, and the next edit of that cell replaces it. Deleting a property resolves relation, formula, rollup, view, and row dependencies explicitly.

A data source names its default template through `default_template_id`, which must be one of its own templates. Template blocks are keyed by `(template_id, ordinal)`, a preorder position; Notes checks that their ids are unique and their parents inside the template, and a template's whole content is bounded at 256 KiB and 1,024 blocks. Views order by an order key within their database.

Property names are unique per data source through Notes writes, but two devices can add or rename properties to one name. Reads then show every such property but the one with the smallest id as `name (property_id)`, so none is hidden from the schema, and the next schema write stores that name. Relation pairing is read from property configs, which merge independently: links stored in either orientation under a paired property read on both sides, and unlinking deletes both orientations.

Schema changes reconcile every referencing view, including linked shells, in the same transaction: deleted property references are removed, incompatible grouping and calculations are cleared, and surviving presentation is preserved. Saved views own grouping, wrapping, freezing, display formats, calculations, and conditional colors by stable property identity.

Row sub-items live in `notes_pages.parent_row_page_id` on the child row: at most one parent per row, same source, acyclic, and at most 32 levels deep. The column only holds a row of the same source; writers clear it when either page leaves the source, and deleting the parent clears it. Trash and archive keep it, so restored parents regain their children. Copies, graph export, and project history include the relationship.

Row windows use stable ordering and keyset boundaries (see [Query plans](query-plans.md)). Group counts and calculation footers describe the complete filtered source, including unloaded rows, and are read projections rather than canonical values.

Text predicates are one contract shared by SQLite queries, Rust export evaluation, and frontend conditional colors. `contains`, `equals`, and `not_equals` fold only ASCII `A-Z`, matching SQLite's default; there is no Unicode normalization, and wildcard characters are literal. Text is empty when null, empty, or made only of the 25 Unicode White_Space characters (U+0009 to U+000D, U+0020, U+0085, U+00A0, U+1680, U+2000 to U+200A, U+2028, U+2029, U+202F, U+205F, U+3000). U+200B and U+FEFF count as content.

## Links, aliases, mentions, and comments

Internal links store stable target identity when resolved, plus source block identity. Titles are presentation snapshots, not identity. Aliases and unresolved-link state let renamed or not-yet-existing targets reconcile without rewriting text. Backlink and unresolved-link indexes are rebuildable.

Mentions, comments, suggestions, and mention notifications keep author, target, thread, resolution, and delivery state as separate concepts. Comment reactions capture the reacting person's display name like comment authors do. Discussion mutes and page notification levels are per-person preferences; a page without a stored level notifies at the broadest level. Notification delivery is a projection. Deleting or restoring content never fabricates a new comment or collaboration identity.

## Assets

Managed Notes assets use feature-owned relative identities below the vault. An asset id is its managed class and content hash (`notes/page-icons:<sha256>`), so identical bytes in one class share one row. Page icons, covers, block files, property files, comment attachments, and imported files stay distinguishable so cleanup applies the correct references and retention. Rust validates type, size, content signature, and destination before importing bytes, and uses the staged workflow in [Data architecture](../architecture.md#transactions-and-filesystem-work). Exported paths never become canonical managed paths.

## Import, export, and working Markdown

Import is an explicit conversion into validated canonical rows; an arbitrary Markdown edit is never an implicit mutation. Transfer workflows stage, validate, and report conflicts before replacing content.

Working Markdown is a controlled bridge for selected Notes and related project context, with provenance and revision checks. Applying changes back requires an explicit command and conflict handling. It is not a second live source of truth.

## History

Page history stores bounded compressed snapshots with digests and retention metadata. Global retention is 0 (indefinite), 7, 30, 90, 180, or 365 days, and a project may inherit it or override it.

History reads treat stored data as untrusted: encoding, declared size, decompression bound, digest, and JSON shape are validated before use. Restore records the current state first, then applies the version as a diff in one transaction: rows still present are updated in place, later rows the version lacks move to the trash (folders and leaf rows are deleted), and only rows that are gone or moved elsewhere return with new identities. Restore never deletes and reinserts a surviving row, suppresses historical notification delivery, and rebuilds derived indexes.

## Sync

The local user, folders, pages, page aliases, blocks, databases, data sources, properties, options, property values, relation edges, views, page and data source templates, comment threads with their anchors, comments, comment reactions, and suggestions replicate as described in [Sync](../sync.md); every history, undo, view state, read state, mute, and notification table stays on the device. A nested page replicates only its `child_block_id`, a block only its parent page or block, and a database only its `block_id`, so a page's parent columns, a block's `page_id` and `plain_text`, and a database's parent columns are hook columns rebuilt from that placement after each apply. A row page's `parent_data_source_id` cascades from its data source, so removing a data source removes its rows and their content through foreign keys on every device. Properties, options, values, and edges are keyed by the derived key of their identity, so concurrent edits to different properties, options, or cells merge, and a removed row can be added again. An option names its property by the property's `sync_key` and goes with it. A template's properties, appearance, and blocks are one snapshot: concurrent template edits keep one whole snapshot and surface the other. A page moved out of its parent keeps its trashed `child_page` block; before a local delete of the page holding it, the block moves under its own page, still trashed, so its replicated row stays live and nesting the page again rewrites it in place. Remote changes queue page history snapshots in the device-local `notes_page_history_pending`, taken by the next history maintenance with a remote change reason. The `page_id` of a comment thread, anchor, or suggestion is a hook column rebuilt from the block or page it names, so moving a block carries its discussions. A comment body, its deleted flag, and a thread status are separate groups, so concurrent edits, resolves, and deletes all apply; a concurrent accept outranks a reject of the same suggestion. Reactions are keyed by the derived key of comment, person, and emoji. Comments on a block deleted on another device go with it and return when the block is recovered. Remote comments refresh mention candidates and reminders: a mention or reminder already due when it arrives settles as delivered without a notification, and a later reminder stays pending. A removed or deleted remote comment clears its candidates and attachment references.

Asset rows replicate too, keyed by their asset id, and are never deleted: path, kind, content type, size, and digest are fixed by the bytes, so two devices that add the same bytes produce the same row, and a file is named by its digest and the extension of its content type. Storage state and the update time stay on the device. Their bytes travel as the page icon, page cover, and Notes file asset classes, which every replicated reference names, including database icons and covers and template content. Reference rows are derived on each device after an apply; an asset row arriving after the rows that name it refreshes those owners, and a reference whose bytes have not arrived shows as missing until they do. History pins have no foreign key, so a pinned asset outlives its last block reference, and file cleanup never removes an asset a replicated or pinned reference names.

Block nesting is not an engine tree, so the vault owner repairs merged structure after each apply in one local transaction that replicates like any edit. A page that names a block other than its own `child_page` block becomes a root page of its project and its block moves to the trash, and a page that names none while its own block is outside the trash nests under that block again. The smallest block id of a cycle becomes the last root block of its page, a block deeper than the nesting bound becomes a root block of the page its ancestry reaches, and the smallest page of a nesting cycle becomes a root page of its project with its block trashed. A row whose row parent is no longer a row of the same data source loses that parent. Applies queue the changed page and block keys in the device-local `notes_sync_repair_pending`, which the repair clears in the transaction that repairs them: keys whose row is gone are dropped, and when repairing every key together fails, each key is repaired on its own, so a key that keeps failing stays pending without blocking the others. Repair leaves `last_edited_time` unchanged, since a clock reading would differ between devices. Repaired order keys follow the current last sibling, so two devices repairing at once can pick different keys and settle through an ordinary placement conflict. The page of a block in a cycle is the one it held before the cycle formed, which can differ between devices that received operations in a different order; one writer keeps this deterministic until replicas may write Notes. Folders and database row parents use the engine tree repair. Duplicate page aliases settle on the lowest row key.

## Search and derived indexes

Full-text search, backlinks, unresolved links, sidebar summaries, computed database values, and previews are rebuildable, each with an explicit source revision and invalidation rule. Authorization and project scope are applied before results leave Rust. A rebuild never changes canonical identities.

## Project planning

A project owns metadata, lifecycle state, optional grouping, views, statuses, tasks, dependencies, custom fields, templates, history, and scheduling links. Presentation order is explicit and deterministic.

Ordered Projects rows (groups, projects, sections, statuses, priorities, tags, checklist items, custom fields, options, views, and custom emojis) carry a fractional order key; tasks carry one key within their section or parent and another within their status. Rows sort by plain code-unit comparison of the key, then by id, never by name or locale, so two devices that insert at the same spot still agree. Clients request a placement before or after a sibling, or at the end, and Rust allocates the key; group, project, and view reorders send the full id list. Deleted statuses and priorities keep their row with `deleted_at` so tasks that still name them stay valid after a concurrent edit, but they are hidden from pickers, settings, and new-task defaults. Rows whose identity is a composite key carry a `sync_key` derived from that key, and dependency ids are derived from their endpoints, so the same logical row has one identity on every device. Number custom field values are stored as signed 64-bit millionths and cross the command boundary as canonical decimal strings, so values compare and merge exactly. Opening a vault runs a Projects conversion pass that replaces the placeholder keys a migration leaves behind before any command runs.

Project views are ordered rows with a type and an optional name. Task view types may repeat; commands add Notes and Chat views at most once per project, though two devices adding one concurrently keep both. New projects receive Overview, List, Notes, and Chat. A view owns its preferences (saved query, List columns and presentation), which are deleted with it; deleting a view never deletes tasks, Notes pages, or Chat channels. A reorder must list every view of the project once.

Tasks have stable identity independent of status, view, schedule, or parent. Dependencies validate both endpoints, reject self-dependencies and forbidden cycles, and survive reordering. Calendar links distinguish scheduled work from looser references.

Projects replicate as described in [Sync](../sync.md), and concurrent edits merge by these rules. A task move (section place or status place) wins whole. A merge that nests a subtask two levels deep moves the deepest task to the root, and concurrent dependencies that close a cycle hide the newest edge as a conflict. Duplicate tag, field, and option names from concurrent edits are kept, a selection of a deleted option is dropped, and a primary folder that another device archived stays stored while reads fall back to the managed folder. Every device may edit Projects except group deletion, external folder removal, and task event links, which stay with the owner. A recovered row returns with new ids for itself and its descendants, so references follow the restored rows and a restored project gets its own managed working folder.

Custom-field definitions and values are separate, and changing a definition validates existing values. Custom-field and Notes data source property icons are optional presentation metadata limited to Lucide icons (a `lucide:` value in Projects, the native icon object in Notes); no icon means the type icon, and emoji or uploaded icons are rejected. Templates create ordinary rows with new identities; template IDs never become privileges or shared mutable state. Project history records meaningful user changes, not derived counts, and restore goes through domain commands so task links, Notes placement, and working folders stay consistent.

### Native project mutations

Dependency date cascades, bulk status, priority, archive, and restore, and reordering are native commands with the same shape:

- Rust claims the SQLite writer, then reads the canonical state it needs, including unloaded tasks (archive and restore compute the full descendant closure).
- Only the intended field comes from the client, and its displayed value is checked against storage; unrelated newer fields are preserved.
- Rows, per-field history, and an immutable receipt commit together. Retrying the same request returns the committed result after restart; reusing an operation ID with different intent is rejected. Receipts are deleted with their project.
- Limits on tasks, edges, siblings, and receipt bytes reject oversized work without truncating its meaning.

A dependency cascade previews deterministic finish-to-start shifts over one consistent project graph and reports cycles explicitly. Apply recomputes the reviewed digest and rejects a stale preview. Restoring a child below an archived parent is rejected unless the parent is restored in the same operation. Reordering separates section order from status order.

Task, custom-field, and option rows carry a revision that increases on every update. The frontend ignores older revisions and keeps deletion evidence for pending requests, so a recovered receipt cannot overwrite newer state or resurrect removed schema. Absence from a paginated view is not deletion evidence.

A task edit sends every field, so it also sends the revision it was based on, and Rust refuses the write when the row has moved on. The client then reloads that task and reapplies only the fields the user changed, so an edit made in another window or by an earlier command is not overwritten. Each committed command tells the other windows of the vault which projects changed; they reload the selected project quietly once their own commands settle and mark other changed projects for reload on selection.

## Working folders

Every project has a durable managed working-folder row and a managed directory below the vault named by project identity. Creation uses staged compensation so a project never claims a folder that does not exist. Folder ids stay within 64 bytes because they become sync row keys, so a project id too long for its managed folder id is refused.

Creating a project or a working folder creates no Chat rows; Chat creates its defaults on demand (see [Chat schema](chat.md#organizational-layer)). The stored primary folder is a preference that may name a folder not present yet: the effective primary is the stored folder when it exists, belongs to the project, and is not archived, and the managed folder otherwise. A project without a stored row reads the managed folder at revision 0. The stored primary folder cannot be archived or removed until another folder is promoted.

External folders use the same logical identity but resolve through a device-local binding; absolute paths and filesystem fingerprints never enter the database. Chat authority over a project does not imply access to its folders; grants are governed by [Chat access control](../access-control.md).

Deleting a project must account for managed files, linked Notes, tasks, calendar events, Chat history, and external bindings. Its Notes pages stay as unassigned workspace pages: the page project and folder references are set to null, so no note content is lost. Filesystem removal is never an automatic foreign-key cascade. A task's section and status are cascading foreign keys, so deleting either row removes its tasks on every replica; commands still refuse deleting a status or priority a task uses and soft delete it otherwise.
