# Chat agents and coordination

Status: Partial. Model line, model, and named agents, channel-centered agent configuration, mention-triggered assignments, frozen context packages, assignment review states, structured delegation, and daily agent usage summaries are implemented. Quiet periods, task-linked assignments, and human collaborators are planned.

Ganbaru coordinates work through durable conversations, explicit assignments, and review. An agent is a model line, a model, or a named model, not a persona, and how it behaves is configured on the channel, as specified in [Channel-centered agent configuration](channel-configuration.md). There is no privileged manager agent or general vault agent, and nothing is seeded.

## Participants and agents

A participant is the local person, an AI agent, or (planned) a human collaborator. Each provider family has one agent per model line and one per catalog model, created when a device first detects that provider, with IDs derived from the family and the line or model so linked devices converge on the same agents; a person can add named agents with a model of their own, as [Channel-centered agent configuration](channel-configuration.md#agents) describes. Changing its model creates a new policy revision, not a new participant. An agent is archived and restored rather than deleted, because its identity is shared with other devices of the vault. Archiving waits until the agent's started work and the queued work this device accepted are stopped. Queued work that this device has not accepted, or that moved to another device, does not block it, because a linked device could otherwise keep the agent from being archived. Queued work of an archived agent stays queued instead of failing, even when another device had already accepted it; it does not start while the agent is archived and can be started again after a restore.

An agent's policy holds its model and model options; without one it uses the model Ganbaru recommends from the provider's catalog. Provider defaults are never offered, because they follow whatever was last chosen in the provider's own tool. The recommendation prefers the native company's balanced flagship, newest version first: Opus, then Fable, Sonnet, and Haiku for Anthropic, and Sol, then Astra, Terra, and Luna for OpenAI; mixed catalogs such as Cursor and OpenCode try Anthropic, then OpenAI, then their first listed model, and routing entries such as Auto are never recommended. Only a provider with no discovered models runs the model set in its own tool. Each device runs the agent through its own installation of that provider family.

Nothing grants authority by itself. An agent acts in a channel only after it is added to the channel, and then works under the channel's effective access (Talk only, Read only, Ask before commands, or Work on their own), inherited from the project and the app and resolved against what the provider on the device can enforce by [Chat access control](../../data/access-control.md).

## Invocation

Ordinary messages never invoke every visible agent. Work starts through an explicit mention, including one a scheduled message posts, or, in the future, a typed assignment or a documented workflow; an agent may propose a schedule, and a person confirms it before anything is scheduled. Mentions distinguish reference from invocation: naming an agent in prose is not enough, and an actionable invocation is visible before execution begins.

An invocation creates a work assignment in a reply thread, linked to its triggering message and any previous assignment. The assignment freezes its model and its composed app, project, and channel instructions when it is created. The model is the one a `/model` token in the starting message names (the token is removed from what the agent reads), else the channel's override for the agent, else the agent's default, else the provider default; work that continues the thread keeps the frozen model unless its message carries its own `/model`. When the executing device's provider does not offer that model, the run uses the provider default, and every reply names the model that actually ran. Assignments move through queued, working, waiting for an answer, waiting for approval, ready for review, completed, failed, or cancelled. A settled assignment run (completed, failed, or cancelled) ignores later provider events, so a late or replayed event cannot reopen it or change how it ended. A launch that fails posts one failure message in the thread and leaves the thread's follow-ups pending, so Retry delivers them to the next run. A reply in an assignment thread continues with that thread's latest agent without a new mention, so review feedback reaches the agent that did the work; this requires the agent to still be in the channel, and removing it stops implicit continuation. Only the local owner posts today; when other people can post, a reply continues an assignment only within its author's own authority (planned).

Assignments sync between linked devices, and each one runs on a single device: the desktop where the mention was posted, when it can write Chat and the agent's provider is ready there; otherwise the work waits for Start here on a desktop that has the provider. Android never runs agent work. When the executing device stops writing Chat, as after an unlink or a revoked writer, a device that can write Chat takes over its active work at startup: work that had not started and that the device already accepted moves over, unaccepted work waits for Start here, and started work fails with a reason so Retry can run it again. Start takes over a mention only while its work is still active; finished work is never rerun. When the mention arrives on another device first, that device shows it without starting work; a desktop can start it there instead (the Start action in the timeline is planned).

Work received from another device never starts by itself. The first assignment of an agent on a device waits in its reply thread until the user chooses Start here, and a Chat notice points to waiting work wherever it sits. The Start here notice names the provider and the access the work would hold. That acceptance covers the agent, its provider, the effective access with its folders and runtime approvals, and the frozen instructions and model, so later assignments with the same access, including ones already queued, run without asking, and any change to that access asks again. Start here accepts only the details the user saw: when a sync changed them first, nothing starts and the notice refreshes. Work queued to start here carries the details it was queued with, and when they differ at the moment it would start, it returns to Start here instead. Posting a message that starts new work, Start, and Retry on the device that runs the work also record an acceptance; a reply added to existing work does not. Scheduling a message, Send now, and Retry on the device that sends it consent to that message as it stands, so when it posts its work starts and records an acceptance of the access it starts with; a message scheduled or changed on another device posts on time, and its work waits for Start here unless its agent is already accepted, also after a restart, and runs on the target the message chose. Such a message never steers active work or closes a review: in a thread with active work it stays a plain message, and a reply to work ready for review waits as a pending reply until Start here, or an accepted agent, continues it on the target the message chose, while a mention of another agent there starts new work that waits for Start here and leaves the review open. A reply waiting after a restart continues only while that acceptance still matches. When the access changed, the reply stays pending in its thread until the user chooses Start here.

Any device can cancel an assignment, and cancelling it elsewhere stops the run on the device that executes it. Any desktop can review work that is ready for review: Accept completes it, and Request changes posts a note as a reply that continues the work in the same thread; any other reply to reviewed work counts as Request changes. Accept is refused while replies still wait on the work, and Request changes while no device can run the agent, so a review never leaves a reply that no run delivers. A Request changes note that the review card stops showing before it is sent moves into the thread reply draft. Scheduled messages sync too and are sent by the device each one names, under that device's writer; other devices can cancel them, and an edit made elsewhere while the message is being sent is lost, since the sent message keeps the sending device's text. Each occurrence of a repeating message posts once, under ids derived from the series and the occurrence, and a rule changed on another device makes later occurrences wait for Start here. A message whose stored request no longer matches its channel, thread, or mentions fails without posting and shows the reason until it is cancelled.

## Resolution before work starts

Rust resolves, and records with the assignment:

- Requesting conversation, participant, and project.
- The agent, its frozen model, and its frozen instructions.
- Authorized working folder or private scratch generation.
- A bounded context package.
- Effective access level, folder capability, and runtime approval.
- Provider, interaction mode, and capability.
- Planned: task link.

Provider-native trust, a previous run, shell availability, instructions, or membership in a broad channel cannot widen any resolved value.

## Context packages

A context package is a bounded selection of information frozen for one assignment, with each source's revision and content hash recorded. It includes the triggering message, its reply thread, channel messages, attachments, referenced resources, and the live notes of the channel that owns the work. Planned sources include approved Notes, task state, and Calendar context. The package is sent as JSON Lines, one record per source with its kind, ID, and text, so message text cannot pose as another source. Its byte budget goes first to the trigger, then the thread root, then the most recently updated channel notes up to 8 KiB, then the newest replies, then the newest channel messages; the notes open the package, each `channel_note` record naming who saved it and which agent proposed it, and the trigger is sent last so it reads as the request. A note that does not fit is left out whole. An agent reply in the thread longer than 4 KiB, other than the trigger or the thread root, travels as a `pointer` record with its size and an opening of at most 480 bytes marked as shortened, so a long earlier answer does not crowd out newer context; its source entry hashes the whole reply, so a continued session does not receive it again. A record cut to fit carries its original length in `truncated_from_bytes` and its source entry hashes the text actually sent, and when replies, channel messages, or channel notes are left out, a final `coverage` record counts them. The package records how many visible replies, channel messages, and channel notes it excluded, including those dropped for size, and lists only the sources it actually sent. Messages posted in the thread while the work runs reach the agent as `follow_up` records in the same format. A run that continues the native session of an earlier run receives a delta instead: a `continuation` record that counts the sources it leaves out, then, in package order, only the sources the session has not received with the same content (an edited message or note is sent again under the same ID and replaces the earlier record, and a note deleted since the session received it is withdrawn once by a `channel_note_removed` record) and that it did not post itself, with the trigger always included and the package's `coverage` record kept. Sources count as received only when the run that sent them, by package, steer, or queued follow-up, reached the provider and has not failed or been cancelled; the full package stays the audit record.

Context assembly follows the channel's access and the execution target: under Talk only the package and instructions carry no folder, file name, or path from disk. It never scans the complete vault or attaches unrelated history because it might be useful. The recorded package makes later review possible without treating provider memory as canonical.

## Results and review

Agents report material outcomes as typed updates (plan, replan, question, approval, failure, result, review) rather than narrating every tool call into a shared channel. Detailed execution stays in the run timeline. Agents post plan, replan, and result reports, suggest channel notes for a person to save or dismiss, and ask questions of the person who assigned the work through host tools; a question offers answer choices, and a reported result moves the assignment to review. An agent under Ask before commands or Work on their own asks to push the same way: the request shows the branch, destination, remote URL, and commit, and nothing reaches the remote until a person confirms it on a desktop device. The person may choose Push and don't ask again, after which later requests of that agent in the same channel for the same folder, remote URL, and branch push on their own when the turn ends; the channel's Agents section lists these approvals for revoking, and lowering the channel's effective access below Ask before commands or removing the agent from the channel ends them (see [Chat security](../../data/security/chat.md#push-requests)).

Each completed assignment that was reviewed records whether it was accepted or changes were requested, who reviewed it, and when. Review focuses on decisions and risk: what changed or was proposed, what could not be completed and why, which assumptions or approvals affected the outcome, what needs human judgment, and which checkpoint or files hold the result. Approval of one result does not grant standing approval for later work, and rejected or superseded proposals remain understandable in history.

The review queue lists, across every channel of the vault, the assignments waiting for an answer or an approval, or ready for review, in that order, and a continued assignment leaves it. Failures stay out of the queue because they have no outcome to record: the channel row shows a red dot for a failure the person has not seen, the reply strip of its thread shows the same dot, and both clear when the person opens the channel or that thread after the failure. In the reply thread, the failure shows at the end of the agent's failed message in localized text, with Retry on the newest failure while the work is still failed and a copy button for the stored error code and diagnostic text, which never shows as the message. A capped queue says how many items it does not show. Batch accept accepts each selected review on its own against the revision the queue showed, so a partial batch is honest: work that changed meanwhile is reported as stale and stays in the queue.

Proposals that would change Projects or Calendar remain drafts until accepted through the owning feature's typed command. See [Guided planning and review](../projects/guided-planning.md).

## Delegation

An agent delegates through a host tool to another agent in the channel. The child is a visible assignment in its own reply thread with its own objective, expected result, and review path, at most two levels below the work a person assigned and at most four open children per assignment. The helper works under the same channel access, and its authority is never broader than the parent's, because the starting device clamps it against the parent's frozen folders, and its outcome is posted back to the parent's reply thread. Cancelling the parent cancels its open descendants. Parallel work stays visible as separate, independently cancellable assignments rather than hidden provider-native subagents, and a failed child never broadens another assignment to compensate.

## Anti-burnout constraints

Coordination should reduce work fragmentation, not create pressure to supervise agents continuously. Defaults favor bounded work, quiet progress, batch review, explicit deadlines, and visible usage. The system must not manufacture urgency, shame inactivity, optimize for message volume, or treat agent activity as proof of human productivity. Repeating messages wait until the sending device's quiet period or Focus phase ends, while one-time messages keep their chosen time. Desktop Chat notifications cover only work waiting for the person (a question or an approval), work ready for review, and failures, each with its own switch; progress, queued work, and completed turns stay silent. A change waits five seconds before it notifies, so short-lived states pass silently, and it is skipped when its reply thread is open in the focused main window. During a Focus phase or a quiet period, and while the quiet state or the Chat settings cannot be read yet, notifications are held and delivered when that ends, as one summary when several changes waited; the main window reads both itself, so notifications do not depend on an open Chat view. Only the device that executed the work notifies, so linked desktops do not repeat it; every device still shows waiting work in the review queue, marks failures on the channel and thread, and announces both. Notifications name the agent, channel, and kind; a failure reason appears only when the device allows notification content.

Work carries no token or working time limit; it runs until it finishes, fails, or a person stops it. A provider usage limit that stops work shows the reset time the provider reported on every linked device, and nothing retries automatically after it, so no spend happens unseen. Each agent's counted tokens and working time are recorded per day, summed across the linked devices that ran its work, but no view shows them yet; working time counts only while the agent works, not while it waits for an answer or approval.

## Authority and safety

Destructive, externally visible, credential-related, security-sensitive, or broad-scope actions require typed boundaries and appropriate confirmation. Revocation stops future reads and context assembly without rewriting legitimate historical messages.
