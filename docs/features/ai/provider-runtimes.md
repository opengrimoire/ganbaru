# AI provider runtimes

Status: Implemented on desktop for Codex, Claude, Cursor, Grok, and OpenCode. Adapters live in `crates/ganbaru-chat-providers/`.

Each adapter normalizes provider-native events into stable Ganbaru contracts while keeping enough native detail for inspection and recovery.

## Shared contract

Each adapter supports exactly the capabilities its metadata advertises; anything else stays absent or disabled. Provider direct actions are not offered in teammate threads, where commands only insert text into the message. Ganbaru never simulates approval, continuation, cancellation, interactive input, model selection, or reasoning controls that the provider cannot truthfully perform. Teammate runs follow the same user and project instruction files (`AGENTS.md`, `CLAUDE.md`, and rules) a direct run in that folder would: Codex and Cursor load them natively, and Ganbaru sends them as text with the teammate instructions to Claude, Grok, and OpenCode, which skip some under teammate restrictions (for Grok, the `~/.claude` and `~/.cursor` home files the sandbox hides); see [Chat security](../../data/security/chat.md#project-provider-configuration). Organizational runs treat a provider that silently starts a fresh session in place of the one they continue as a lost session and resend the full context package.

All transports apply bounded parsing, payload limits, timeouts, cancellation, process-tree cleanup, redaction, and stable error categories. Short probes (version, account, and catalog queries) read each output stream only up to a fixed limit and stop the whole process tree once a stream exceeds it or the probe times out. Provider output is untrusted input: unknown events may be kept for diagnostics but never become typed application state without validation.

Usage reports carry provider facts only. Context fill is the size of the newest root model request measured against the main model's context window, turn and thread counts are the totals the provider reports, and cache writes appear only when the provider sends them. Every provider's counts follow one convention: input excludes cache reads and writes, and output includes reasoning. Each report names what its counts cover: one model request (OpenCode), the running turn (Claude, which reports before the turn ends so failed and interrupted turns still count), or the thread's lifetime total (Codex). A report with no documented scope, such as an ACP context update, is shown but never counted toward usage. Rate limit status carries the windows and reset times the provider reports; a provider that reports none shows none.

Users may set any launch arguments, environment variables, and provider settings their CLI accepts. Values on a per-family allowlist (formatting and locale variables, telemetry, timeout, and context window switches, inherited API key variables, and a few cosmetic flags) apply immediately. Anything else, including values typed in settings, applies after one native confirmation on this device, and arguments that duplicate options Ganbaru manages (protocol mode, output format, session selection and continuation, permission and approval transport) are always rejected. Claude teammate runs accept no launch arguments at all, so a provider instance with launch arguments cannot run teammates. Executables and provider homes chosen with the native picker, or the family default command, apply without asking. Default commands and Settings discovery search only absolute `PATH` entries, the usual user install folders, and Homebrew on the platform that has it, and skip any program that every local account can write or that sits in a folder every account can write, so a planted copy never becomes a provider silently. See [Chat security](../../data/security/chat.md#provider-configuration-and-secrets).

Settings > Agents > Agent files lists each provider instance beside the user files it reads: the global instructions file, then typed controls for a catalog of common preferences with links to the provider's documentation, then the raw configuration file. For Claude and Cursor the catalog is the allowlist their teammates keep. Codex and Grok `config.toml` and OpenCode `opencode.json` and `opencode.jsonc` (both read as JSONC) get catalogs of reasoning display, compaction, output limits, update, sharing, and telemetry switches, which teammates load natively with the rest of the file. The catalogs leave out models and effort, approvals, sandboxes and permissions, MCP servers, providers, credentials, and hooks, which stay in the raw editor or Ganbaru's own provider settings. A preference edit changes only that entry and keeps every other key, its order, and the comments of TOML and JSONC files; a Claude or Cursor JSON file is rewritten pretty-printed. A file that does not parse must be fixed in the raw editor first, and a value outside its type is flagged instead of shown. Files follow the folders the CLI reads: a Grok instance with an API key uses its private home, Cursor follows `CURSOR_CONFIG_DIR` and then an XDG configuration folder that holds `cli-config.json`, and an OpenCode instance with its own home also shows the global configuration OpenCode still loads. Sources the page cannot show or that teammates skip get a short notice with the path and a link to the provider documentation: Cursor User Rules kept in the Cursor account, the user's own Grok home that an API key instance replaces, Grok's home rules folder and the `~/.claude` and `~/.cursor` home instructions Grok also loads, a non-empty Codex `AGENTS.override.md` (also shown as an editable file), OpenCode's fallback to `~/.claude/CLAUDE.md` and files its `instructions` field lists, and Claude's home rules folder. The Cursor CLI loads no home-level rules or `AGENTS.md`, so the private home of a confined Cursor teammate drops nothing.

## Discovery and model catalogs

Native discovery owns provider readiness, model identities, and capability options, including cached catalogs. The frontend validates the catalog and never infers capabilities from model IDs or labels; distinct routing aliases stay selectable even when they share a display name.

Discovery is lazy. App startup and vault preparation load cached Chat history and settings without launching provider processes; opening Chat or Settings > Agents starts automatic discovery once per vault, and explicit refresh is always available. Probes, catalog queries, and thread lifecycle calls outside a session run in a fresh empty directory that only the user can access, so project configuration in the folder the app was launched from never loads. A failed probe leaves local history usable, and late results never overwrite settings from another vault or a newer load. A status check never authenticates or creates a session; model refresh does.

Rationale: provider probes spawn external processes, so they must not slow startup or block reading local history.

Each device keeps the newest plan limits it observed per provider instance and when it last used that instance. Ganbaru never polls for limits: a status probe of a signed-in Codex account, or of a Claude account with a plan, reads them once over the connection the probe already opened, without starting a turn, and Claude turns refresh them from their rate limit events. The first time Chat opens in an app session, enabled providers that have gone an hour without a successful probe or limit report get one status probe each in the background, so limits and sign-in state are current without visiting Settings. The Claude read uses the CLI's experimental usage request, so a CLI that lacks it or changes its reply only leaves the last observation in place. The agent profile card lists the 5-hour and weekly windows with the share left and the reset time, and the Settings provider header shows one ring per window, each with its own details on hover; both say when the reading is older than an hour. Model pickers order providers that are ready first, then providers limited until a future reset, then providers that need setup or sign-in, breaking ties by most recent use; the Settings provider list keeps a stable order.

Rationale: extra provider requests could look automated to the provider and cost memory and battery, so limits are read only where a probe or turn already talks to the provider.

## Codex

Codex uses its native app-server protocol. Ganbaru owns the process, thread association, event ingestion, interaction requests, cancellation, and workspace authority. The app-server thread identity is an execution detail and never replaces the Chat conversation or agent identity. Provider-supported model, reasoning, approval, and sandbox choices are recorded with the run. Teammate instructions join the thread when it opens or resumes. A checkpoint restore rewinds the native thread to the restored turn, so the provider context matches the restored conversation; a turn Codex no longer has fails the restore before any workspace change. Codex rate limit updates are sparse, so Ganbaru merges them per metered limit and reports every known window together.

## Claude

Claude uses its native bidirectional stream-JSON protocol. Ganbaru speaks that control protocol directly instead of through the TypeScript Agent SDK, because the SDK wraps the same CLI protocol and would add a Node runtime and its dependency tree; replay transcripts and compatibility ranges catch protocol drift. Ganbaru owns the process and translates streamed messages, tool activity, permission requests, questions, and completion into canonical events. Session identity stays provider-local, and resuming a session must keep its authorized project and execution target; it can never silently resume in a different folder. Subagent frames stay out of the root stream and never move the resume cursor. Teammate runs load only an allowlist of built-in file, planning, and question tools beside the internal server, and stop when the CLI reports any other built-in tool; see [Chat security](../../data/security/chat.md#project-provider-configuration). Teammate runs load no Claude settings files, but they keep an allowlist of user preferences that only shape answers, thinking, limits, and reporting (response language, thinking defaults, commit attribution, and variables such as `CLAUDE_CODE_DISABLE_1M_CONTEXT`), copied from the user settings file or the host environment and checked against their types, so a teammate answers like the user's own runs and uses the context window the model picker shows. Confined Cursor teammates likewise keep the boolean Max mode, HTTP/1 transport, and attribution switches of the user CLI configuration. Teammate instructions join the system prompt when a session opens or resumes, inline or through an owner-only file when they exceed 16 KiB. On CLI versions that record the system prompt of a conversation (2.1.267 and later), Ganbaru turns that record off for launches with instructions, so a resumed session follows the current instructions and not the ones it first opened with. A turn whose instructions differ from the running session's fails with a retryable conflict instead of changing them silently. Effort and Fast mode change in the running session without a restart. Host proxy and CA certificate variables reach the CLI. Claude reports each rate limit type separately, so Ganbaru merges them per type and a request stays limited until every rejected type resets. Rate limits and root API retries become typed notices; the timeline does not render them yet.

## ACP agents

Cursor, Grok, and any other agent that speaks the official Agent Client Protocol (ACP v1) run on one bounded ACP runtime. Cursor and Grok keep provider-specific executable discovery, credentials, model handling, interactions, continuation, and diagnostics; a generic ACP agent instance names its own executable. Capabilities such as native resume and image input come from the initialize negotiation. Host tools reach a generic agent only when it advertises HTTP MCP server support; otherwise its sessions run without them. A status probe sends only initialize. Teammate instructions travel with the first prompt of each native session, and again only when they change; a session loaded to continue a reply thread under an unchanged continuation key already holds them, so its turns omit them. Loading a native session for resume suppresses the history the agent replays, because the provider already restores its own context and the Ganbaru timeline is the history the user sees; permission requests that arrive during the load are cancelled.

## OpenCode

OpenCode runs as a local server reached through its HTTP and event-stream interfaces. Ganbaru reconciles streamed and fetched history, deduplicates events, keeps events whose own or nested session ID names another session (such as a subagent) out of the thread, reconnects within bounds, and keeps cancellation and session ownership explicit. When the user allows a request for the session, Ganbaru keeps that grant for the session and answers each later matching request once itself; it never writes the grant into OpenCode configuration. An event stream that stays silent for 180 seconds while a turn is busy reconnects and reconciles history; idle time does not count.

## Compatibility

Recorded bidirectional replay transcripts and focused tests define the supported protocol surface. Each provider has a minimum version, a newest tested version, and optionally a ceiling where a protocol line Ganbaru has no runtime for begins. A version below the minimum or at the ceiling is refused with a recoverable error, and a newer untested version below the ceiling runs with a notice. Codex accepts 0.156.0 and later, is tested through 0.167.1, and stops at 1.0.0. OpenCode takes its range from its compatibility range table (`OPENCODE_COMPATIBILITY` in `crates/ganbaru-chat-providers/src/opencode/cli.rs`), and releases at its ceiling, prereleases included, are refused until a runtime for that protocol exists. Claude, Cursor, and Grok keep their ranges beside their protocol constants; Grok accepts 1.0.77 and later and stops at 2.0.0. Teammate runs can need a newer version than direct threads: Claude teammates need 2.1.314, or 2.1.325 where the sandbox helper confines their commands, OpenCode teammates need 1.19.5, and confined Cursor teammates need the verified Cursor build. The status probe reports that teammate minimum, and Settings > Agents > Providers names the needed version with the provider's own update command (`claude update`, `codex update`, `cursor-agent update`, `grok update`, `opencode upgrade`) instead of failing later in a run. Where automatic update notifications are on, the app checks each enabled provider for a newer CLI shortly after startup and then at most daily: Claude reads its release channel (`autoUpdatesChannel`) from `downloads.claude.ai`, Codex and OpenCode read their npm package's latest version, Grok runs `grok update --check --json`, and Cursor is not checked because its CLI updates itself. A release at or past the family ceiling is never offered. Settings > Agents > Providers then names the new version with the update command, and an Update button runs that command unless a package manager owns the install; OpenCode and Grok are pinned to the checked version, while Codex and Claude update along their own channel.
 When a provider has no configuration or its probe cannot find the program, Settings > Agents > Providers shows that provider's own documented installer for the platform with a link to its install page; Ganbaru never runs an installer. When a provider changes its protocol incompatibly, the adapter and its fixtures are updated without weakening the shared authorization boundary.

Dependency choices and rejected alternatives are recorded in [Chat dependency decisions](../../architecture/decisions/chat-dependencies.md).
